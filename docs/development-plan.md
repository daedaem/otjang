후속 백업 사전 검증 시작: 정리 #73까지 머지된 master `d26a69a` 기준이다. 먼저 추가한 검사8개에서 손상/미래 메타데이터·상담 ID/등록 URL·직접 복원 사전 거절·React 영수증 집계의 7개 실패와 정상 원문 왕복1개 통과를 확인했다. 실패 테스트 커밋 뒤 구현을 수정하며 완료 전 진행 중 표시는 유지한다.

갱신: 2026-10-25. 확인한 원격 master는 `f620c35`다. 테스트 보존 [#69](https://github.com/daedaem/otjang/pull/69) → 코드 위치 [#70](https://github.com/daedaem/otjang/pull/70) → 입력 상태 [#71](https://github.com/daedaem/otjang/pull/71)은 매번 새 master CI를 확인한 뒤 순서대로 머지했다. 남은 문서 [#73](https://github.com/daedaem/otjang/pull/73)을 검사·머지한 뒤 승인된 백업 사전 검증을 별도 PR로 수행한다. master 병합·배포·실물 검증은 구분한다. 이 문서 작업에서 운영 API나 실물 휴대폰을 새로 검사하지 않았다.

[대표 요구사항](owner-requirements.md)과 [사업 계획](business-plan.md)이 목표의 기준이며, [시스템 인수인계](system-handover.md)가 구현·운영 경계를 설명한다. 이전의 상세 판단·검사 이력은 [정리 전 개발 계획](log/2026-10/development-plan-before-cleanup-20261025.md)과 [재작업 기록](log/2026-10/repository-cleanup-rework-20261025.md)에 보존한다.

## 시작 전 확인

한 영역은 한 번에 한 에이전트만 변경한다. 원격 master와 이 파일 맨 위의 진행 중 표시를 먼저 확인한다. 담당·범위가 겹치면 다른 기능 PR을 시작하지 않는다. 읽기 전용 검토는 병행할 수 있다. 현재 자료를 지우거나 옛 브랜치의 구현으로 덮어써서 충돌을 해결하지 않는다.

## 저장소 정리의 완료 기준

- #59~#62는 대조·보존 근거를 남기고 종료. #63~#65도 새 PR 링크를 남기고 종료한다. 브랜치 삭제를 반복하지 않는다.
- #61의 기존 12검사와 #66의 11검사를 [대조표](log/2026-10/backup-tests-reconciliation-20261025.md)로 설명하고, 정본 위에서 가능한 누락 검사만 #69에 보존한다. 옛 저널·추가 validator·집계 동작을 몰래 되살리지 않는다.
- 위치 이동은 최신 파일을 스크립트로 옮긴다. rank/core import 경로 외 예산·BK·반품·MIME·기존 검사·부팅 원문은 `python3 tools/repository-cleanup/check-preserved.py`의 12항목으로 비교한다.
- 테스트 수와 각 단계의 실제 결과를 기록하고, 이전한 검사와 제외한 옛 계약을 구분한다. 모든 새 PR의 병합 대상은 master이고 위 순서를 따른다.
- 구현·검증·인수인계 정리를 마치면 진행 중 표시를 지운다. 실제 병합·배포가 뒤에 일어나면 인수인계도 그때 갱신한다.

2026-10-25 후속 승인: #69 → #70 → #71 → 문서 PR #73을 하나씩 새 master CI 확인 후 머지한다. 그 뒤 백업 사전 검증을 별도 PR로 수행한다. 손상/미래 초안·등록 메타데이터, 백업 파일의 상담 ID·등록 URL, React 등록 영수증을 포함한 미리보기 건수를 다루며 실패 테스트를 먼저 커밋하고 수정 커밋으로 통과시킨다. **이 후속 수정까지 마친 뒤 진행 중 표시를 지운다.**

## 정리 후 이어갈 우선순위

| 순서 | 작업 | 완료로 인정할 증거 |
|---|---|---|
| 1 | 대표 실물 기기에서 현재 흐름·자료 보존 확인 | 기존 자료를 먼저 내보내 보존한 뒤 iPhone Safari/PWA와 Galaxy의 설치·재실행·한글 입력·뒤로가기·초안 복원·저장 실패·방문 뒤 오프라인을 확인. 버전/기기/입력/결과 기록. 초기화로 해결하지 않음 |
| 2 | 상담 설명의 남은 한계 확인·개선 | 예산 이하/초과/최소/가격 모름/한 벌과 합계/이어 묻기, 이름 없는 지칭과 핏·색 사례에서 카드·사실 줄·답을 대조. 실제 제공자 호출은 기존 승인·한도 안에서만, 관찰하지 않은 정확도 수치 금지 |
| 3 | 외부 후보의 비교·옵션·구매 기록 연결 설계·부족분 구현 | 공급원/후보/옵션/원문/확인 시각을 보존하고 동일 후보로 돌아옴. 옷장 0벌/보유 옷 경로와 새로고침·백업 왕복 확인. 실제 거래 확인 여부 별도 표시 |
| 4 | 공개 출시 가능한 상품 공급 확보 | 공급자별 표시/저장/AI/이미지/갱신·삭제/광고 조건의 근거, 허용한 데이터만 사용하는 공개 목록과 검사. API 키 발급·검색 성공만으로 권리 확보 완료 처리하지 않음 |
| 5 | 중고 매물 공식 경로·재사용 가치·커뮤니티 | 승인 경로의 실제 매물·상태·시각·링크 확인. 없으면 외부 검색으로 표시. 본인 실사용 관찰부터 하며 외부 모집/계정/비용/공개 운영은 별도 결정 |

사진 식별·가상 착용/영상·동일 상품 최저가·확인된 주문 연동·자체 결제는 장기 목표다. 보류를 완료·삭제로 바꾸지 않는다. 공개 출시 전에는 데이터 권리·기상 데이터 상업 조건·개인정보/약관·계정/삭제/보안·복구/지원 체계와 사용자 승인을 확인해야 한다. 새 비용·사진 외부 전송·공개 범위 확장은 이번 정리의 승인이 아니다.

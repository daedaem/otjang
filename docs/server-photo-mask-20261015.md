# 서버에서 하는 배경 지우기와 영역 정리 (2026-10-15, Claude)

## 왜 했나

사용자 요청은 "퀄리티 좋게 하되 빠르게"였다. Claude는 이렇게 제안했다(사용자 확인은 아직 없음).
- 기기에서 바로 하는 처리는 그대로 둔다.
- 로그인한 사용자는 운영자 서버의 더 큰 모델로 처리한다.

## 시험

**시험 사진** (개인 사진 없음)
- 이전 시험([배경 지우기](background-removal-20261015.md))의 옷 5벌(셔츠·치노·트러커·티셔츠·해링턴)을 다시 썼다.
- 집에서 찍을 법한 배경 4가지 위에 다시 합성했다. 모두 20장이다.
  - 흰 이불
  - 어두운 나무 바닥
  - 체크 담요
  - 잡동사니: 색이 다른 상자 14개
- 그림자도 넣었다.
- 셔츠 사진은 모델이 입은 상품 사진이라, 정답 영역이 사람 전체다.

**정확도**: 정답 영역과 겹치는 비율(IoU)

| 모델 | 크기 | 평균 | 가장 나쁨 | 0.9 미만 | 잡동사니 배경 평균 | 1장 시간 (2.1GHz vCPU) |
|---|---|---|---|---|---|---|
| U-2-Netp (기기에서 쓰는 모델) | 4.6MB | 0.925 | 0.655 | 3장 | 0.788 | 스레드 1개 0.44초 |
| **U-2-Net** | 176MB | 0.961 | 0.851 | 2장 | 0.919 | 스레드 1개 0.99초, 4개 0.35초 |
| IS-Net general-use | 179MB | 0.894 | 0.510 | 6장 | 0.679 | 스레드 1개 2.7초 |
| U-2-Netp + 영역 정리 | | 0.949 | 0.741 | 2장 | 0.884 | |
| **U-2-Net + 영역 정리** | | **0.970** | **0.938** | **0장** | **0.956** | 4개 0.33초(중앙값) |

**영역 정리** (`app/src/mask-cleanup.js`)
- 모델이 옷 말고 다른 물건(상자, 가방)까지 옷으로 잡는 경우가 있다.
- 그래서 가장 큰 영역과, 그 30% 이상인 영역만 남긴다.
- 남긴 영역 둘레 3픽셀은 남겨서, 부드러운 가장자리를 자르지 않는다.
- 흰 이불, 나무 바닥, 체크 담요 결과는 바뀌지 않았다.

## 결정

1. **영역 정리를 기기와 서버 모두에 넣는다.** 비용이 거의 없고(320×320 한 번 훑기), 가장 나쁜 사진의 결과를 크게 올린다.
2. **로그인한 사용자는 서버의 U-2-Net + 영역 정리를 쓴다.**
   - 가장 나쁜 사진이 0.741에서 0.938로 오른다.
   - 기기 도구 7MB를 내려받을 필요가 없다.
3. **IS-Net은 쓰지 않는다.** 잡동사니를 옷으로 잡아 오히려 나빠졌다.
4. **BiRefNet 등 더 큰 모델은 시험하지 않았다.** CPU에서 1장에 여러 초가 걸릴 것으로 추정해서 빠른 처리 목표와 맞지 않는다고 봤다. 측정은 하지 않았다.

## 동작

**처음 한 번은 묻는다.**
- 로그인한 사용자가 "배경 지우기"를 처음 누르면, 사진을 보내기 전에 "서버에서 지우기 / 이 기기에서 지우기(도구 약 7MB) / 취소"를 고르게 한다.
- 고르기 전에는 아무것도 보내지 않는다.
- "서버에서 지우기"를 고르면 이 기기·이 계정에서 기억한다. 프로필 계정 칸의 "끄기"로 되돌리면 다음에 다시 묻는다.
- "이 기기에서 지우기"를 고르면 그 세션은 서버에 묻지 않고, 기기 도구의 내려받기 동의로 넘어간다.
- 가입 안내에 이 목적을 더했으므로 안내 버전을 `2026-10-15.2`로 올렸다. 이전 버전 화면에서는 가입하지 않는다.

**보내고 받는 것**
- 앱이 서버로 보내는 것은 지금 사진(잘랐으면 자른 사진)을 320×320으로 줄인 RGB 픽셀(307,200바이트)뿐이다.
- 서버는 320×320 영역 정보(102,400바이트)를 돌려준다.
- 흰 배경 사진은 앱이 기존 코드(`photoAssetWithoutBackground`)로 만든다. 그래서 사진 이름(SHA-256), 저장, 되돌리기는 기기 처리와 같다.
- 서버는 받은 픽셀과 결과를 저장하거나 로그에 남기지 않는다. 시험으로 확인했다.
- 서버는 한 번에 한 장씩 처리하고, 기다리는 요청은 4개까지 받는다. 더 들어오면 503으로 답한다.
- 사용자당 10분에 60회까지 받는다.

**서버가 처리하지 못하면** (꺼짐, 바쁨, 기능 꺼짐, 로그인 만료)
- 사진은 그대로 두고 "다시 누르면 이 기기에서 지워요"라고 알린다.
- 그 세션 동안은 기기 도구를 쓴다. 기기 도구는 처음 한 번 내려받기 동의를 받는다.

**로그인하지 않은 사용자**
- 서버로 아무것도 보내지 않는다.

**가입 안내와 처리방침 초안**
- 목적에 "로그인한 동안 누른 사진의 배경 지우기(줄인 사진을 서버에서 처리하고 저장하지 않아요)"를 더했다.

**모델과 실행 도구는 선택 설치다.**
- 둘이 없거나 모델 해시가 다르면, 서버는 기능을 끈 채 정상 동작한다.
- 앱은 `/v1/health`의 `features.photoMask`를 보고 경로를 고른다.

## 검증

**자동 시험**
- 서버 19개 통과. 6개를 새로 더했다.
  - 기능이 꺼지는 조건 3가지
  - rembg와 같은 전처리, 영역 정리
  - 한 장씩 처리와 바쁨 응답
  - 모델 해시가 다르면 저장하지 않음
  - API: 로그인 필수, 정확한 크기, 저장하지 않음, 503, 404
  - 실제 U-2-Net이 밝은 바닥 위의 어두운 옷 모양을 찾음(IoU 0.85 초과)
- 앱 405개 통과. 5개를 새로 더했다.
  - 영역 정리 단위 시험 2개
  - 앱 흐름 시험 3개: 로그인하면 내려받기 동의 없이 서버로 처리하고 줄인 픽셀만 보냄, 서버 실패 뒤 사진을 유지하고 다음에는 기기로 처리함, 로그인하지 않으면 서버에 묻지 않고 다른 물건 영역을 떼어 냄
- 새 시험은 모두 고치기 전 동작에서 실패하도록 만들었다.

**실제 Chromium** (390px, 같은 PC의 서버, 실제 U-2-Net)
1. 가입
2. 재킷 사진 넣기
3. "배경 지우기" 누르기

- "서버에서 지우기"를 고른 뒤 결과까지 **895ms**였다(아래 재확인 참고). 기기 처리는 첫 실행 2.8초, 두 번째 1.9초였다.
- 보낸 것은 307,200바이트 한 번이다.
- 결과의 모서리는 흰색(255,255,255), 가운데는 재킷 색이다.
- 페이지 오류 0건, 서버 로그에 이메일 없음

## 확인하지 않은 것

- **실제 사용자 사진**: 시험 사진은 깨끗한 상품 사진을 합성한 것이다.
  - 구겨진 옷, 옷걸이, 어두운 조명, 흰 옷을 흰 이불에 둔 경우는 시험하지 않았다.
  - 정답 영역도 합성에서 나온 것이다.
- **휴대폰과 터널을 거친 시간**: 보내는 양은 307KB와 102KB다. 휴대폰 회선과 터널 지연은 재지 않았다.
- **사용자 PC의 CPU에서 걸리는 시간**: 이 개발 서버의 2.1GHz vCPU 4개 기준이다.
- **여러 사람이 동시에 쓸 때**: 한 장씩 처리하므로 기다리는 시간이 늘어난다. 기다리는 요청이 4개를 넘으면 기기 처리로 넘어간다.

## 검토로 찾고 고친 예외

- 미전송 반품 기록을 구매·보류·null로 정정할 때 보호 대상에서 빠지던 문제.
- 확인한 서버 스냅샷에 없던 새 로컬 기록 때문에 보내기/받기가 모두 막히던 문제.
- 같은 revision의 다른 저장 내용과 계정 전환 중 저장 큐가 섞일 위험.
- IDB의 최신 값을 읽지 못한 상태에서 오래된 LS 복사본을 성공 처리하던 문제. 읽기를 검증한 뒤 쓰기만 실패한 경우에만 대체 저장한다.
- 초기화에서 충돌 검사 전에 저장소를 지우던 경로. 초기 상태를 CAS 저장하고 실패 시 원상태를 유지한다.
- 유효한 원격 null 정정은 명시적으로 선택할 수 있게 하고 키 누락과 구분했다.
- 모바일 빌드의 플랫폼 `copyfile` 시간 초과. 원본 바이트를 읽어 산출물에 쓰며 manifest가 참조하는 두 아이콘이 없으면 빌드를 실패시킨다.

첫 계약·저장 보호 검증 당시 독립 소스 검토와 집중 Node 회귀에서 추가 확정 P0/P1을 찾지 못했다. 이후 확인한 재로그인 예외는 다음 절의 범위다. 모든 검사의 입력은 합성이며 개인 옷장·사진 원문은 커밋하지 않는다.

## 추가 검증 · 재로그인 뒤 알려진 revision 복구

`d81e2a1` 이후 같은 origin·인증 owner의 유효한 ack는 남아 있지만 `syncStamp`가 없거나 무효인 경우를 확인했다. 이전 보내기는 버전을 새로 조회해 서버 revision 8을 채택하므로, ack revision 7에서 시작한 기기가 다른 기기의 최신 정정을 덮어쓸 수 있었다. 수정은 유효한 ack의 알려진 revision을 조건부 쓰기 기준으로 복구한다. 합성 서버의 최신 revision이 8이면 `If-Match: "7"`로 409를 받고, 서버 쓰기 0건·로컬 결과 보존·자동 probe/재전송 없음으로 끝난다.

정상 `syncStamp`가 있는 재로그인은 기존에도 이전 revision으로 보호됐다. 따라서 모든 재로그인에서 덮어쓰기가 발생한다는 주장은 확인된 범위가 아니다. 다른 계정·출처 또는 손상 ack를 쓰기 버전으로 사용하지 않으며, 신뢰할 revision이 없는 명시적 첫 보내기 동작은 유지한다.

## 추가 검증 · 기록 용량과 실제 상품 비교 연결 (`d7dfa70`)

## 남은 검증과 기능

현재 실행 환경에서 브라우저 검사 스크립트는 구문만 확인했다. 실제 브라우저의 확인 화면·다중 탭·두 기기, 실제 휴대폰/Safari, production TLS/CORS/proxy, 배포 확인, DB+사진 복구 훈련과 결제 시점의 실제 상품 가격·옵션별 재고는 확인하지 않았다. 수동 상품 작성 담당자가 읽은 당시 공식 표시 가격과 구분한다.
용량·상품 연결 코드의 게시 뒤 사용자 우선순위에 따라 핵심 등록·실제 상품 추천을 구현·검증했다. 이어서 일반 미전송 옷·판정·상품의 전체 pull 손실, 명시적 삭제 전파/tombstone, 일반 outbox/v2 sync, PurchaseCase 이전, 복원 epoch와 CI를 해결해야 한다. 현재 FASHN v1.5 착용 결과는 품질 불합격으로 채택 보류했으며 다른 방식의 품질 검증도 남아 있다. 현재 결과로 플랫폼 출시 완료나 사업성 점수를 확정하지 않는다.
받기 저장 실패 보호는 동결 소스의 회귀와 독립 제보 해결, 코드 게시를 확인했다. 정상 받기에서 새/수정 옷·판정·상품이 사라지는 여섯 유형의 손실은 단계 A의 전체 기록 baseline·3방향 병합 대상이며 아직 미해결이다. 단계 A 순수 모듈 초안은 별도 실험이며 앱의 실제 송수신에 통합하지 않았고 이번 게시에서 제외한다. 단계 B의 영구 삭제 ID 보호·조회·복원 generation도 후속 설계 상태다. 앞선 별도 입력 UX 시안과 이번 앱 통합 흐름을 구분한다. 순수 `record-sync` 실험 43개는 앱 미통합·미게시이며 해당 353개와 후속 게시 대상 검사에 포함하지 않는다.

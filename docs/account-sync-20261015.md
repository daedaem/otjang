# 계정과 옷장 동기화 (2026-10-15, Claude)

## 사용자 결정

2026-10-15 대화에서 사용자가 정한 것:

- **서버**: 직접 운영한다. 외부 BaaS(Supabase, Firebase)는 쓰지 않는다.
- **로그인**: 이메일만으로 시작한다. 단, 나중에 다른 로그인 방식을 붙일 수 있게 만든다.
  - 사용자는 "일단 테스트니까 이메일만" 또는 "만들어 놓고 이메일만 되도록"을 물었다.
  - Claude가 뒤쪽을 추천했고, 그렇게 구현했다.
- **가입 시점**: 앱을 써 본 뒤, 저장할 때 가입한다.
- **속도**: 업로드와 처리 때문에 사용자가 기다리면 안 된다.

## 무엇을 만들었나

**서버** (`server/`, [실행 안내](../server/README.md))
- Node.js 기본 기능(`node:http`, `node:sqlite`, `node:crypto`)만 쓴다. npm 의존성은 없다.
- 계정, 로그인, 옷장, 사진을 SQLite 파일 하나에 저장한다.

**앱**
- `app/src/account.js`와 `main.js`의 "계정과 동기화" 부분이다.
- 페이지에 서버 주소 표시(`<meta name="eoul-api">`)가 있을 때만 계정 기능이 보인다.
- 표시가 없으면 앱은 지금처럼 기기 안에서만 동작하고, 서버로 아무것도 보내지 않는다.

## 기다리지 않게 하는 방법

실서비스들이 흔히 쓰는 방식과 같다. 화면은 기기 저장으로 끝내고, 서버 일은 뒤에서 한다.

1. **옷 저장은 언제나 이 기기 IndexedDB에 먼저 한다.**
   - 저장이 끝나면 화면이 바로 바뀐다.
   - 실제 Chromium에서 사진 1장짜리 옷 저장은 111ms였다.
2. **로그인한 기기는 저장이 끝난 옷장을 뒤에서 서버로 옮긴다.**
   - 서버에 없는 사진만, 한 번에 두 장씩 올린다.
   - 사진 이름이 내용의 SHA-256이라서, 같은 사진은 다시 올리지 않는다.
3. **서버가 꺼져 있거나 연결이 끊겨도 저장은 계속된다.**
   - 프로필에 이유를 보여 준다.
   - 5초에서 시작해 최대 5분 간격으로 다시 시도한다.
   - 화면으로 돌아오거나(`visibilitychange`) 연결이 돌아올 때(`online`)도 다시 시도한다.

**측정** (2026-10-15)
- 환경: 이 개발 서버의 Chromium, 같은 기기의 서버, 2.1GHz vCPU, 사진 1장(95KB)

| 동작 | 걸린 시간 |
|---|---|
| 가입 버튼부터 시트가 닫힐 때까지 (scrypt N=2^17 포함) | 830ms |
| 가입 버튼부터 옷장과 사진이 서버에 저장될 때까지 | 849ms |
| 두 번째 기기에서 로그인 버튼부터 옷장과 사진을 받을 때까지 | 540ms |

**측정하지 못한 것**
- 실제 휴대폰
- 터널을 거친 인터넷 경로
- 사진 수십 장인 옷장

## 동기화 규칙

옷장 전체를 한 덩어리로 맞춘다. 버전 번호는 기기 저장소가 쓰는 revision 비교와 같은 방식이다. 이 기기는 마지막으로 맞춘 지점을 기억한다.
- 서버 버전
- 이 기기 저장소 구분값(epoch)
- 이 기기 버전

| 이 기기 | 계정(서버) | 하는 일 |
|---|---|---|
| 그대로 | 그대로 | 없음 |
| 바뀜 | 그대로 | 이 기기 옷장을 올림 |
| 그대로 | 앞으로 바뀜(다른 기기) | 계정 옷장을 받음 |
| 바뀜 | 바뀜 | **묻는다** |
| 그대로 | 뒤로 감(서버를 백업으로 복구) | **묻는다** |
| 저장소가 새로 생김(삭제·자동 정리·복구), 비어 있음 | 내용 있음 | 계정 옷장을 받음 |
| 저장소가 새로 생김, 내용 있음 | 내용 있음 | **묻는다** |
| 아무 경우 | 비어 있음 | 이 기기 옷장을 올림 |

**자동으로 합치지 않는다.**
- 옷, 구매 기록, 취향을 항목별로 합치면 지운 옷이 되살아나거나, 같은 옷이 두 벌이 될 수 있다.
- 그래서 시험 단계에서는 사용자가 어느 쪽을 쓸지 고른다.
- 고르기 화면에는 양쪽의 옷 수, 사진 수, 구매 기록 수, 마지막 저장 시각을 보여 준다.
- "이 기기 옷장을 계정에 저장"은 두 번 눌러야 한다.
- 고르는 동안 이 기기 저장은 계속되고, 서버에는 올리지 않는다.

**두 쪽 내용이 같으면 묻지 않는다.**
- 로그아웃 뒤 다시 로그인한 경우나, 같은 백업으로 복원한 경우다.
- 이 기기의 이전 버전 가져오기 표시(`legacyFingerprint` 등)는 비교에서 뺀다.

**이 기기 전용 값은 받지 않는다.**
- 계정 옷장을 받을 때 이전 버전 가져오기 표시 3개는 이 기기 값을 유지한다.
- 그래야 다른 기기에서 "이전 버전에서 옷장이 바뀌었어요" 안내가 잘못 뜨지 않는다.

**막은 위험: 비어 버린 브라우저가 계정 옷장을 덮어쓰는 일**
- 예를 들어 Safari가 7일 규칙으로 저장 공간을 지운 뒤 앱이 빈 옷장으로 시작하는 경우다.
- 이때 저장소 구분값이 바뀌므로, 앱은 이것을 "수정"이 아니라 "새 저장소"로 본다.
- 그래서 계정 옷장을 받아 오고, 덮어쓰지 않는다. 시험으로 확인했다.

## 로그인과 보안

**계정 정보 저장**
- 비밀번호
  - scrypt(N=2^17, r=8, p=1)와 개별 salt로 해시한다.
  - 강도는 해시마다 함께 저장하므로, 나중에 올릴 수 있다.
  - 이 서버에서 해시 1회에 약 0.37초 걸렸다. OWASP Password Storage Cheat Sheet의 scrypt 최소 권고값이다.
- 로그인 토큰
  - 32바이트 난수다. 서버에는 SHA-256만 저장하므로, DB가 유출돼도 바로 쓸 수 없다.
  - 60일 동안 쓰지 않으면 만료된다.
  - 앱의 `Authorization: Bearer` 헤더로 보낸다.

**쿠키 대신 토큰을 쓴 이유**
- 앱과 서버가 다른 주소일 때, Safari는 다른 사이트 쿠키를 막는다.
- 헤더 방식은 다른 사이트가 사용자 대신 요청을 보내는 공격(CSRF)도 생기지 않는다.

**토큰 방식의 약점**
- 토큰은 `localStorage`에 있어서, 앱 페이지에 악성 스크립트가 들어오면 읽힐 수 있다.
- 지금 앱에 들어오는 외부 스크립트는 하나다. 사진 분석의 OCR 스크립트로, 고정 버전 해시를 확인한다.
- 이 조건이 바뀌면 다시 검토한다.

**공격 대비**
- 이메일이 없을 때도 비밀번호 확인과 비슷한 시간을 써서, 가입한 이메일인지 드러내지 않는다.
  - 다만 가입 화면은 "이미 가입한 이메일"을 알려 준다. 이메일 인증이 없는 지금은 이 편이 쓰기 편하다.
- 시도 횟수 제한(서버 메모리에 기록하므로, 서버를 다시 켜면 초기화된다)
  - 가입: 접속 주소당 시간당 10회
  - 로그인: 주소당 15분 30회, 이메일당 15분 10회
  - 계정 삭제: 계정당 15분 5회
- 초대 코드(`EOUL_INVITE_CODE`): 시험 기간에는 설정을 권한다.

**서버가 받는 자료 검사**
- 옷장: 앱과 같은 `validateWardrobe`로 검사한다. schema 5만 받는다.
- 사진
  - JPEG 머리 바이트, 800KB 이하, 이름과 내용 해시 일치를 확인한다.
  - 계정당 400장, 250MB까지 받는다.
- 다른 계정의 사진 이름을 알아도 그 사진을 볼 수 없고, 내 옷장에 연결할 수도 없다.

**사진 정리**
- 옷장에서 마지막 참조가 사라진 사진은 다음 저장 때 지운다.
- 올렸지만 하루 동안 옷장에 연결되지 않은 사진도 지운다.

**계정 삭제**
- 비밀번호로 다시 확인한다.
- 그 계정의 모든 행을 한 트랜잭션으로 지운다.
- `secure_delete`를 켜서 지운 자리를 덮어쓰고, WAL 파일을 정리한다.

## 가입 화면과 안내

**계정에 저장을 권하는 때**
- 개인 옷을 처음 저장한 뒤, 옷장에서 "계정에 저장해 둘까요?"를 한 번 권한다.
- "나중에"를 누르면 그 세션에서는 다시 권하지 않는다.
- 프로필과 보관 안내에서도 시작할 수 있다.

**필수 확인 세 가지**
- 만 14세 이상
- 개인정보 수집·이용
- 이용 조건
- 셋 중 하나라도 없으면 서버에 아무것도 보내지 않는다.
- 안내 버전(`AGREEMENT_VERSION`)은 앱과 서버가 같은 상수를 쓴다. 버전이 바뀌면 이전 화면에서는 가입하지 않는다.

**계정 기록 남기기**
- 로그아웃하거나 이 브라우저의 전체 삭제를 해도 계정 옷장은 남는다.
  - 전체 삭제는 로그아웃도 함께 한다. 그러지 않으면 다시 받아 오기 때문이다.
- 계정을 삭제해도 이 기기 옷장은 남는다.
- 처리방침은 [개인정보 처리방침 초안](privacy-policy-draft-20261015.md)에 있다. 법률 자문이 아니며, 운영자 확정이 필요하다.

## 검토한 다른 방법

| 방법 | 장점 | 택하지 않은 이유 |
|---|---|---|
| **직접 서버 + SQLite (선택)** | 비용 0원, 사진이 운영자 서버에만 있음, 백업은 파일 하나, Windows PC에서 설치 없이 동작 | 서버 한 대 규모에 맞다. 사용자가 늘면 DB 접근 부분을 Postgres로 옮겨야 한다. |
| 직접 서버 + Postgres | 여러 서버로 확장 가능 | 사용자 PC에 설치와 운영 부담이 생긴다. 지금 규모에는 과하다. |
| Supabase | 인증·저장·카카오 로그인 제공 | 사용자가 직접 서버를 골랐다. 무료 요금제는 1주일 동안 쓰지 않으면 멈춘다는 안내가 있다(3자 자료, 확인 필요). |
| Firebase | 인증과 모바일 연동이 쉬움 | 2026-02-03부터 Storage에 Blaze(사용량 과금) 요금제가 필요하다는 안내가 있다(3자 자료, 확인 필요). 비용 0원 원칙과 맞지 않는다. |
| 항목별 자동 병합(CRDT 등) | 충돌을 묻지 않음 | 지운 항목이 되살아나는 문제를 막으려면 설계가 크다. 시험 단계에서는 묻는 쪽이 안전하다. |

- 앱 398개 통과. 이전 387개에 계정 동기화 11개를 더했다.
- 서버 13개 통과.
- 시험한 것:
  - 서버 주소 표시가 없으면 아무 요청도 하지 않음
  - 필수 확인 전에는 가입 요청을 보내지 않음
  - 비밀번호를 기기에 저장하지 않음
  - 가입 뒤 사진까지 저장됨
  - 이후 수정이 자동으로 올라감
  - 두 번째 기기가 같은 옷장과 해시가 맞는 사진을 받음
  - 양쪽이 바뀌면 묻고, 양쪽 선택이 모두 동작함
  - 비어 버린 브라우저가 계정을 덮어쓰지 않음
  - 연결이 끊겨도 저장이 계속되고, 다시 이어짐
  - 로그인 만료 안내와 다시 로그인
  - 계정 삭제는 서버 자료만 지움
  - 로그아웃과 전체 삭제는 계정 자료를 지우지 않음

**실제 Chromium 두 기기** (390px, 같은 서버)
1. 옷 저장
2. 권유 표시
3. 동의 없이 가입 거부
4. 가입
5. 서버에 계정·옷장·사진이 1개씩 생김

- 페이지 오류 0건

- 서버 로그에 이메일·비밀번호 없음

## 확인하지 않은 것과 남은 일

**확인하지 않은 것**
- 실제 휴대폰, Cloudflare·Tailscale 터널, Windows PC에서 실행

**남은 일**
- 이메일 인증과 비밀번호 찾기: 메일 발송이 필요하다. 무료 SMTP를 쓸지는 결정이 필요하다.
- 카카오·구글 로그인: `identities` 표는 준비돼 있다. 각 개발자 콘솔에 앱을 등록해야 한다.
- 서버에서 하는 고품질 배경 지우기: 다음 작업으로, 뒤에서 처리한 뒤 사진을 바꿔 끼운다.
- 처리방침 확정과 앱 안 공개
- 서버 백업 자동화와 보관 기간 지키기
- 사용자가 늘면 Postgres로 옮기기와 서버 모니터링

# 사진에서 옷 종류·라벨 후보를 찾는 기능 — 2026-10-14

## 문제와 완료 범위

기존 사진 입력은 사진을 저장하고 보여 주는 기능이었다. 사진의 종류·색·브랜드·상품명을 분석하지 않았으므로 사용자가 사진을 넣어도 속성 입력이 그대로 남았다. 이 문제는 원스톱 목표의 첫 단계인 옷 등록을 막는다.

이번 변경은 브라우저에서 사진을 분석해 **종류 후보와 읽힌 라벨 글자**를 보여 주고, 사용자가 고른 정보만 등록 초안에 적용한다. 라벨 글자와 내장 카탈로그를 비교해 브랜드·상품 후보도 보여 준다. 색 자동 제안은 실제 오류를 확인해 이번 배포에서 제외했고 직접 선택을 유지한다. 사진 외형만 보고 정확한 브랜드·상품명을 확정하는 기능은 아니다. 이 문서는 구현 계약과 실제 측정의 범위를 기록하며, 실제 모바일 검증 완료나 서비스 출시를 선언하지 않는다.

## 데이터 흐름과 파일 책임

1. 사용자가 로컬 JPG·PNG·WebP를 고른다. 등록 전처리 `prepareGarmentPhoto()`는 25,000,000바이트 이하 파일을 긴 변 1,024px 이하 JPEG로 준비한다. 첫 사진 선택만으로 모델·OCR 다운로드를 시작하지 않는다. 초기 용량 안내를 읽고 `photo-start`의 “이 기기에서 사진 분석하기”를 누르면 분석을 시작한다. 이 선택은 현재 앱 실행의 메모리에만 남고 옷장·장기 저장소에는 쓰지 않는다. 같은 앱 실행에서 이후 사진을 고르면 자동 분석하며, 새로고침하거나 앱을 다시 열면 처음 시작을 다시 확인한다. 실제 UI는 준비된 `Blob`을 분석에 전달한다. 분석 어댑터 `analyze()`도 별도로 비어 있지 않은 25,000,000바이트 이하 이미지 `Blob`을 검사하며 URL·파일 경로·base64 문자열 입력을 거부한다.
2. 종류 분석은 별도 module Worker에서 CLIP을 실행한다. 라벨 분석은 Tesseract Worker에서 영어·한국어 OCR을 실행한다. 라벨 사진만 분석하는 모드는 CLIP을 시작하지 않는다.
3. CLIP은 앱이 제공한 영어 종류 목록과 사진을 비교하고 최대 3개 후보를 반환한다. `denim jacket`은 재킷, `hoodie`는 맨투맨 계열에 대응시킨다. 여러 옷을 입은 사람·옷이 없는 장면을 위한 비교 문구도 포함한다. 이 문구가 1위이면 종류·색을 적용하지 않고 옷 한 벌이 보이는 사진을 요청한다. 이것이 모든 부적합 사진을 탐지한다는 뜻은 아니다.
4. 실제 흰 셔츠를 차콜로 제안한 색 분석은 배포에서 제거했다. 기본 Worker는 `colors: []`를 반환한다. 어댑터의 색 결과 검증·주입 테스트가 남아 있더라도 고객에게 색을 분석하는 기능이 있다는 의미는 아니다. 색은 직접 고르며, 목록 밖 세부 종류·소재·핏을 만들어 채우지 않는다.
5. OCR 원문 최대 1,200자를 `suggestPhotoIdentity()`에 전달한다. 일반 옷 사진에서는 프린트·배경 글자도 읽힐 수 있으므로 원문만 먼저 보여 주고 브랜드·상품 후보를 숨긴다. 사용자가 `photo-text-match`의 “이 글자로 브랜드·상품 찾기”를 눌러 라벨 문구임을 확인하거나, 별도 라벨 사진을 선택해 라벨 모드로 분석한 경우에만 후보를 표시한다. 그 뒤에도 브랜드·상품 적용은 별도 사용자 선택이다. 분석 결과는 옷장 상태와 분리된 초안에 머문다.
6. 사용자가 종류·색·브랜드 또는 상품 후보를 명시적으로 고른 뒤 저장하면 기존 옷·사진의 원자 저장 경로를 사용한다. 분석 완료 자체는 저장이 아니며, 사용자가 입력한 이름·속성을 비동기 결과로 자동 덮어쓰지 않는다.

| 파일 | 책임 |
|---|---|
| `app/src/photo-recognition.js` | 종류 모델·OCR 다운로드, 로컬 Worker 실행, 결과 제한, 진행 상태·취소·시간 초과 |
| `app/src/photo-identity.js` | OCR 글자의 브랜드 별칭·상품 링크·상품명 대조, 충돌·중의성·근거 반환 |
| `app/src/main.js` | 사진 등록 초안, 후보 표시와 사용자 선택, 늦은 결과 차단, 저장·재시도 |
| `app/src/garment-photo.js` | 보관용 사진 변환. 현재 긴 변 1,024px 이하 JPEG로 준비 |
| `app/src/wardrobe-store.js` | 기존 IndexedDB 옷·사진 트랜잭션, 저장 충돌·용량 실패 보호 |

종류와 OCR 작업에는 각각 **준비 최대 10분, 준비 완료 뒤 추론 최대 90초**의 독립 제한이 있다. 모델 다운로드를 추론의 90초 안에 끝내야 하는 구조를 제거했다. 종류 작업은 `kind-analysis` 단계에서, OCR은 Worker 초기화 뒤 `recognize()` 직전에 추론 제한을 시작한다. 반복 진행 메시지는 제한을 연장하지 않는다. OCR 라이브러리 스크립트 자체의 다운로드 제한 30초 등 더 이른 초기화 실패는 별도로 반환할 수 있다. 한 작업의 실패·시간 초과가 다른 작업의 준비·추론을 중단하지 않으며, 두 작업이 끝나면 성공한 후보와 실패 안내를 함께 반환하거나 양쪽 실패를 알린다. 준비에 10분을 보장하거나 전체 고객 대기 시간이 90초라는 의미는 아니다.

분석이 완료된 같은 등록 초안에서는 재시도·사진 교체·라벨 분석에 이미 준비된 recognizer를 재사용한다. 진행 중 사진을 교체하거나 취소·닫기·저장을 실행하면 작업과 Worker를 종료하고, 이전 작업의 늦은 결과를 새 초안에 적용하지 않는다. Worker 초기화 중 취소된 OCR 작업은 핸들이 있으면 즉시 종료하고, 아직 없으면 핸들을 얻는 즉시 종료한다. 완료 Worker의 재사용은 같은 초안 범위이며, 모든 등록 시트 사이에 모델이 메모리에 계속 남아 있다는 보장은 아니다. 직접 입력하거나 다시 시도할 수 있다. 분석 결과를 wardrobe JSON에 새 형식으로 저장하지 않으므로 이번 기능 때문에 schema 5를 바꾸지 않는다.

## 브랜드·정확한 상품을 다루는 기준

- 브랜드는 OCR에 실제로 나온 글자와 카탈로그에 존재하는 브랜드·별칭으로만 제안한다. `POLO`, `NB`처럼 짧거나 여러 의미가 있는 별칭은 사용하지 않는다. `LEE` 등 짧고 흔한 명칭은 라벨 한 줄 전체가 맞는 경우에만 후보로 취급한다.
- 우먼 등 긴 브랜드명이 읽혔다면 그 이름 안에 있는 부모 브랜드까지 함께 확정하지 않는다. 여러 브랜드가 나오면 중의성을 표시한다. 미등록 브랜드의 `Brand:` 또는 `브랜드:` 글자는 원문으로 남기며 다른 유명 브랜드로 대체하지 않는다. 카탈로그에 없는 `BARACUTA`처럼 접두어 없이 읽힌 글자도, 라벨 문구 확인 뒤 읽힌 줄 선택에서 사용자가 브랜드 줄을 직접 고르면 이름만 저장할 수 있다. 이때 `productId`는 `null`이며 미등록 브랜드를 실제 상품과 연결한 것으로 세지 않는다.
- 상품 후보는 알려진 무신사 상품 링크, 브랜드와 상품명 글자, 또는 브랜드와 사용자가 확인한 종류를 근거로 찾는다. **상품 ID 연결은 `exact`인 `product-link` 또는 `brand-and-name` 결과에만 허용**한다. 브랜드와 종류만 맞는 `brand-and-kind`나 상품명의 일부 단어만 맞는 후보는 참고 상품으로 볼 수 있지만 동일 상품 확인·연결 버튼을 제공하지 않으며, 이벤트를 직접 호출해도 연결을 거부한다. 링크 또는 해당 브랜드에서 고유하게 맞는 전체 상품명 근거를 추가한 뒤 다시 대조한다.
- 내부 `exact`는 **카탈로그 링크·문자 증거가 정확히 일치한다는 의미**다. 사진 속 실제 옷의 진위·모델·색·옵션·구매 사실을 확인한 값이 아니다. 모든 결과는 `identityConfirmed: false`, `requiresConfirmation: true`에서 시작한다.
- 종류·성별·문자 근거가 있는 색이 충돌하거나 여러 상품이 맞으면 충돌을 보여 준다. 카탈로그 사진에서만 추정한 색으로 문자 후보를 단정적으로 제외하지 않는다. 내 옷 색은 모르지만 카탈로그에 문자 근거가 있는 색이 있으면 `photo-product-color`의 “이 색이 맞아요”를 먼저 누른 뒤 전체 상품 확인을 해야 그 색과 상품 ID를 함께 적용한다. 상품 페이지가 맞다는 이유만으로 색을 자동 채우지 않는다. 내 옷에서 이미 고른 색·직접 적은 이름·사진은 유지하며, 확인 전 종류·색·브랜드·상품 ID가 바뀌면 기존 확인을 그대로 적용하지 않는다.
- 목록 밖 상품 링크는 원주소 확인 경로로 안내한다. 사진에서 읽힌 가격이나 내장 카탈로그 가격을 현재 최저가로 표현하지 않는다. 라벨이 안 보이는 옷은 종류·색만으로 등록하고, 상품 링크나 라벨 사진을 나중에 추가할 수 있어야 한다.

## 모델·버전 선택과 비용

| 구성 | 고정 값·근거 |
|---|---|
| Transformers.js | `3.8.1`; CDN ESM `@huggingface/transformers@3.8.1/dist/transformers.min.js` |
| 종류 모델 | `Xenova/clip-vit-base-patch32` |
| 모델 revision | `d15189d7028b43f1d3e65039190477f6af591c2a` |
| 실행 | 브라우저 `device: 'wasm'`, `dtype: 'q8'`, WASM `numThreads: 1`; WebGPU 필수 아님 |
| 브라우저 OCR | `tesseract.js@6.0.1`, worker `6.0.1`, `tesseract.js-core@6.0.0`, 영어·한국어, `SPARSE_TEXT` |
| OCR 언어 경로 | `https://tessdata.projectnaptha.com/4.0.0` |

처음 분석 시작을 선택하면 인터넷에서 공개 라이브러리·모델·언어 데이터를 내려받는다. 측정한 CLIP 합산 ONNX 파일은 **153,695,702바이트**다. 여기에 토크나이저·설정·WASM 런타임·OCR 언어 파일이 추가된다. 이 숫자는 전체 다운로드 용량이나 메모리 사용량이 아니다. 전체 첫 다운로드·모바일 첫 실행 시간은 미측정이다. 캐시를 지원하지만 브라우저 용량 정책·비공개 모드·삭제에 따라 다음 실행에서도 다시 받을 수 있다. 앱 첫 화면이나 최초 사진 선택에서 모델을 먼저 받지 않는다. 분석 시작을 허용하는 앱 세션 상태는 모델 캐시가 있다는 증거도 아니다.

24,281,512바이트의 TinyCLIP q8도 실제 실행해 보았다. 공개 흰 옥스포드 셔츠를 코트로 분류했고 fp32 실행에서도 같은 오류가 나타나, 이번 구현에는 더 큰 CLIP을 선택했다. 용량이 작은 모델을 채택했다는 이유로 인식 품질을 통과 처리하지 않는다. CLIP에도 아래 오분류가 남아 있어 자동 확정 대신 후보 선택을 유지한다.

Transformers.js와 Tesseract.js 패키지는 Apache-2.0이다. 원 CLIP 저장소는 MIT 라이선스이며 Xenova 모델 카드는 OpenAI CLIP을 ONNX로 변환한 모델임을 명시한다. 확인한 패키지와 원 CLIP의 라이선스·번들 고지 원문은 [THIRD_PARTY_NOTICES.md](../app/THIRD_PARTY_NOTICES.md)에 보존한다. 모든 원격 의존성의 고지를 확보했다는 의미는 아니다. ONNX 변환 저장소의 출처, OCR core·언어 데이터의 고지와 CDN 공급망도 운영 의존성으로 관리한다. 라이선스 허용과 실제 의류 서비스 품질 검증은 별개다. [Transformers.js 고정 버전](https://github.com/huggingface/transformers.js/blob/3.8.1/package.json), [Tesseract.js 고정 버전](https://github.com/naptha/tesseract.js/blob/v6.0.1/package.json), [CLIP 라이선스](https://github.com/openai/CLIP/blob/main/LICENSE), [ONNX 모델 출처](https://huggingface.co/Xenova/clip-vit-base-patch32)

| `ms-3084874`, 타입 I 트러커 자켓 | 코트 | 코트 | denim jacket |
| `ms-7055559`, 덴톤 코튼 블렌드 데님 팬츠 | trousers | jeans | knitted sweater |

CLIP q8의 세 번째 결과는 원하는 상품 종류와 충돌하는 **반례**다. `m-denim.jpg`를 직접 확인하면 바지 외에 상의·신발이 함께 보이는 전신 상품 사진이다. 분석기는 고객이 어느 옷을 등록하려는지 알 수 없으므로 카탈로그의 바지 종류와 사진 전체의 1위 분류를 동일하게 취급하면 안 된다. 이 3개로 정확도·경쟁 우위·평상복 인식 품질을 계산하지 않는다. `clip-q8.json`은 Node CPU 실행이며 개별 측정값 82·106·153ms는 모델을 불러온 뒤의 해당 실행 값이다. 휴대폰 브라우저 WASM, 모델 다운로드, OCR 병행, 사진 디코딩을 포함한 고객 대기 시간으로 사용할 수 없다. 최종 앱의 종류 문구·별칭이 이 초기 비교 목록과 같다고 가정하지 않는다.

최종 종류 문구 목록을 사용한 추가 Node CPU 실행은 `worker-prompt-check.json`에 기록했다. 흰 옥스포드 셔츠는 셔츠, 트러커 재킷은 재킷이 1위였다. 전신 사진은 니트가 1위였고 `requiresCrop: false`였다. 즉, 여러 옷 비교 문구를 넣었더라도 자동으로 전신 사진을 걸러 준다고 주장할 수 없다. 같은 실행의 색 비교에서는 흰 셔츠에 차콜·그레이·라이트 블루가 앞섰고 화이트는 5위였다. 그 결과 색 추론 호출을 기본 Worker에서 제거하고 직접 선택을 유지하기로 했다. 이 추가 로그의 시간은 종류와 당시의 색 추론을 포함하므로 색이 제거된 최종 기능의 성능 값으로 쓰지 않는다.

OCR Node Worker는 `eng+kor`를 로드한 상태에서 영어 합성 라벨의 `MUSINSA STANDARD`, `BASE OXFORD SHIRT`, `WHITE / M / 100% COTTON` 글자를 읽었다. Node 검증 환경의 실제 설치 버전은 `tesseract.js@6.0.1`, `tesseract.js-core@6.1.2`이며 브라우저의 core `6.0.0` 고정과 다르다. 기록된 658ms는 그 한 실행이다. 실제 구겨진 라벨·작은 자수·흐림·한글 품명·카메라 입력이나 모바일 첫 실행을 검증한 결과가 아니다. `BASE OXFORD SHIRT`가 읽혔다는 사실만으로 내장 카탈로그의 한국어 상품명과 정확히 일치한 상품이 생기는 것도 아니다.

어댑터·텍스트 매칭·등록 흐름 회귀 검사는 취소, 늦은 응답, 입력 보존, 사진 교체, 사용자 확인, 원자 저장을 검증한다. 준비·추론 제한과 Worker 재사용 검사는 VM 타이머·프로토콜 및 기본 factory의 비동기 처리 검사이며, 실제 모바일 첫 다운로드를 측정한 검사가 아니다. 추론·디코딩 대역을 사용하는 검사는 실제 인식 품질이나 브라우저 Worker 호환성 증거와 구분한다. 이번 문서에 전체 테스트 수를 고정하지 않고 해당 변경의 최종 실행 로그·PR에 기록한다.

## 운영·장애 대응

- Worker, module Worker, `OffscreenCanvas`, `createImageBitmap`, WASM 또는 CDN 접근을 지원하지 않는 환경에서는 분석 실패 사유와 직접 등록 경로를 제공한다. 실제 Safari·Chrome 지원 결과는 별도로 확인해야 하며 코드의 지원 검사가 실기기 검증을 대체하지 않는다. 분석 실패 때문에 기존 옷장이나 사진을 삭제하지 않는다.
- 첫 실행이 오래 걸리면 진행 중임을 표시하고 취소·재시도를 제공한다. 시간 초과를 잘못된 종류로 대체하지 않는다. 전신·여러 옷·흐린 사진은 옷 한 벌을 가까이 찍거나 사용자가 잘라 다시 선택하게 한다. 현재 자동 의류 분할·배경 제거·촬영 품질 보장은 없다.
- 모델 교체 시 모델 ID·revision·dtype·문구 목록·배포 식별자를 함께 기록하고, 같은 고정 입력과 반례를 다시 실행한다. 기존 기록을 새 모델로 자동 다시 쓰지 않는다. 실패한 새 배포는 이전 앱 배포로 복구하며 schema 5 옷·사진은 유지한다.
- CDN·Hugging Face·OCR 언어 서버 장애는 분석 기능 장애다. 옷장 직접 등록·저장·복원은 계속 가능해야 한다. 유료 API 키·계정·추론 서버는 이번 구현에 추가하지 않는다.

## 로컬 개인정보 처리와 출시 전 과제

선택한 사진은 로컬 Worker로 전달한다. 애플리케이션 코드에는 사진을 추론 API·Claude·상품 검색 서버에 업로드하는 경로가 없다. 다만 모델을 받으려면 외부 서버와 통신하고, 그 서버는 일반 네트워크 요청 정보를 받을 수 있으므로 완전 오프라인 기능으로 안내하지 않는다. 외부 다운로드 스크립트가 실행되는 구조의 공급망 위험까지 없어지는 것은 아니다. 실제 브라우저 네트워크 탭으로 사진 본문이 전송되지 않는지 확인하고, 운영 배포에는 자산 자체 호스팅·CSP·SRI를 포함한 무결성·업데이트 절차를 검토한다.

개인 사진·OCR 원문·Worker 메시지는 분석 로그나 Git 저장소에 수집하지 않는다. 라벨 원문은 초안에서 확인 용도로 쓰고, 옷장에는 사용자가 선택해 저장한 속성과 기존 사진만 남긴다. 앱의 옷장 삭제가 외부 런타임·모델 캐시까지 삭제한다는 의미는 아니며, 캐시와 개인 옷 데이터의 삭제 범위를 구분한다.

출시 전에는 iOS Safari·Android Chrome·데스크톱에서 첫 실행과 재실행, 비공개 모드·낮은 메모리·느린 네트워크·중단·복원까지 확인해야 한다. 동의를 받은 실제 옷·라벨 데이터로 종류, 직접 선택한 색, 브랜드 문자, 정확한 상품 후보를 각각 평가한다. 흐림·그림자·여러 옷·전신·유사 브랜드·목록 밖 상품·읽히지 않는 라벨의 실패를 포함하고, 틀린 후보를 확인 없이 적용하는 비율과 고객의 수정 부담을 측정한다. 라벨 전처리의 긴 변 1,024px·JPEG 압축이 작은 글자 판독에 미치는 영향, 브라우저 모델·OCR 캐시의 실제 총 용량과 개인 사진 저장 quota의 영향도 측정해야 한다. 확정 품명에는 품번·상품 링크와 권리 있는 최신 카탈로그 검증이 필요하다. 클라우드 분석을 나중에 도입한다면 별도 사진 전송 동의·보관·삭제·비용 정책을 먼저 정의한다.

CSP·SRI와 전체 공급망 고지, 실기기 라벨 해상도, 캐시·저장 quota 산출은 이번 미리보기에서 검증하지 않은 운영 과제다. 코드·자동 검사·공개 미리보기 배포로 생산 서비스의 준비가 완료됐다고 표시하지 않는다.

공식 문서도 CLIP의 영어 입력, 세부 분류 한계와 작업별 평가 필요성을 명시한다. 원스톱 기능의 진입을 개선하는 이번 분석을 정확한 브랜드·상품 식별, 가상 착용 또는 실제 핏·사이즈 예측으로 확대해 표현하지 않는다. [Transformers.js 브라우저 실행](https://huggingface.co/docs/transformers.js/v3.8.1/en/index), [CLIP 모델 한계](https://huggingface.co/openai/clip-vit-base-patch32)

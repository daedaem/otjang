# 웨어넥스트 PRD v0.4 — 나에게 맞게 옷장을 채워 가는 개인화 서비스

- 작성일: 2026-10-11, 한국 시간
- 상태: **검토용 초안**. 사용자 결정은 아래에 명시하며, 세부 범위와 수용 기준은 제안이다.
- 제품 책임자: 프로젝트 소유자 / 기획·검토 지원: OpenAI Codex
- 목적: 사업 아이디어를 검증할 수 있는 개인 제품과, 설명·재현 가능한 백엔드·AI 포트폴리오를 함께 만든다.
- 변경 기록: [결정 기록](decisions/001-product-direction.md) / 검증 방법: [개인판 검증 계획](validation-plan.md)

## 1. 제품을 한 문장으로

**내 옷장, 원하는 스타일, 체형과 분위기, 예산을 바탕으로 다음에 보완할 아이템과 실제 상품을 찾고, 후기·코디·구매처까지 한 흐름에서 비교하도록 돕는다.**

사용자가 설명한 현재 여정은 ‘커뮤니티에서 추천받기 → 후기를 따로 검색하기 → 무신사 같은 판매처에서 다시 찾기 → 내 옷과 어울릴지 스스로 판단하기’다. 제품은 흩어진 이 과정을 개인의 맥락 안에서 이어 주려 한다. 단순히 상품을 한 화면에 모으는 것만으로 이 요구가 충족되지는 않는다.

핵심 흐름은 **나와 내 옷장 이해 → 원하는 스타일과의 차이 파악 → 보완 우선순위 → 실제 상품·후기 비교 → 내 옷과 코디·사이즈 확인 → 구매처 연결 → 실제 사용 기록**이다. 보유 옷만으로 목표를 충족할 때는 새 구매 없이 코디를 제안하는 것도 정상 결과다.

코디는 새 구매 없이 얻는 반복 사용 가치이고, 옷장 보완은 구매가 필요할 때의 가치다. 이후 공개를 선택하면 다른 사람의 사용 기록을 이 판단의 근거로 연결한다. 커뮤니티의 규모·성장·수익성은 아직 확인되지 않았다.

‘원스톱’의 첫 구현 제안은 발견·후기 확인·개인화 비교·구매처 선택까지 연결하고, 결제·배송·반품은 판매처에서 하는 것이다. 자체 결제·판매 중개를 시작하기로 결정한 것은 아니다.

사용자는 커뮤니티 형성이 사업 성장에 중요할 수 있다는 의견을 냈고 더 나은 대안을 허용했다. 이는 **검토할 사업 가설**이며, 커뮤니티 우선 출시나 성장 보장이 확정된 것은 아니다.

### 인계 요구로 이어받는 기준

이번 대화에서 각각 재확인한 사항과 구분한다. 변경이 필요하면 결정 기록을 추가한다.

- 운영비 기본 목표 0원. 월 2만원은 예외 사용의 최대 한도로 기록되어 있으며 기본 예산이나 자동 결제 허가가 아니다.
- 개인 사진은 로컬에 보관하고 공개 배포·외부 API 전송을 하지 않는다. 얼굴·전신 사진은 개인판 핵심 흐름의 필수 입력이 아니다.
- 실제로 확인하지 않은 상품·가격·재고·링크와 어울림 확률을 만들지 않는다.
- 시각적 품질을 중요하게 다룬다. 3D 연결이나 렌더 성공만으로 품질 합격이라 하지 않는다.
- 코디와 실제 판매 상품 추천은 이번 사용자 설명에 따라 개인판 핵심 요구로 구체화한다. 실사 착장은 장기 품질 요구로 유지하고, 실제 구현 범위와 분리해 소개한다.
- Blender는 기본 자산 제작에 쓰는 도구이며, 고객 사진마다 사용자의 PC에서 돌리는 서버로 삼지 않는다.
- PRD v0.1과 과거 자료는 보존한다. 과거 문서에 있는 결제 실험·외부 사진 전송·재촬영 우선 요구는 최신 인계 기준과 충돌하므로 현재 실행 근거로 쓰지 않는다.

과거 PRD의 경쟁사 기능·가격·이용자 수·API 상태는 이번 작업에서 재조사하지 않았다. 이 문서는 해당 수치를 시장 근거나 최신 사실로 재사용하지 않는다.

## 3. 첫 사용자, 문제, 대안

첫 사용자는 프로젝트 소유자 본인이다. 셔츠·니트·재킷·데님·치노 등을 초기 검증 재료로 삼되, 연령·성별·아이비 취향을 사업 타깃으로 확정하지 않는다.

| 사용 상황 | 문제 가설 | 사용자가 끝내고 싶은 일 | 현재 대안 |
| --- | --- | --- | --- |
| 원하는 스타일로 옷장을 보완함 | 무엇을 먼저 더해야 하고 어떤 실제 상품을 골라야 할지 어렵다 | 내 조건과 보유 옷에 맞는 보완 우선순위·상품 비교 | 커뮤니티 질문 → 후기 검색 → 판매처 재검색 |
| 외출 전에 옷을 고름 | 가진 옷은 있지만 조합이 잘 떠오르지 않는다 | 오늘의 용도와 계절에 맞는 조합을 고르기 | 실제 옷장 보기, 기억, 저장해 둔 코디 사진 |
| 새 옷을 살까 고민함 | 비슷한 옷이 있는지, 함께 입을 옷이 있는지 놓친다 | 중복·활용 근거와 모르는 점을 보고 결정하기 | 쇼핑몰 사진, 메모, 직접 비교 |
| 나에게 어울릴지 확인함 | 모델 착용 사진과 일반 후기가 내 체형·인상·선호 핏을 설명하지 못한다 | 스타일의 방향과 실제 사이즈 위험을 구분해 판단하기 | 거울, 착용 경험, 지인 조언, 실측 비교 |
| 옷을 오래 입음 | 좋았던 점과 안 입는 이유를 잊는다 | 다음 코디·구매에 쓸 기록을 남기기 | 기억, 사진첩, 메모 앱 |
| 다른 사람의 옷을 구경함 — 향후 | 예쁜 코디가 내 옷에 적용되는지 알기 어렵다 | 가진 옷으로 재현할 부분과 필요한 부분을 구분하기 | 패션 피드, 커뮤니티, 지인에게 질문 |

일반 챗봇·쇼핑 검색보다 나아야 할 지점은 보유 옷과 목표 스타일을 유지하고, 상품 추천마다 ‘나에게 왜 필요한가, 무엇과 입는가, 어떤 후기와 실측이 근거인가’를 연결하는 것이다. 사용자 본인이 이 불편을 겪었다는 사실과 타인에게도 시장이 있다는 가설은 구분한다. 경쟁 서비스 대비 우위는 아직 검증 전이다.

## 4. 제품 전략과 개인판 완료의 경계

### 권고안

1. **개인판 완성**: 옷장 보완·실제 상품/후기 비교·코디·구매 판단을 한 흐름으로 사용한다. 같은 개인 맥락과 옷장 데이터를 재사용한다.
2. **공개 여부 결정**: 본인이 실제로 사용한 뒤 기록·입력 부담·시각적 만족도를 근거로 결정한다.
3. **선택적 커뮤니티 실험**: 공개를 선택했을 때만 취향이 비슷한 소수의 옷장 방문과 비교를 검증한다.

‘충분히 완성’의 제안 기준은 §6의 필수 요구와 §10의 개인 사용 문턱을 모두 통과하는 것이다. **실제 상품 제안은 필수이고, 인터넷 전체를 자동 검색하는 구현은 필수가 아니다.** 먼저 소수의 확인된 상품과 후기 자료를 수동으로 준비해 경험을 검증하고, 반복 작업을 자동화한다. 사용자가 모든 후보·후기를 찾아 입력해야 한다면 원스톱 경험은 아직 미완성으로 기록한다.

실사 착장·공개 피드·무제한 상품 검색까지 개인판 완료 조건으로 두지는 않는 제안이다. 수동 운영으로 검증한 결과를 완전 자동 서비스라고 소개하지 않는다.

### 이번 개인판의 범위

| 필수(P0 제안) | 후속(P1 제안) | 공개 결정 이후 | 별도 품질 실험 |
| --- | --- | --- | --- |
| 개인 맥락·스타일 목표, 옷 기록, 보완 우선순위, 확인된 소수의 실제 상품·후기·구매처, 근거 있는 체형/핏 정보, 코디, 구매 판단, 저장·복원, 보기 좋은 화면 | 상품 수집·갱신 자동화, 반복 피드백 학습, 입력 보조, 후보·판매처 범위 확장 | 계정, 접근 권한, 선택적 옷장 공개, 초대, 비교·저장, 신고·삭제 운영 | Blender 유형 자산, 실사 착장, 사진 기반 자동 매칭 |

가입·결제·소셜 피드·실시간 채팅·가상 피팅을 필수 흐름의 앞단에 두지 않는 것이 제안이다. 기본 템플릿에 없는 옷을 ‘반드시 사야 하는 옷’으로 표현하지 않는다.

## 5. 핵심 사용 흐름

### A. 원하는 스타일로 옷장 채우기 — 주 흐름

1. 원하는 스타일과 피하고 싶은 스타일, 용도, 계절, 예산을 알려 준다. 스타일 이름을 몰라도 문장·선호/비선호 예시로 표현할 수 있다.
2. 관련된 보유 옷을 확인한다. 잘 맞는 옷의 실측, 선호 핏, 체형 관련 고민, 원하는 인상은 선택적으로 더한다. 없는 정보 때문에 전체 기능을 막지 않는다.
3. 보유 옷으로 목표를 얼마나 실현할 수 있는지와 먼저 보완할 아이템 종류·색·실루엣을 제안한다. ‘기본템이라서’만으로 구매를 권하지 않는다.
4. 제안한 종류에서 실제 상품을 최대 3개 비교한다. 원하는 스타일, 보유 옷 활용, 예산, 개인 특성과 연결된 추천 이유와 단점을 보여 준다.
5. 상품별 후기에서 내 고민과 관련된 근거를 읽고 원문을 확인한다. 정보가 부족하거나 서로 상반되는 경우도 표시한다.
6. 후보마다 내 옷과의 코디, 비슷한 보유 옷, 확인 가능한 실측 차이, 아직 모르는 핏/분위기 요소를 비교한다.
7. 구매처로 이동하거나 보류한다. 실제 구매 후 보유로 바꾸고 입어 본 결과를 남긴다.

초기 상품 탐색 범위는 첫 실제 고민에 맞춘 한 용도·계절·예산 구간으로 좁히는 제안이다. 특정 브랜드나 성별 범위를 임의로 확정하지 않는다. 조건에 맞는 실제 상품이 없으면 검색 범위와 부족한 정보를 알리고 조건 변경은 사용자가 선택한다.

### B. 가진 옷으로 코디 고르기 — 반복 사용 흐름

1. 옷을 등록하거나 기존 옷을 수정한다. 사진 없이도 기록할 수 있다.
2. 계절과 용도를 고른다. 세탁 중이거나 오늘 제외한 옷은 선택에서 뺀다.
3. 실제 보유 옷으로 만든 조합을 최대 3개 본다. 조합별 근거와 주의점을 읽는다.
4. 마음에 드는 조합을 저장하거나, 별로인 이유를 남기고 다른 조합을 본다.
5. 실제 입은 뒤 ‘입었다/저장만 했다’를 구분해 기록한다. 평가 입력은 건너뛸 수 있다.

### C. 이미 찾은 상품 가져오기 — 보조 진입점

1. 후보 한 벌을 수동 입력하거나 사진·링크를 보관한다. 링크만 넣었다고 상품 정보를 자동 확보한 것으로 처리하지 않는다.
2. 용도·예산·망설이는 이유는 선택 입력한다. 판정 전 마음은 건너뛸 수 있고 평가용 기록 여부를 분리한다.
3. 후보와 같은 종류의 보유 옷을 충분히 등록했는지 확인한다. 함께 입을 상의·하의도 선택한다.
4. 비슷한 보유 옷, 후보를 활용하는 조합, 주의점, 입력 부족을 한 화면에서 본다.
5. ‘산다/보류/사지 않는다/아직 모르겠다’와 이유를 남긴다. 구매 여부와 도움 여부는 별개다.
6. 구매 의향만으로 보유로 바꾸지 않는다. 실제 구매 후 사용자가 보유 전환을 실행한다.

직접 가져온 후보도 A와 같은 상품·후기·활용도 비교로 이어진다. 별개 도구로 끊기거나 개인 맥락을 매번 다시 입력하게 만들지 않는다.

첫 결과를 보기 위해 옷장 전체를 등록할 필요는 없다. 다만 일부만 등록했다면 ‘등록된 옷 기준’임을 보여 주며, 중복이 없다는 전체 옷장 결론을 내리지 않는다.

## 7. 판단과 데이터의 의미

### ‘나에게 맞는다’의 다섯 축

| 축 | 사용할 근거 | 결과 | 한계 |

초기에는 근거와 우선순위를 공개하는 규칙·수동 큐레이션을 기준선으로 둔다. 서로 다른 축을 근거 없는 ‘어울림 92%’로 합치지 않는다. 예산은 입력된 경우 상한 조건으로 다루고, 초과 대안은 별도 표시한다. 조건 변경 없이 상한을 몰래 넘기지 않는다.

### 상품·후기 정보 확보 — 제품의 핵심 의존성

- 첫 검증은 프로젝트 측이 소수의 실제 상품과 접근 가능한 후기 근거를 확인해 준비한다. 사용자가 평소 하던 검색을 모두 다시 해야 한다면 절감한 일이 없는 것이다.
- 공식 상품 설명, 판매처 정보, 후기 작성자의 경험, 제품의 해석을 구분한다. 원문 링크·확인일·모델/옵션·증거를 남기고 요약은 추적 가능하게 한다.
- 후기 수, 구매 인증 여부, 작성자 체형, 사용 기간을 확인하지 못했으면 추정하지 않는다. 서로 상반된 후기는 평균적인 결론으로 지우지 않는다.
- 접근 제한·이용 조건 때문에 읽을 수 없는 후기는 자료 부족으로 표시한다. 외부 데이터를 가져올 수 있는 경로와 갱신 비용은 구현 전 확인할 핵심 과제다.
- 초기 로컬 카탈로그는 해당 시점의 자료다. 최신 정보 조회가 안 되면 마지막 확인일을 보여 주고 판매처 재확인을 안내한다. 오프라인에서 실시간 가격·재고를 주장하지 않는다.
- 상품 조사·요약 준비 시간도 기록한다. 수동 시범 운영의 편의성이 자동 운영의 실현 가능성까지 입증하지는 않는다.

### 조합 수와 중복

- 상의/하의 후보: 후보와 짝지을 수 있는 반대 분류의 보유 옷 조합을 센다. 같은 상하의에 겉옷만 여러 개 바꾼 것을 기본 조합 수에 중복 가산하지 않는다.
- 아우터 후보: 등록된 상하의 쌍 가운데 그 아우터를 함께 입는 조건을 충족한 쌍을 센다. ‘기존 조합 수에서 늘어난 수’로 표현하지 않는다.
- 기본 조합 수는 규칙이 통과한 경우의 수다. 사용자 취향, 실제 착용 가능 횟수, 구매 가치와 동일하지 않다.
- 규칙상 주의점은 취향에 따라 받아들일 수 있다. 사용자는 추천을 거절하거나 자신만의 조합을 저장할 수 있다.
- 신발·소품은 초기에 기록만 지원한다는 제안이다. 미지원 조합을 0점으로 평가하지 않는다.
- 필수 속성이 모르면 관련 판단을 보류한다. 임의 기본값으로 단정하거나 미확인을 ‘모든 계절에 적합’으로 바꾸지 않는다.
- 같은 입력·같은 규칙 버전의 결과는 재현 가능해야 한다. 과거 판정에는 입력 요약과 규칙 버전을 남긴다. 전체 사용자 사진을 로그로 남길 필요는 없다.

현재 코드에는 색·밝기·격식·무늬에 관한 수작업 규칙이 있다. 이 숫자와 ‘주의점 없음’이 패션 전문성이나 실제 만족도를 보장하지 않는다. 규칙 조정은 반례와 실제 사용 기록을 근거로 한다.

## 8. 화면 품질과 3D의 위치

핵심 화면은 나의 스타일/조건, 내 옷장, 다음 한 벌 제안, 상품·후기 비교, 내 옷과 코디, 기록/백업이다. 탭 수를 그대로 여섯 개 만들라는 요구는 아니다. 같은 맥락을 유지하며 이동하는 흐름을 우선한다. 3D 구현 여부와 별개로 정보 우선순위·여백·사진 품질·선택 피드백이 갖춰져야 한다.

개발 전 시안에서 ‘원하는 스타일 → 보완 제안 → 실제 상품/후기 → 내 옷과 코디 → 구매처’의 주 흐름과 ‘보유 옷으로 코디’의 반복 흐름을 보여 준다. 가져온 후보는 주 흐름의 상품 비교로 합류한다. 실데이터와 예시를 구분하고, 제품명·가격·만족도 숫자를 화면을 채우기 위해 만들어 넣지 않는다.

**화면 수용 기준(제안)**

- 390×844와 1440×900에서 핵심 텍스트·버튼·옷이 겹치거나 잘리지 않는다. 스크롤을 금지하는 뜻은 아니다.
- 등록된 옷과 구매 후보를 즉시 구분하고, 결과가 어떤 옷을 근거로 나왔는지 확인할 수 있다.
- 빈 옷장, 입력 부족, 결과 0개, 불러오기 실패, 저장 실패 상태를 디자인한다.
- 비교·선택·수정·뒤로 가기를 찾을 수 있다. 사용자에게 ‘다시 쓰고 싶은가’와 불편한 구체적 요소를 묻는다.
- 브라우저가 3D를 지원하지 않아도 핵심 기록과 판단이 가능하다.

Blender 셔츠는 **유형 기반 자산 실험**이다. 실제 보유 제품 재현, 몸에 입힌 결과, 핏 예측과 구분한다. 웹/정지 렌더 품질 비교 후 사용자 선택으로 도입한다. 개인판 공개 결정 전에 3D를 반드시 채택해야 한다는 조건은 두지 않는 것이 제안이다.

## 9. 데이터·비용·운영 조건

- 개인 옷장·프로필·판정은 로컬 저장과 수동 입력을 기본으로 한다. 저장된 카탈로그는 로컬에서 비교할 수 있고, 상품·후기 최신 확인과 판매처 이동은 네트워크가 필요한 별도 동작이다. 핵심 흐름을 유료 API에 종속시키지 않는다.
- 개인 데이터는 공개 GitHub, 오류 로그, 스크린샷, 테스트 결과물에 포함하지 않는다. 공개 예시는 합성 데이터를 사용한다.
- 개인 백업과 공유용 내보내기를 구분한다. 공유 파일에서 무엇이 빠지는지 사용자에게 보여 준다.
- 사진·민감한 원문을 수집하는 분석 도구를 기본 설치하지 않는다. 초기 사용 검증은 로컬 기록과 수동 회고로 충분하다.
- 외부 이미지 URL을 자동으로 불러오거나 링크 내용을 몰래 수집하지 않는다. 링크 방문은 사용자 동작이며 외부 이동임을 알린다.
- 상품 이미지 사용 권한과 API 제공 여부는 도입 직전에 확인한다. 접근 가능하다는 것과 재배포 허용을 동일시하지 않는다.
- 유료 서비스는 자동 대체 경로가 아니다. 필요해지면 비용·데이터 전송·실패 처리에 관한 별도 결정이 있어야 한다.
- 다중 사용자 공개를 선택하면 인증·권한·삭제·신고·운영 비용을 새 요구사항으로 명세한다. 개인판의 저장 방식으로 공개 서비스를 충분히 보호한다고 주장하지 않는다.

## 10. ‘본인 전용으로 충분히 완성’의 검증 — 제안

기능 완료, 실제 사용 가치, 사업성을 나눈다. 아래 숫자는 **사용자와 조정할 임시 판단 기준**이며 관찰 결과나 업계 기준이 아니다.

| 문턱 | 관찰 | 제안 통과 기준 | 실패하면 |
| --- | --- | --- | --- |
| 기능 | §6의 수용 기준과 주 흐름·반복 흐름·후보 합류, 저장·복원·삭제 | 필수 항목 검증 완료, 데이터 손실·의도치 않은 전송·흐름 중단 결함 없음 | 관련 결함부터 수정 |
| 원스톱 효용 | 실제 옷장 보완 고민 3건, 직접 찾는 과정과 비교 | 2건 이상에서 보완할 역할·실제 후보·후기 근거·보유 옷 활용을 한 흐름에서 검토하고 유용한 이유를 설명 | 빠진 단계가 데이터 확보·개인화·화면 중 무엇인지 진단 |
| 코디 효용 | 실제 외출 기회 5회에서 결과 확인·선택·착용을 구분해 기록 | 3회 이상에서 한 조합 이상을 실제로 입을 만하다고 판단하고, 최소 1회 실제 착용 | 이유를 취향·입력·규칙·화면으로 나눠 개선 |
| 구매·개인화 효용 | 위 3건에서 선택 이유·본인 조건 반영·미확인 핏을 구분 | 2건 이상에서 일반 인기 추천과 다른 개인 근거를 설명하고, 구매 여부와 무관하게 판단에 도움 | 실제 효용이 없는 개인화 표현·근거 부족을 수정 |
| 정보 신뢰 | 위 후보의 상품·후기 주장과 원문 대조 | 검증 대상 주장에 근거가 있고, 오래됨·추정·자료 없음이 구분됨 | 잘못된 주장 수정, 해당 수집/요약 경로 재검증 |
| 입력·유지 부담 | 최초 입력과 후속 수정 시간을 직접 측정 | 본인이 계속 유지할 수 있다고 판단하고 반복 방해 요소를 해결 | 자동화 추가 전에 필수 입력을 줄임 |
| 시각 품질 | 시안과 실제 화면, 모바일/데스크톱 | 사용자 화면 수용, 겹침·왜곡·구분 실패 해결 | 디자인 재검토; 3D 실패를 다른 화면 전체의 중단 이유로 삼지 않음 |

실제 구매 후보나 외출 기회가 없으면 해당 관찰은 ‘대기’다. 검증을 위해 구매를 유도하거나 가짜 사례로 통과시키지 않는다. 개인판 사용은 그동안 계속할 수 있다.

직접 검색한 시간·찾아간 곳·중복 입력과 제품을 쓴 뒤에도 추가로 찾아야 했던 정보를 기록한다. 시간 단축 수치는 같은 범위로 측정한 뒤에만 보고한다. 운영자가 대신 조사한 시간도 함께 남긴다.

한 사람에게 쓸모 있다는 결과는 개인판 성공의 근거다. 시장 수요·타인의 반복 사용·지불 의사의 증거로 확대하지 않는다. 이 결과를 보고 **공개를 진행할지, 개인 도구로 유지할지** 결정한다.

## 11. 커뮤니티는 어떤 가설로 검증할 것인가

커뮤니티는 사용자에게 도움이 되는 상호작용이 반복될 때 가치가 생긴다. 방문자 수만 늘거나 지인이 한 번 옷장을 올리는 것으로 성공이라 판단하지 않는다.

| 가설 | 도움이 될 수 있는 이유 — 추론 | 반론/실패 가능성 | 공개를 선택한 뒤 볼 행동 |
| --- | --- | --- | --- |
| 실제 옷장 기록이 유용하다 | 구매 직후 평점보다 오래 입은 조합·사용 기록이 판단에 도움이 될 수 있음 | 꾸준히 기록할 동기가 없을 수 있음 | 기록 추가, 구체적 질문, 재방문 |
| 취향이 맞는 사람의 옷장을 보고 싶다 | 한 장의 코디보다 반복되는 선택을 이해할 수 있음 | 기존 패션 피드로 충분할 수 있음 | 동일 옷장 재방문, 저장, 관심 이유 |
| 내 옷장과 비교하면 행동으로 이어진다 | 보유 옷으로 재현할 부분을 바로 찾을 수 있음 | 입력 부담이 이득보다 클 수 있음 | 비교 후 내 조합 저장·착용, 후보 판단 |

**추천하는 첫 공개 경험**: 사용자가 고른 작은 옷 묶음/코디와 실제 사용 기록을 공유하고, 방문자가 자기 옷으로 적용할 부분을 찾아보는 ‘옷장 방문’. ‘무엇을 샀는가’에 더해 ‘어떤 조건에서 얼마나 입었는가’를 개인화 판단의 근거로 연결한다. 유용한 기록이 실제로 모일지는 미검증이다. 옷장 전체 공개·연락처 수집·광범위한 피드 운영부터 시작하지 않는 제안이다.

초기에는 구경할 콘텐츠도 기록하는 사람도 적다는 문제가 있다. 본인 기록과 참여 의사가 있는 사람의 동의한 자료로 시작할 수 있지만, 임의의 가짜 사용자·후기·활동량을 채워 넣지 않는다. 동의받지 않은 상품 사진이나 개인 사진을 공개 자료로 쓰지 않는다.

성장 가설의 고리는 **자발적 공유 → 방문 → 내 옷에 적용 → 실제 사용 → 후속 기록**이다. 이 고리가 측정되지 않으면 ‘커뮤니티 효과’라 부르지 않는다. 빈도·표본·기간·계속할 기준은 공개 결정 시 별도 실험 계획으로 정한다. 현재 모집 일정이나 성장 목표 숫자는 확정하지 않는다.

수익모델과 가격은 미정이다. 유료화나 실제 결제를 개인판 개발의 완료 조건으로 삼지 않는다. 제휴를 도입하더라도 수수료를 추천의 판단 근거로 사용하지 않는 것이 인계 원칙이다.

## 12. 포트폴리오로 남길 증거

| 제품 문제 | 남길 기술 증거 | 착수 시점 |
| --- | --- | --- |
| 추천이 왜 나왔는지 설명해야 함 | 규칙 명세, 반례, 결정적 결과, 회귀 검증 | 개인판 핵심 |
| 상품·후기가 변경되거나 서로 충돌함 | 출처·갱신·상품 식별 모델, 오래된 정보 처리, 근거 추적과 실패 시 동작 | 원스톱 흐름의 핵심 |
| AI 요약이 근거를 벗어날 수 있음 | 원문 대조 평가, 상반된 후기·미확인 값 처리, 규칙/수동 기준선과 비교 | 요약 자동화를 선택할 때 |
| 데이터가 쌓여도 믿고 수정·복원해야 함 | 보유 상태 전이, 스키마 버전, 입력 검증, 복원·손실 대응 | 개인판 핵심 |
| AI 입력 보조가 실제로 도움이 되는지 모름 | 수동 기준선, 평가 사례, 오류·수정률, 모델 버전, 실패 시 수동 경로 | 입력 보조를 선택할 때 |
| 서버에 남의 옷장이 있으면 접근을 제한해야 함 | 소유권·공개 범위·권한·삭제 테스트 | 서버 구현을 선택할 때 |
| 생성 작업이 오래 걸리거나 실패함 | 멱등성, 상태 전이, 재시작·타임아웃 처리와 측정 | 실제 비동기 작업이 생길 때 |

Java/Spring·PostgreSQL·React·AI 모델은 과거 설계 후보다. 구체적 버전과 도입 순서는 PRD 이후 ADR에서 정한다. 개인 사용 중에도 학습용 백엔드를 만들 수 있으나 그것을 공개 수요의 증거로 쓰거나 현재 로컬 기능의 필수 운영비로 만들지 않는다. 사업 검증이 실패해도 재현 가능한 기술적 결과는 남길 수 있다.

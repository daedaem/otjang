## 1. 제품을 한 문장으로

**내 옷장과 취향에 맞는 실제 상품을 찾고, 구매 전에 내 얼굴·체형에 입었을 모습을 현실에 가깝게 비교하며, 후기·코디·구매처까지 이어 준다.**

최신 사용자 결정은 **자신이 실제로 입을 모습의 충실한 미리보기**가 핵심이며 3D는 필수 방식이 아니라는 것이다. 2D 생성형 착장을 먼저 검증할 수 있다. 현재 Blender 공간·코디 설명에는 이 기능이 없으며, 물리적 핏·사이즈를 보장하는 기술과도 구분한다. [가상 착장 검토](virtual-fitting-feasibility.md)에 공식 후보·제약·실제 착용 비교 방법을 기록한다.

사용자가 설명한 현재 여정은 ‘커뮤니티에서 추천받기 → 후기를 따로 검색하기 → 무신사 같은 판매처에서 다시 찾기 → 내 옷과 어울릴지 스스로 판단하기’다. 제품은 흩어진 이 과정을 개인의 맥락 안에서 이어 주려 한다. 단순히 상품을 한 화면에 모으는 것만으로 이 요구가 충족되지는 않는다.

핵심 흐름은 **옷장·옷 사진으로 초기 옷장 만들기 → 나의 스타일과 조건 이해 → 보완 우선순위 → 실제 상품·후기 비교 → 내 얼굴·체형의 착장 미리보기와 보유 옷 코디·실측 비교 → 구매처 연결 → 실제 사용 기록**이다. 보유 옷만으로 목표를 충족할 때는 새 구매 없이 코디를 제안하는 것도 정상 결과다.

코디는 새 구매 없이 얻는 반복 사용 가치이고, 옷장 보완은 구매가 필요할 때의 가치다. 이후 공개를 선택하면 다른 사람의 사용 기록을 이 판단의 근거로 연결한다. 커뮤니티의 규모·성장·수익성은 아직 확인되지 않았다.

‘원스톱’의 첫 구현 제안은 발견·후기 확인·개인화 비교·구매처 선택까지 연결하고, 결제·배송·반품은 판매처에서 하는 것이다. 자체 결제·판매 중개를 시작하기로 결정한 것은 아니다.

### 인계 요구로 이어받는 기준

이번 대화에서 각각 재확인한 사항과 구분한다. 변경이 필요하면 결정 기록을 추가한다.

- 운영비 기본 목표 0원. 과거 자료의 월 2만원 예외 한도보다 현재 사용자 결정 D-13을 우선하며, 이번 개인판에는 반복 API 과금을 도입하지 않는다.
- 개인 사진은 로컬에 보관하고 공개 배포·외부 API 전송을 하지 않는다. 일반 옷장·코디는 얼굴·전신 사진 없이 사용하며, 향후 본인 착장 미리보기에는 사용자가 선택한 본인 사진이 필요하다. 외부 추론의 전송·보관 경로는 아직 정하지 않았다.
- 실제로 확인하지 않은 상품·가격·재고·링크와 어울림 확률을 만들지 않는다.
- 시각적 품질을 중요하게 다룬다. 3D 연결이나 렌더 성공만으로 품질 합격이라 하지 않는다.
- 코디·실제 상품 추천과 함께 D-16의 본인 착장 미리보기를 핵심 요구로 둔다. 기존 ‘실사 착장은 별도 장기 실험’ 제안은 최신 요구로 대체하며, 현재 구현 완료와 구분한다.
- Blender는 기본 자산 제작에 쓰는 도구이며, 고객 사진마다 사용자의 PC에서 돌리는 서버로 삼지 않는다.
- PRD v0.1과 과거 자료는 보존한다. 과거 문서에 있는 결제 실험·외부 사진 전송·재촬영 우선 요구는 최신 인계 기준과 충돌하므로 현재 실행 근거로 쓰지 않는다.

과거 PRD의 경쟁사 기능·가격·이용자 수·API 상태는 이번 작업에서 재조사하지 않았다. 이 문서는 해당 수치를 시장 근거나 최신 사실로 재사용하지 않는다.

## 3. 첫 사용자, 문제, 대안

첫 사용자는 프로젝트 소유자 본인이다. 셔츠·니트·재킷·데님·치노 등을 초기 검증 재료로 삼되, 연령·성별·아이비 취향을 사업 타깃으로 확정하지 않는다.

**한 사례를 고르는 것과 한 장르 전용 제품으로 만드는 것은 다르다.** 제품 구조는 복수의 취향·상황을 지원하는 방향을 제안한다. 같은 사람이 공통 옷장을 사용하면서도 출근·주말 등에 다른 목표 스타일과 예산을 적용할 수 있어야 한다. 스타일을 사용자당 하나의 고정 분류로 저장하거나, 장르 하나의 규칙을 모든 판단에 적용하지 않는다. 실제 사례 선택은 추천 검증 때 구체화하며 현재 PRD 보완의 선행 조건으로 삼지 않는다.

| 사용 상황 | 문제 가설 | 사용자가 끝내고 싶은 일 | 현재 대안 |
| --- | --- | --- | --- |
| 처음 내 옷장을 만듦 | 가진 옷을 하나씩 입력하는 수고가 추천을 보기 전에 생긴다 | 사진에서 생성된 옷 목록을 확인하고 바로 활용하기 | 사진첩 정리, 수동 목록 입력 |
| 원하는 스타일로 옷장을 보완함 | 무엇을 먼저 더해야 하고 어떤 실제 상품을 골라야 할지 어렵다 | 내 조건과 보유 옷에 맞는 보완 우선순위·상품 비교 | 커뮤니티 질문 → 후기 검색 → 판매처 재검색 |
| 외출 전에 옷을 고름 | 가진 옷은 있지만 조합이 잘 떠오르지 않는다 | 오늘의 용도와 계절에 맞는 조합을 고르기 | 실제 옷장 보기, 기억, 저장해 둔 코디 사진 |
| 새 옷을 살까 고민함 | 비슷한 옷이 있는지, 함께 입을 옷이 있는지 놓친다 | 중복·활용 근거와 모르는 점을 보고 결정하기 | 쇼핑몰 사진, 메모, 직접 비교 |
| 나에게 어울릴지 확인함 | 모델 착용 사진과 일반 후기로는 내 얼굴·체형에 입었을 모습을 알기 어렵다 | 본인 착장 미리보기로 인상을 비교하고, 실제 사이즈 위험은 별도 실측·착용 근거로 판단하기 | 직접 착용, 기존 가상 착장 도구, 실측 비교 |
| 옷을 오래 입음 | 좋았던 점과 안 입는 이유를 잊는다 | 다음 코디·구매에 쓸 기록을 남기기 | 기억, 사진첩, 메모 앱 |
| 다른 사람의 옷을 구경함 — 향후 | 예쁜 코디가 내 옷에 적용되는지 알기 어렵다 | 가진 옷으로 재현할 부분과 필요한 부분을 구분하기 | 패션 피드, 커뮤니티, 지인에게 질문 |

일반 챗봇·쇼핑 검색보다 나아야 할 지점은 보유 옷과 목표 스타일을 유지하고, 상품 추천마다 ‘나에게 왜 필요한가, 무엇과 입는가, 어떤 후기와 실측이 근거인가’를 연결하는 것이다. 사용자 본인이 이 불편을 겪었다는 사실과 타인에게도 시장이 있다는 가설은 구분한다. 경쟁 서비스 대비 우위는 아직 검증 전이다.

## 4. 제품 전략과 개인판 완료의 경계

### 권고안

1. **개인판 완성**: 사진으로 초기 옷장을 만들고, 실제 상품·후기·본인 착장 미리보기·보유 옷 코디·구매 판단을 같은 개인 맥락으로 연결한다. 미리보기는 실제 보유 옷의 착용 결과와 먼저 비교한다.
2. **공개 여부 결정**: 본인이 실제로 사용한 뒤 기록·입력 부담·시각적 만족도를 근거로 결정한다.
3. **선택적 커뮤니티 실험**: 공개를 선택했을 때만 취향이 비슷한 소수의 옷장 방문과 비교를 검증한다.

‘충분히 완성’의 제안 기준은 §6의 필수 요구와 §10의 개인 사용 문턱을 모두 통과하는 것이다. **실제 상품 제안은 필수이고, 인터넷 전체를 자동 검색하는 구현은 필수가 아니다.** 먼저 소수의 확인된 상품과 후기 자료를 수동으로 준비해 경험을 검증하고, 반복 작업을 자동화한다. 사용자가 모든 후보·후기를 찾아 입력해야 한다면 원스톱 경험은 아직 미완성으로 기록한다.

본인 착장 미리보기는 최신 사용자 요구에 따라 핵심 완료 조건으로 검토한다. 공개 피드·무제한 검색·물리적 사이즈 보장까지 한 번에 요구하지 않는다. 수동 운영이나 제한된 착장 실험을 완전 자동·모든 옷 지원으로 소개하지 않는다.

| 사진 기반 초기 옷장 생성·확인, 개인 맥락·옷 기록, 보완 우선순위, 확인된 실제 상품·후기·구매처, 본인 착장 미리보기와 실제 착용 비교, 코디·구매 판단·저장·복원 | 상품 수집·갱신 자동화, 반복 피드백, 후보·표현 범위 확장, 선택적 3D 옷장 | 계정·접근 권한·선택적 공개·초대·신고·삭제 운영 | 물리적 핏·사이즈 예측, 사진만으로 정확한 판매 상품 식별 |

가입·결제·소셜 피드·실시간 채팅을 필수 흐름의 앞단에 두지 않는 것이 제안이다. 본인 사진 입력은 착장 미리보기를 이용할 때 요청한다. 기본 템플릿에 없는 옷을 ‘반드시 사야 하는 옷’으로 표현하지 않는다.

### 첫 검증과 개인판 전체 완성을 구분한다

위 P0는 개인판 전체의 목표다. 한 번에 모두 구현하는 작업 목록으로 쓰지 않는다. 다음 단계 구분은 전체 요구를 유지하면서 가장 큰 불확실성을 먼저 확인하기 위한 제안이다.

| 단계 | 이번 단계에서 끝낼 것 | 완료로 해석하지 않을 것 |
| --- | --- | --- |
| V0: 실제와 비교하는 착장 검증 | 이미 가진 옷의 10–20착장으로 본인 사진·상품 사진 입력과 실제 착용 정답을 분리해 비교. 얼굴·체형·제품 디테일·길이 왜곡과 오판 위험 기록 | 물리적 핏 보장, 모든 체형·상품 지원, 상용 서비스 완료 |
| S0: 사진 입력과 실제 고민 검증 | 사진으로 초기 옷장 초안을 만드는 로컬 시제품에서 누락·수정 부담을 측정. 병행하여 개인 조건·보유 옷 → 보완할 역할 → 실제 상품·후기 → 코디 → 구매처/보류를 비교. 수동 조사 여부와 시간을 기록 | 자동 제품 완성, 개인화 효용 확정, 개인판 전체 완성 |
| S1: 첫 흐름의 제품화 | S0의 사진 초안 생성·검토·확정과 개인화 비교를 저장하고 다시 이어가게 구현. 부분 등록·후속 사진 추가·미확인 표시·백업·복원·삭제 포함 | 모든 옷 종류 지원, 일상 코디와 관리 기능 전체 완료 |
| S2: 개인판 완성 | 일상 코디·사용 가능 상태·착용 기록 등 전체 FR 수용 기준과 §10의 개인 사용 문턱 검증 | 공개 서비스나 사업성 검증 |

S0에서 실제 상품 또는 관련 후기 근거를 확보하지 못하면 `자료 확보 실패` 또는 `부분 근거`로 남긴다. 그 상태에서도 화면 구조는 설계할 수 있으나, 원스톱 기능 검증에 성공했다고 기록하지 않는다. 개인 조건이 미정인 동안 사용하는 합성 예시는 실제 추천으로 세지 않는다.

사진으로 옷 목록과 기본 속성 초안을 만드는 자동화는 P0다. 수동 목록으로 추천 흐름을 검토할 수는 있지만 사진 온보딩을 완료했다고 세지 않는다. 로컬 처리 모델·성능·지원 기기는 미검증이며, [사진 온보딩 검증안](photo-onboarding.md)에 따라 개발 전에 범위와 실행 가능성을 확인한다.

## 5. 핵심 사용 흐름

### 시작. 사진으로 내 옷장 만들기 — 첫 진입의 필수 경험

1. 옷장 전경 또는 개별 옷 사진을 한 장 이상 선택한다. 촬영·기존 사진 선택을 제공하며, 사진 없이 직접 기록하는 대안도 둔다. 계정·체형·얼굴 사진을 먼저 요구하지 않는다.
2. 사진에서 보이는 옷을 찾아 아이템별 이미지와 종류·색·무늬의 초안을 만든다. 가려진 부분, 소재·사이즈·브랜드·정확한 모델은 임의로 채우지 않는다.
3. 사용자에게 초안 목록을 보여 준다. 잘못 나눈 영역과 누락을 고치고, 같은 옷으로 보이는 후보는 함께 보여 주되 합칠지는 사용자가 정한다. 비슷한 옷 두 벌을 자동으로 하나로 없애지 않는다.
4. 사용자가 고른 초안을 보유 옷으로 확정한다. 일괄 확인할 수 있으며 모든 속성을 일일이 입력할 필요는 없다. 보유 확정과 속성의 정확성 확인은 별도로 기록한다.
5. 일부만 확정해도 옷장을 열고 첫 코디·보완 제안으로 넘어간다. 불확실한 속성에 의존하는 판단은 유보하고, 관련 옷이 부족하면 이유를 알린다. 중단한 초안은 나중에 이어갈 수 있다.
6. 새로 산 옷이나 빠뜨린 옷도 같은 사진 추가 흐름으로 넣는다. 기존 옷과의 중복은 확인을 거치며, 이미 고친 속성을 자동 분석이 덮어쓰지 않는다.

옷장 전체가 한 번에 완전히 복원되었다고 표현하지 않는다. 등록된 범위와 더 추가할 수 있음을 보여 준다. 재촬영은 선택지이며 직접 영역 지정·수정·건너뛰기도 가능해야 한다. 초기 옷장 구성 뒤 목표 스타일과 이번 고민을 묻고, 세부 프로필은 필요한 때 보완하는 제안이다.

### A. 원하는 스타일로 옷장 채우기 — 주 흐름

1. 원하는 스타일과 피하고 싶은 스타일, 용도, 계절, 예산을 알려 준다. 스타일 이름을 몰라도 문장·선호/비선호 예시로 표현할 수 있다.
2. 관련된 보유 옷을 확인한다. 잘 맞는 옷의 실측, 선호 핏, 체형 관련 고민, 원하는 인상은 선택적으로 더한다. 없는 정보 때문에 전체 기능을 막지 않는다.
3. 보유 옷으로 목표를 얼마나 실현할 수 있는지와 먼저 보완할 아이템 종류·색·실루엣을 제안한다. ‘기본템이라서’만으로 구매를 권하지 않는다.
4. 제안한 종류에서 실제 상품을 최대 3개 비교한다. 원하는 스타일, 보유 옷 활용, 예산, 개인 특성과 연결된 추천 이유와 단점을 보여 준다.
5. 상품별 후기에서 내 고민과 관련된 근거를 읽고 원문을 확인한다. 정보가 부족하거나 서로 상반되는 경우도 표시한다.
6. 후보마다 내 옷과의 코디, 비슷한 보유 옷, 확인 가능한 실측 차이, 아직 모르는 핏/분위기 요소를 비교한다.
7. 구매처로 이동하거나 보류한다. 실제 구매 후 보유로 바꾸고 입어 본 결과를 남긴다.

한 번의 상품 탐색 범위는 그 고민의 용도·계절·예산 구간으로 좁히는 제안이다. 이는 제품 전체를 한 장르로 제한하는 결정이 아니다. 특정 브랜드나 성별 범위를 임의로 확정하지 않는다. 조건에 맞는 실제 상품이 없으면 검색 범위와 부족한 정보를 알리고 조건 변경은 사용자가 선택한다.

### B. 가진 옷으로 코디 고르기 — 반복 사용 흐름

1. 옷을 등록하거나 기존 옷을 수정한다. 사진 없이도 기록할 수 있다.
2. 계절과 용도를 고른다. 세탁 중이거나 오늘 제외한 옷은 선택에서 뺀다.
3. 실제 보유 옷으로 만든 조합을 최대 3개 본다. 조합별 근거와 주의점을 읽는다.
4. 마음에 드는 조합을 저장하거나, 별로인 이유를 남기고 다른 조합을 본다.
5. 실제 입은 뒤 ‘입었다/저장만 했다’를 구분해 기록한다. 평가 입력은 건너뛸 수 있다.

### 구매 전 본인 착장 미리보기 — 핵심 검증 흐름

사용자가 선택한 본인 사진과 확인한 상품 사진으로 착장 이미지를 만들고, 본인·의류가 바뀌거나 가려진 부분을 구분해 확인한다. 먼저 보유 옷의 실제 착용 사진과 같은 조건에서 비교한 뒤 구매 후보로 확장한다. 이미지가 자연스럽다는 이유만으로 해당 사이즈가 맞거나 실제 원단이 그렇게 떨어진다고 단정하지 않는다. 구체적인 입력·평가 기준은 [가상 착장 검토](virtual-fitting-feasibility.md)를 따른다.

### C. 이미 찾은 상품 가져오기 — 보조 진입점

1. 후보 한 벌을 수동 입력하거나 사진·링크를 보관한다. 링크만 넣었다고 상품 정보를 자동 확보한 것으로 처리하지 않는다.
2. 용도·예산·망설이는 이유는 선택 입력한다. 판정 전 마음은 건너뛸 수 있고 평가용 기록 여부를 분리한다.
3. 후보와 같은 종류의 보유 옷을 충분히 등록했는지 확인한다. 함께 입을 상의·하의도 선택한다.
4. 비슷한 보유 옷, 후보를 활용하는 조합, 주의점, 입력 부족을 한 화면에서 본다.
5. ‘산다/보류/사지 않는다/아직 모르겠다’와 이유를 남긴다. 구매 여부와 도움 여부는 별개다.
6. 구매 의향만으로 보유로 바꾸지 않는다. 실제 구매 후 사용자가 보유 전환을 실행한다.

직접 가져온 후보도 A와 같은 상품·후기·활용도 비교로 이어진다. 별개 도구로 끊기거나 개인 맥락을 매번 다시 입력하게 만들지 않는다.

첫 결과를 보기 위해 옷장 전체를 등록할 필요는 없다. 다만 일부만 등록했다면 ‘등록된 옷 기준’임을 보여 주며, 중복이 없다는 전체 옷장 결론을 내리지 않는다.

## 6. 필수 요구사항과 수용 기준 — 제안

아래 표는 다음 구현의 계약 초안이다. **현재 구현 완료 목록이 아니다.**

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| FR-01 | 옷 등록과 수정 | 사진 없이 이름·분류와 확인 가능한 속성을 저장한다. 모르는 속성은 미확인으로 남고 나중에 수정된다. 사진 입력 실패가 기록 자체를 막지 않는다. |
| FR-02 | 보유 상태 관리 | 보유·구매 후보·처분을 구분한다. 세탁/오늘 제외는 별도 사용 가능 상태로 둔다. 후보와 처분한 옷이 일반 보유 코디에 섞이지 않는다. |
| FR-03 | 속성과 출처 확인 | 자동 추정·직접 입력·사용자 확인을 구분한다. 브랜드·상품명·품번·참조 링크를 직접 입력하고 확인 여부를 남긴다. 브랜드 목록 밖의 자유 입력과 미확인을 허용한다. 검색 링크에는 입력한 텍스트만 사용하고 사진으로 브랜드를 추정하지 않는다. |
| FR-04 | 코디 추천 | 보유·사용 가능·선택 조건에 맞는 옷만 사용한다. 서로 다른 조합을 최대 3개 보여 주며, 부족하면 가능한 수와 이유를 알린다. 근거가 없는 확률을 표시하지 않는다. |
| FR-05 | 후보 중복 비교 | 비슷한 옷과 비교 근거를 보여 준다. 유형·색이 비슷하다는 사실을 동일 제품이나 구매 불필요 판정으로 바꾸지 않는다. 등록 범위가 불완전하면 그 한계를 표시한다. |
| FR-06 | 후보 활용도 설명 | §7의 정의에 따라 후보와 함께 입을 수 있는 조합을 제시한다. 0개·판단 불가·지원하지 않는 종류를 서로 구분한다. 옷이 부족할 때 구매를 자동 권유하지 않는다. |
| FR-07 | 결정과 실제 사용 기록 | 판정 전후 생각, 도움 여부, 실제 구매·착용을 별도로 저장한다. 평가 질문을 건너뛰어도 제품을 사용할 수 있다. 과거 판정의 기준 시점을 확인할 수 있다. |
| FR-08 | 사진·상품 정보의 경계 | 사진을 동일 제품/미확인 후보/대체 이미지로 구분한다. 유형 기반 그림은 별도 표시다. 대체 이미지의 브랜드·가격이 보유 정보에 자동 복사되지 않는다. |
| FR-09 | 사진 기반 초기 옷장 생성 | 옷장 전경·개별 옷 사진에서 보이는 아이템과 종류·색·무늬 초안을 자동 생성한다. 미확인과 추정을 구분하고 브랜드·상품명·사이즈 입력 없이 검토할 수 있다. 재촬영을 강제하지 않으며 수동 대안을 제공한다. 자동 생성 검증 없이 수동 입력만으로 이 요구를 완료 처리하지 않는다. |
| FR-10 | 저장·내보내기·복원 | 다시 열어도 기록이 유지되고, 파일로 내보내 재가져오면 선택한 데이터가 보존된다. 저장 실패를 알린다. 가져오기 전 덮어쓰기 범위를 보여 주며 잘못된 파일로 기존 기록을 손상시키지 않는다. |
| FR-11 | 삭제와 비공개 기본값 | 아이템·사진·전체 기록 삭제를 제공한다. 개인 사진·가격·체형·결정 기록은 공유용 내보내기에서 기본 제외한다. 백업 파일의 별도 삭제가 필요함을 알린다. |
| FR-12 | 시각적 완성도와 접근성 | §8의 데스크톱/모바일 흐름을 검증한다. 보유와 후보·미확인 정보를 색만으로 구분하지 않는다. 주요 동작은 키보드로 가능하다. 사용자에게 완성 화면 판단을 받는다. |
| FR-13 | 개인 맥락과 목표 스타일 | 공통 옷장·개인 정보와 고민별 목표 스타일·용도·계절·예산을 구분해 수정·재사용한다. 복수 스타일과 상황별 선택을 허용하고 한 장르를 영구 분류로 강제하지 않는다. 체형·얼굴 분위기 입력은 선택이며, 사용자 표현·추정·미입력을 구분한다. |
| FR-14 | 옷장 보완 우선순위 | 먼저 보완할 종류·색·실루엣과 이유를 목표 스타일 및 보유 옷에 연결한다. 새 구매 없는 대안을 함께 검토한다. 조건 변경 시 순위·후보 유지 여부와 이유를 재평가하고, 조합 수만으로 구매 가치를 판단하지 않는다. |
| FR-15 | 실제 상품 발견·구매처 연결 | 확인된 상품명·옵션·판매처·링크·조회일과 확인 가능한 가격을 제공한다. 예산/용도 조건에 맞는 상품을 비교하고, 품절·정보 없음·조회 실패를 구분한다. 사용자가 후보를 전부 가져오지 않아도 검증 범위에서 결과를 받을 수 있다. |
| FR-16 | 나에게 관련 있는 후기 비교 | 출처와 원문 근거가 있는 후기를 내 관심사에 연결한다. 장점·단점·상반된 의견·자료 부족을 표시한다. 후기의 착용자 조건은 명시된 경우만 쓰며, 같은 모델/버전인지 확인하고 다른 제품 후기를 섞지 않는다. |
| FR-17 | 개인화 설명과 핏의 한계 | 목표 스타일, 보유 옷, 선호 핏, 실측, 후기 각각의 근거를 구분한다. 선택 실측은 같은 측정 부위·단위일 때만 비교한다. 얼굴 분위기 취향 제안과 객관적인 치수 비교를 하나의 정확도 점수로 합치지 않는다. |
| FR-18 | 사진 초안 검토·확정·이어하기 | 여러 사진의 초안을 검토하며 영역 수정·누락 추가·제외·중복 병합/취소를 할 수 있다. 사용자 확인 전 보유 옷이나 추천 근거로 쓰지 않는다. 선택한 항목만 확정하고 나머지는 저장·재개·삭제한다. 재시도·중복 확정이 보유 기록을 늘리지 않으며 후속 추가에서도 기존 사용자 수정이 보존된다. |
| FR-19 | 선택적 공간에서 옷 선택 | 현재 Blender 옷장은 보조 표현으로 유지한다. 옷 꺼내기·확대·복귀와 해당 옷 코디를 연결하고, 개인 옷장에는 등록한 옷만 연결한다. 미지원·초과 옷과 WebGL 미지원 상태에서도 목록 접근을 유지한다. 이 기능을 본인 착장 미리보기의 완료 근거로 쓰지 않는다. |
| FR-20 | 미리 준비한 AI 추천과 선택적 갱신 | 준비한 추천·가져온 AI 응답·규칙 조합의 출처를 구분한다. 샘플 추천을 실제 개인 옷장 추천으로 표시하지 않는다. 사용자가 요청문을 내보내고 JSON을 가져올 수 있으며, 현재 보유·사용 가능 옷 ID와 선택한 옷 포함 여부를 검증한다. 앱 안에서 모델을 실행하거나 자동 전송하지 않는다. |
| FR-21 | 본인 착장 미리보기 | 본인 얼굴·체형과 실제 의류의 색·무늬·구조를 유지하는 결과를 목표로 한다. 구현 방식은 2D/3D로 제한하지 않는다. 보유 옷 10–20착장의 생성 결과와 실제 착용 정답을 분리해 비교하고, 왜곡·지원 범위·실패를 표시한다. 미리보기로 물리적 핏이나 사이즈 적합을 보장하지 않는다. 현재 미구현이다. |

사진에서 옷을 찾아 초안으로 만드는 기능과 정확한 판매 상품을 식별하는 기능은 별개다. 자동 상품 식별·계정 동기화·모든 의류 지원은 필수 완료 범위에서 제외하는 제안이다. 본인 착장 미리보기는 FR-21로 별도 검증하며, 기존 기능도 새 수용 기준을 만족하는지 다시 확인한다.

## 7. 판단과 데이터의 의미

### ‘나에게 맞는다’의 다섯 축

| 축 | 사용할 근거 | 결과 | 한계 |
| --- | --- | --- | --- |
| 원하는 스타일 | 사용자가 고른 방향·선호/비선호 예시 | 원하는 느낌을 만드는 색·실루엣·디테일 제안 | 주관적 선호이며 보편적 정답이 아님 |
| 옷장 활용 | 실제 보유 옷과 사용 조건 | 함께 입을 조합, 겹치는 역할, 보완 이유 | 미등록 옷은 알 수 없음 |
| 체형·핏 | 사용자 설명, 잘 맞는 옷의 실측, 확인된 상품 치수 | 측정 부위별 차이, 확인할 점, 선호 핏과의 관계 | 사진만으로 정확한 사이즈·착용감 보장 불가 |
| 얼굴 분위기·인상 | 사용자가 표현한 인상·선호 색·원하는 분위기, 선택한 로컬 참고 자료 | 원하는 인상을 위한 스타일 가설과 비교 선택 | 외모 점수·인종·성격 판정으로 바꾸지 않음; 사용자가 고칠 수 있음 |
| 예산·사용성 | 사용자 예산, 출처 있는 가격, 착용 목적, 관련 후기 | 비교 가능한 후보와 단점 | 재고·가격 변동, 후기 편향 |

초기에는 근거와 우선순위를 공개하는 규칙·수동 큐레이션을 기준선으로 둔다. 서로 다른 축을 근거 없는 ‘어울림 92%’로 합치지 않는다. 예산은 입력된 경우 상한 조건으로 다루고, 초과 대안은 별도 표시한다. 조건 변경 없이 상한을 몰래 넘기지 않는다.

**판단 순서**는 `확인된 필수 조건 → 목표 상황/스타일 → 보유 옷으로 해결되지 않는 역할 → 활용 가능한 코디와 사용자의 선호`를 기본 제안으로 둔다. 사용자에게 명시적으로 등록된 제외 조건은 필터로 적용하고, 취향에 관한 선호와 미확인 정보는 구분한다. 알 수 없는 가격·사이즈·소재가 필수 조건과 관련되면 조건을 충족했다고 처리하지 않는다.

각 추천은 `사용한 개인 조건 → 확인된 상품 특징·보유 옷·후기 근거 → 추천/보류 이유 → 모르는 점`으로 추적할 수 있어야 한다. 입력 하나를 바꾸어도 결과가 그대로일 수 있지만, 그 조건이 사용됐는지와 그대로인 이유를 설명해야 한다. 얼굴·체형 정보를 입력하지 않았다면 이를 분석한 듯한 문장을 만들지 않는다. 세부 사례는 [개인화 판단 기준](first-slice.md#3-개인화가-작동한다는-것의-의미)에 둔다.

### 상품·후기 정보 확보 — 제품의 핵심 의존성

- 첫 검증은 프로젝트 측이 소수의 실제 상품과 접근 가능한 후기 근거를 확인해 준비한다. 사용자가 평소 하던 검색을 모두 다시 해야 한다면 절감한 일이 없는 것이다.
- 공식 상품 설명, 판매처 정보, 후기 작성자의 경험, 제품의 해석을 구분한다. 원문 링크·확인일·모델/옵션·증거를 남기고 요약은 추적 가능하게 한다.
- 후기 수, 구매 인증 여부, 작성자 체형, 사용 기간을 확인하지 못했으면 추정하지 않는다. 서로 상반된 후기는 평균적인 결론으로 지우지 않는다.
- 접근 제한·이용 조건 때문에 읽을 수 없는 후기는 자료 부족으로 표시한다. 외부 데이터를 가져올 수 있는 경로와 갱신 비용은 구현 전 확인할 핵심 과제다.
- 초기 로컬 카탈로그는 해당 시점의 자료다. 최신 정보 조회가 안 되면 마지막 확인일을 보여 주고 판매처 재확인을 안내한다. 오프라인에서 실시간 가격·재고를 주장하지 않는다.
- 상품 조사·요약 준비 시간도 기록한다. 수동 시범 운영의 편의성이 자동 운영의 실현 가능성까지 입증하지는 않는다.
- 자료 공급 상태를 `비교 가능 / 부분 근거 / 자료 확보 실패`로 기록한다. 후기 링크만 존재하고 관련 원문을 읽지 못한 경우에는 후기 비교 완료로 세지 않는다. 현재 실제 접근 관찰과 미확인 범위는 [확보 상태 문서](data-readiness.md)에 둔다.

### 조합 수와 중복

- 상의/하의 후보: 후보와 짝지을 수 있는 반대 분류의 보유 옷 조합을 센다. 같은 상하의에 겉옷만 여러 개 바꾼 것을 기본 조합 수에 중복 가산하지 않는다.
- 아우터 후보: 등록된 상하의 쌍 가운데 그 아우터를 함께 입는 조건을 충족한 쌍을 센다. ‘기존 조합 수에서 늘어난 수’로 표현하지 않는다.
- 기본 조합 수는 규칙이 통과한 경우의 수다. 사용자 취향, 실제 착용 가능 횟수, 구매 가치와 동일하지 않다.
- 활용도 설명은 `목표 상황에서 입을 코디 / 이미 있는 옷과 역할 중복 / 새로 해결하는 부족`을 먼저 제시하고 조합 수는 보조 정보로 쓴다. 가진 옷만으로 목표를 충족하는 대안을 함께 비교한다.
- 규칙상 주의점은 취향에 따라 받아들일 수 있다. 사용자는 추천을 거절하거나 자신만의 조합을 저장할 수 있다.
- 신발·소품은 초기에 기록만 지원한다는 제안이다. 미지원 조합을 0점으로 평가하지 않는다.
- 필수 속성이 모르면 관련 판단을 보류한다. 임의 기본값으로 단정하거나 미확인을 ‘모든 계절에 적합’으로 바꾸지 않는다.
- 같은 입력·같은 규칙 버전의 결과는 재현 가능해야 한다. 과거 판정에는 입력 요약과 규칙 버전을 남긴다. 전체 사용자 사진을 로그로 남길 필요는 없다.

현재 코드에는 색·밝기·격식·무늬에 관한 수작업 규칙이 있다. 이 숫자와 ‘주의점 없음’이 패션 전문성이나 실제 만족도를 보장하지 않는다. 규칙 조정은 반례와 실제 사용 기록을 근거로 한다.

예를 들어 현재 `scorePair`는 가까운 색·밝기를 감점하지만, 사용자가 톤온톤을 목표로 삼으면 그 기준이 맞지 않을 수 있다. 이를 새 개인화 기능으로 그대로 재사용하기 전에 취향에 따른 규칙을 재검토한다. 현재 동작에 맞춰 새 PRD의 품질 기준을 낮추지 않는다.

| 후기 근거 | 출처·제품 식별·확인일·관련 주장·원문 근거·요약. 사용자 프로필과 분리 |
| 조합 | 실제 옷 기록 ID의 묶음, 조건, 준비한 AI/가져온 응답/규칙의 출처, 저장·착용 여부, 제외 사유 |
| 판정 기록 | 후보 ID, 입력 요약, 규칙 버전, 비교 결과, 전후 생각·구매·도움 여부 |
| 내보내기 | 스키마 버전, 사용자가 선택한 공개 항목, 데이터 파일 |

브랜드와 이름이 같다는 이유만으로 두 옷이 동일 상품이라고 확정하지 않는다. 상품 식별과 스타일 유사도를 분리한다. 상품 가격은 출처와 확인일이 있을 때만 보여 주고 실시간 가격으로 표현하지 않는다.

## 8. 화면 품질과 3D의 위치

핵심 화면은 사진 가져오기·초안 확인, 나의 스타일/조건, 내 옷장, 다음 한 벌 제안, 상품·후기 비교, 본인 착장 미리보기·실제 착용 비교, 내 옷과 코디, 기록/백업이다. 각 화면을 별도 탭으로 만들라는 요구는 아니다. 같은 맥락을 유지하며 이동하는 흐름을 우선한다. 3D 구현 여부와 별개로 정보 우선순위·여백·사진 품질·선택 피드백이 갖춰져야 한다.

개발 전 시안에서 ‘사진 선택 → 자동 초안 → 간단한 검토 → 첫 옷장 → 원하는 스타일 → 보완 제안 → 실제 상품/후기 → 본인 착장 미리보기·내 옷과 코디 → 구매처’와 ‘보유 옷으로 코디’의 반복 흐름을 보여 준다. 가져온 후보는 주 흐름의 상품 비교로 합류한다. 실데이터와 예시를 구분하고, 제품명·가격·만족도 숫자를 화면을 채우기 위해 만들어 넣지 않는다.

**화면 수용 기준(제안)**

- 390×844와 1440×900에서 핵심 텍스트·버튼·옷이 겹치거나 잘리지 않는다. 스크롤을 금지하는 뜻은 아니다.
- 등록된 옷과 구매 후보를 즉시 구분하고, 결과가 어떤 옷을 근거로 나왔는지 확인할 수 있다.
- 사진 처리 중·취소·일부 실패·옷을 못 찾음·중복 확인·초안 재개, 빈 옷장, 입력 부족, 결과 0개, 불러오기 실패, 저장 실패 상태를 디자인한다.
- 비교·선택·수정·뒤로 가기를 찾을 수 있다. 사용자에게 ‘다시 쓰고 싶은가’와 불편한 구체적 요소를 묻는다.
- 브라우저가 3D를 지원하지 않아도 핵심 기록과 판단이 가능하다.

Blender 공간은 D-12에 따라 구현했으나 D-16 이후 선택적 보조 경험이다. 옷은 **유형 기반 자산**이며 실제 보유 제품 재현·본인 착장·핏 예측과 구분한다. 현재 공간의 시각 품질을 개선하되, 핵심 제품의 합격은 실제와 비교한 본인 착장 미리보기로 판단한다. 2D가 더 충실하면 2D를 선택하고 저사양 기기의 부담도 함께 측정한다.

## 9. 데이터·비용·운영 조건

- 현재 개인판은 API 키·로컬 LLM 설치·상시 AI 서버 없이 실행한다. 개발 단계에서 Codex로 작성한 샘플 추천을 앱에 포함하고, 추가 추천은 사용자가 이미 이용하는 Codex·Claude에서 준비할 수 있다. 앱의 반복 API 호출 비용은 없으며, 외부 AI 서비스 자체의 이용 조건·요금이 무료라는 의미는 아니다.
- 선택적 AI 요청문에는 확정한 사용 가능 옷의 텍스트 정보·스타일 조건과 등록한 구매 후보의 이름·종류·기록 가격·확인일을 담는다. 사진·상품 URL·개인 메모·착용 기록은 제외하며 전달은 사용자가 직접 실행한다. 응답을 가져와도 생성 모델이나 내용의 사실성을 검증한 것으로 표시하지 않는다. MCP로 AI 도구가 옷장을 읽고 쓰는 연결은 후속 범위이며 현재 연결되어 있지 않다.
- 개인 옷장·프로필·판정은 로컬 저장을 기본으로 한다. 사진 처리도 사용자의 로컬 환경 안에서 수행하며 원본·잘라낸 이미지·사진에서 추출한 표현을 외부에 보내지 않는다. 브라우저 내 처리 등 구체적 실행 방식과 지원 기기는 별도 검증한다. 저장된 카탈로그는 로컬에서 비교할 수 있고, 상품·후기 최신 확인과 판매처 이동은 네트워크가 필요한 별도 동작이다. 핵심 흐름을 유료 API에 종속시키지 않는다.
- 개인 데이터는 공개 GitHub, 오류 로그, 스크린샷, 테스트 결과물에 포함하지 않는다. 공개 예시는 합성 데이터를 사용한다.
- 개인 백업과 공유용 내보내기를 구분한다. 공유 파일에서 무엇이 빠지는지 사용자에게 보여 준다.
- 사진·민감한 원문을 수집하는 분석 도구를 기본 설치하지 않는다. 초기 사용 검증은 로컬 기록과 수동 회고로 충분하다.
- 외부 이미지 URL을 자동으로 불러오거나 링크 내용을 몰래 수집하지 않는다. 링크 방문은 사용자 동작이며 외부 이동임을 알린다.
- 상품 이미지 사용 권한과 API 제공 여부는 도입 직전에 확인한다. 접근 가능하다는 것과 재배포 허용을 동일시하지 않는다.
- 유료 서비스는 자동 대체 경로가 아니다. 필요해지면 비용·데이터 전송·실패 처리에 관한 별도 결정이 있어야 한다.
- 다중 사용자 공개를 선택하면 인증·권한·삭제·신고·운영 비용을 새 요구사항으로 명세한다. 개인판의 저장 방식으로 공개 서비스를 충분히 보호한다고 주장하지 않는다.

## 10. ‘본인 전용으로 충분히 완성’의 검증 — 제안

기능 완료, 실제 사용 가치, 사업성을 나눈다. 아래 숫자는 **사용자와 조정할 임시 판단 기준**이며 관찰 결과나 업계 기준이 아니다.

| 문턱 | 관찰 | 제안 통과 기준 | 실패하면 |
| --- | --- | --- | --- |
| 기능 | §6의 수용 기준과 주 흐름·반복 흐름·후보 합류, 저장·복원·삭제 | 필수 항목 검증 완료, 데이터 손실·의도치 않은 전송·흐름 중단 결함 없음 | 관련 결함부터 수정 |
| 본인 착장 충실도 | 보유 옷 10–20착장의 생성 결과와 실제 착용 사진을 비교 | 얼굴·체형·의류 디테일·길이·가림을 각각 평가하고, 구매 오판을 부르는 왜곡을 실패로 기록. 사용자가 유용한 지원 범위를 확인 | 입력·모델·지원 품목을 수정. 화질만으로 통과시키거나 평균 점수로 위험한 오류를 숨기지 않음 |

| 구매·개인화 효용 | 위 3건에서 선택 이유·본인 조건 반영·미확인 핏을 구분 | 2건 이상에서 일반 인기 추천과 다른 개인 근거를 설명하고, 구매 여부와 무관하게 판단에 도움 | 실제 효용이 없는 개인화 표현·근거 부족을 수정 |
| 정보 신뢰 | 위 후보의 상품·후기 주장과 원문 대조 | 검증 대상 주장에 근거가 있고, 오래됨·추정·자료 없음이 구분됨 | 잘못된 주장 수정, 해당 수집/요약 경로 재검증 |
| 입력·유지 부담 | 사진 준비·처리 대기·검토·후속 추가 시간을 직접 측정 | 본인이 계속 유지할 수 있다고 판단하고 반복 방해 요소를 해결 | 필수 입력과 자동 초안의 오류·수정 부담을 함께 줄임 |
| 시각 품질 | 시안과 실제 화면, 모바일/데스크톱 | 사용자 화면 수용, 겹침·왜곡·구분 실패 해결 | 디자인 재검토; 3D 실패를 다른 화면 전체의 중단 이유로 삼지 않음 |

실제 구매 후보나 외출 기회가 없으면 해당 관찰은 ‘대기’다. 검증을 위해 구매를 유도하거나 가짜 사례로 통과시키지 않는다. 개인판 사용은 그동안 계속할 수 있다.

직접 검색한 시간·찾아간 곳·중복 입력과 제품을 쓴 뒤에도 추가로 찾아야 했던 정보를 기록한다. 시간 단축 수치는 같은 범위로 측정한 뒤에만 보고한다. 운영자가 대신 조사한 시간도 함께 남긴다.

개인화 검증에서는 같은 후보 자료를 놓고 개인 조건을 쓰지 않는 기본 비교와 개인 조건을 반영한 결과를 대조한다. 본인 조건 때문에 달라진 후보·순서·제외·주의점을 기록하고, 설명 문구만 개인화한 경우는 별도로 표시한다. 사용자가 실제로 고르고 싶은 후보와 일치하는지도 확인한다. ‘3건 중 2건’은 개인 회고의 임시 기준으로, 통계적 유효성이나 타인에게의 일반화를 뜻하지 않는다.

한 사람에게 쓸모 있다는 결과는 개인판 성공의 근거다. 시장 수요·타인의 반복 사용·지불 의사의 증거로 확대하지 않는다. 이 결과를 보고 **공개를 진행할지, 개인 도구로 유지할지** 결정한다.

## 11. 커뮤니티는 어떤 가설로 검증할 것인가

커뮤니티는 사용자에게 도움이 되는 상호작용이 반복될 때 가치가 생긴다. 방문자 수만 늘거나 지인이 한 번 옷장을 올리는 것으로 성공이라 판단하지 않는다.

| 가설 | 도움이 될 수 있는 이유 — 추론 | 반론/실패 가능성 | 공개를 선택한 뒤 볼 행동 |
| --- | --- | --- | --- |
| 실제 옷장 기록이 유용하다 | 구매 직후 평점보다 오래 입은 조합·사용 기록이 판단에 도움이 될 수 있음 | 꾸준히 기록할 동기가 없을 수 있음 | 기록 추가, 구체적 질문, 재방문 |
| 취향이 맞는 사람의 옷장을 보고 싶다 | 한 장의 코디보다 반복되는 선택을 이해할 수 있음 | 기존 패션 피드로 충분할 수 있음 | 동일 옷장 재방문, 저장, 관심 이유 |
| 내 옷장과 비교하면 행동으로 이어진다 | 보유 옷으로 재현할 부분을 바로 찾을 수 있음 | 입력 부담이 이득보다 클 수 있음 | 비교 후 내 조합 저장·착용, 후보 판단 |

**추천하는 첫 공개 경험**: 사용자가 고른 작은 옷 묶음/코디와 실제 사용 기록을 공유하고, 방문자가 자기 옷으로 적용할 부분을 찾아보는 ‘옷장 방문’. ‘무엇을 샀는가’에 더해 ‘어떤 조건에서 얼마나 입었는가’를 개인화 판단의 근거로 연결한다. 유용한 기록이 실제로 모일지는 미검증이다. 옷장 전체 공개·연락처 수집·광범위한 피드 운영부터 시작하지 않는 제안이다.

초기에는 구경할 콘텐츠도 기록하는 사람도 적다는 문제가 있다. 본인 기록과 참여 의사가 있는 사람의 동의한 자료로 시작할 수 있지만, 임의의 가짜 사용자·후기·활동량을 채워 넣지 않는다. 동의받지 않은 상품 사진이나 개인 사진을 공개 자료로 쓰지 않는다.

성장 가설의 고리는 **자발적 공유 → 방문 → 내 옷에 적용 → 실제 사용 → 후속 기록**이다. 이 고리가 측정되지 않으면 ‘커뮤니티 효과’라 부르지 않는다. 빈도·표본·기간·계속할 기준은 공개 결정 시 별도 실험 계획으로 정한다. 현재 모집 일정이나 성장 목표 숫자는 확정하지 않는다.

수익모델과 가격은 미정이다. 유료화나 실제 결제를 개인판 개발의 완료 조건으로 삼지 않는다. 제휴를 도입하더라도 수수료를 추천의 판단 근거로 사용하지 않는 것이 인계 원칙이다.

Java/Spring·PostgreSQL·React·AI 모델은 과거 설계 후보다. 구체적 버전과 도입 순서는 PRD 이후 ADR에서 정한다. 개인 사용 중에도 학습용 백엔드를 만들 수 있으나 그것을 공개 수요의 증거로 쓰거나 현재 로컬 기능의 필수 운영비로 만들지 않는다. 사업 검증이 실패해도 재현 가능한 기술적 결과는 남길 수 있다.

## 13. 현재 상태와 다음 작업

### 인계 검증과 현재 구현 상태

- 인계 개인판의 `npm test`: 19개 통과, 실패·건너뜀 0개.
- `npm run build`, `npm run build:empty`: HTML 빌드 통과.
- 사진 제외 인계본의 옷 데이터는 13개이며 이미지 필드가 비어 있다. 속성 정확도는 사용자 확인 전이다.
- 위 숫자는 인계판의 초기 검증이다. 후속 `prototype/`의 실행 결과는 [프로토타입 검증 기록](../prototype/VALIDATION.md)에 별도로 남긴다.
- 사진·3D·코디·구매 비교 기능의 프로토타입 이후 사용자가 시각 품질 미달을 지적했다. 현재 재질·조명·의류 형태와 화면을 수정 중이며, 최신 변경의 기능 검증과 실제 기기 성능·사용자 만족도는 각각 확인해야 한다.
- 준비한 AI 추천과 상품 식별 정보 입력을 추가하는 현재 작업을 개인판 전체 완료나 실시간 AI 연결로 해석하지 않는다.
- 본인 얼굴·체형에 실제 상품을 입히는 생성형 착장 기능은 없다. [공식 후보·라이선스·검증 설계](virtual-fitting-feasibility.md)만 조사했으며 모델을 설치하거나 실행하지 않았다.

### 다음 순서

1. 이 PRD의 개인판 범위와 ‘충분히 완성’ 기준을 사용자와 다듬는다.
2. 본인 착장 미리보기의 후보·라이선스·비용을 검토하고 보유 옷의 실제 착용 정답과 비교할 V0 실험을 준비한다. 기존 사진 온보딩·코디·상품 비교 흐름은 유지한다.
3. 기존 개인판과 FR-01~FR-21의 차이를 이슈로 정리하고 사진 처리·착장 충실도·상품/후기 확보 경로를 검증한다. 기존 코드를 새 PRD에 맞다고 가정하지 않는다.
4. 선택한 범위에 필요한 환경 검증을 마치고, 작은 PR 단위로 구현한다.
5. 개인 사용 기록을 모아 공개 여부를 결정한다. 커뮤니티 실험은 그 결정 이후다.

첫 검증 스타일은 아메리칸 클래식이다. 핵심 목표는 현실에 가까운 본인 착장 미리보기이며 3D는 필수 조건이 아니다. 미결정: 구체적 모델·실행 위치·비용, P0 세부 수용 기준, 실제 용도·예산·보유 옷, 상품/후기 확보와 이용 범위, 개인화 평가, 후속 MCP 연결, 공개 타깃과 수익모델. 이 문서의 초안 작성은 이 결정들이 모두 끝났다는 의미가 아니다.

## D1: 장기 방향은 권고, 이전은 계정 경계 다음

다기기 이용·커뮤니티를 위해 **로그인 사용자의 옷장/구매 기록은 서버 정본으로 옮기는 방향**이 적절하다. 현재 규모의 관계형 메타데이터에 D1은 자연스러운 후보다. 다만 커뮤니티를 만든다는 사실만으로 모든 개인 기록을 공개 저장할 이유는 없다. 옷장/구매는 비공개, 게시물은 사용자가 고른 항목의 공개 스냅샷으로 분리한다.

먼저 계정/세션·탈퇴·데이터 소유권을 설계한다. 현재 본인 전용 Access 통제나 기기 ID를 다중 사용자 ownerId로 대체 없이 사용하지 않는다. ownerId는 서버 인증 결과에서 결정한다. D1 용량·쓰기 빈도·무료 한도 적합성은 실제 사용량을 측정해 재평가한다. 사진은 보류하며 미래에도 원본 바이너리를 D1 레코드에 넣는 설계를 기본으로 하지 않는다.

인터페이스 제안(지금 구현하지 않음):

```ts
interface WardrobeRepository {
  load(): Promise<Snapshot>; // schemaVersion + revision + 원본 도메인 데이터
  execute(command: WardrobeCommand, options: {
    commandId: string; draftId?: string; expectedRevision: string;
  }): Promise<CommitResult>;
  exportJSON(): Promise<Backup>;
  previewImport(input: unknown): Promise<ImportPreview>;
  // 확인된 preview/revision으로 명시적 merge/replace 커맨드를 실행
}
```

- UI는 localStorage/SQL/fetch를 직접 호출하지 않는다. 코어 서비스가 비동기 저장 성공 뒤 캐시를 교체하고 subscribe로 알린다. React는 그 구독을 사용하며 두 번째 도메인 상태를 별도로 유지하지 않는다.
- CommitResult는 committed/duplicate/conflict/rejected(용량·접근 불가·검증 오류 등)를 구별한다. 네트워크 타임아웃은 실패 확정이 아니므로 outcomeUnknown으로 취급하고 **같은 commandId**로 재조회/재시도한다.
- 등록·부가정보·구매 전이·착용 기록을 커맨드 단위로 원자 처리한다. 로컬 어댑터는 v1+reg를 읽는 호환 reader를 두고 새 버전 단일 저장 단위로 전환하는 방안을 검증한다. 원본 키를 먼저 삭제하지 않고 다음 새로고침 검증/내보내기까지 보존한다. 기존 IndexedDB를 자동 합치지 않는다.
- draftId는 등록 시작 때 발급한다. 제출 commandId와 연결하여 유일성 제약을 둔다. 같은 ID/같은 payload는 기존 결과 반환, 같은 ID/다른 payload는 오류다. 버튼 비활성화만으로 중복을 막지 않는다.
- 서버 어댑터는 `(owner_id, command_id)` 유일성과 revision 조건부 갱신을 **같은 D1 트랜잭션/원자 batch 안에서** 보장한다. 충돌은 409 계열의 명시적 결과로 돌려주며 다른 기기 기록을 덮어쓰지 않는다.
- schemaVersion(데이터 형식), revision(동시성), API 버전, draftVersion을 분리한다. 마이그레이션은 순수 함수+과거 fixture 검사, 미지원 미래 버전은 읽기/가져오기 거절이다.
- 서버 이전은 JSON 백업→명시적 업로드→개수/ID/기록 검증→정본 전환 순서로 한다. 처음부터 양방향 오프라인 동기화·자동 병합을 구현하지 않는다. 로컬은 입력 초안과 선택적 읽기 캐시를 맡는다.

## 병행 트랙: 실제 브랜드·품명 추천

개선 순서:

1. 합성 옷장·요청 20–30개로 평가 세트를 만든다. 없는 종류, 이미 충분한 종류, 어울릴 색, 예산/제외 조건, 특정 브랜드, 후보 0개를 포함한다. “부족함”은 계절/상황/사용자 목표 기준의 역할 빈자리이며 종류가 없다는 이유만으로 구매 필요로 단정하지 않는다. **1–2인일**.
2. 옷장 빈자리→필요한 역할/종류/색/예산→허용된 실제 상품 공급원 검색을 연결한다. 공급원별 canonical ID/brand/name/category/price+currency/checkedAt/url/출처/사용권한과 미확인 필드를 분리한다. 먼저 국내 피드 하나에서 검증하며 실제 브랜드 커버리지/최신성/판매 링크 유효성을 측정한다. **3–5인일**, 공급자 권한 확인 대기 별도.
3. 예산·종류·제외 조건 등 확정 조건은 코드로 필터링, 새 코디 수/기존 옷 중복/사용자 선호로 순위를 계산한다. unknown 핏/재고를 맞다고 처리하지 않는다. AI는 허용된 사실의 설명/정렬만 보조한다. 실상품 카드에는 “어떤 내 옷과 어울리는지·무엇이 추가되는지·확인 안 된 점”을 제시한다. **2–4인일**.
4. 상담 화면 한 곳에 먼저 연결해 상품 상세→구매/착용 피드백까지 평가한다. 후보 부족이면 이유와 조건 완화 선택지를 주며 몰래 다른 브랜드/예산으로 채우지 않는다. **1–2인일**.

총 **7–13인일**의 별도 트랙 추정. 가격 조건 위반율, 실제 링크 있는 후보 제공률, 브랜드 요청 충족률, 중복 추천률, 사용자가 선택/보유/착용한 결과를 측정한다. 측정 전 추천 정확도 개선 수치를 제시하지 않는다. 두 트랙을 같은 개발자가 진행하면 인일은 합산되며 병행한다고 작업량이 줄지 않는다. 엔진/API 개선을 React 컴포넌트 안에 넣지 않는다.

## 이번에 만든 것

### 1. 사진에서 옷 한 벌만 자르기

- **동작**
  - 사진을 고르면 "옷만 자르기" 버튼이 나온다.
  - 누르면 자르기만 하는 화면으로 바뀐다. 원본 위의 상자를 끌어 옮기고, 네 모서리를 끌어 크기를 바꾼다.
  - 키보드로는 방향키로 옮기고, Shift+방향키로 크기를 바꾼다.
  - "이 영역으로 자르기"를 누르면 잘린 JPEG가 저장 대상이 된다.
  - 자른 뒤에는 "자른 영역 다시 조정"과 "자르기 전 사진으로"를 쓸 수 있다.
  - 사진 분석이 "한 벌을 구분하기 어려워요"라고 판단하면 그 안내에서 바로 자르기로 간다.
- **원본은 저장하지 않는다**
  - 고른 원본 파일은 초안(메모리)에만 둔다. 그래서 저장하기 전까지는 몇 번이고 다시 조정할 수 있다.
  - 저장되는 것은 잘린 JPEG 한 장(긴 변 1024px 이하)뿐이다. 개인 사진의 원본을 기기 저장소에 하나 더 두지 않으려는 결정이다.
- **실패하거나 취소해도 입력은 남는다**
  - 취소하면 이전 사진, 고른 종류, 적은 이름이 그대로다.
  - 인코딩이 실패해도 이전 사진을 바꾸지 않고, 자르기 상자를 열어 둔 채 오류를 보여 준다. 같은 동작으로 다시 시도할 수 있다.
  - 사진이 복잡해 용량이 크면 JPEG 품질을 0.82 → 0.7 → 0.6 순으로 낮춘 뒤에야 실패로 처리한다.
  - 자른 뒤에는 이전 사진에서 나온 분석 후보만 지운다. 사용자가 확정한 종류·색·이름과 라벨 글자는 유지한다.
- **이미 저장한 옷 수정**: 저장된 JPEG를 원본으로 다시 자를 수 있다. 옷 ID와 등록일은 유지한다. 해상도는 저장본(1024px) 이하로 제한된다.
- **검토한 대안**
  - Cropper.js 1.6.2(MIT, 약 14KB gzip)는 쓰지 않았다. 필요한 것이 사각형 하나라서 직접 구현했다. 외부 스크립트를 하나 덜 들이고, 단일 HTML 빌드에도 그대로 들어간다.
  - 원본까지 저장하는 방식은 버렸다. 용량이 두 배가 되고, 개인 사진을 불필요하게 하나 더 보관하게 된다.

### 2. iPhone HEIC 사진

- **브라우저 자체 해독을 먼저 시도한다**
  - `image/heic`·`image/heif` 형식이거나, 형식은 비어 있지만 파일 이름이 `.heic`·`.heif`이면 브라우저의 자체 해독기로 열어 본다(Safari 17+에는 해독기가 있다).
  - 열리면 JPEG로 바꿔 저장한다. 같은 사진을 자를 수도 있다.
- **열리지 않으면 안내한다**: iPhone 설정 > 카메라 > 포맷 > '높은 호환성'과 앨범에서 다시 고르는 방법을 알려 준다. 등록 초안은 그대로 남는다.
- **앨범 입력은 그대로 둔다**: `accept="image/jpeg,image/png,image/webp"`를 유지한다. WebKit 버그 292350에 따르면, HEIC를 뺀 형식 목록이면 Safari가 사진을 목록 첫 형식(JPEG)으로 바꿔 넘긴다.
- **해독 라이브러리는 넣지 않았다**: `libheif-js`와 `heic2any`는 LGPL-3.0이고, HEVC 특허 문제가 확인되지 않았다(`toolkit-20261014.md` 3절).
- **실기기 미확인**: 어느 iOS 버전부터 이렇게 변환하는지, 실제 iPhone에서 어떻게 동작하는지는 확인하지 않았다.

### 3. 색 미확인이 구매 판단에 주는 영향

`compareCandidate`는 종류와 색이 모두 확인된 실제 옷만 코디 공식 수에 넣는다. 그래서 색을 건너뛴 옷은 구매 판단에서 빠진다. 이 사실이 보이도록 했다.

- **상품 목록 보유 확인 화면**
  - 색 상태에 따라 안내가 바뀐다.
    - 확인 전: "색을 확인하지 않으면 이 옷은 구매 비교의 조합 수에 들어가지 않고, 비교할 때 색을 다시 물어봐요."
    - 확인 뒤: "구매 후보와 비교할 때 이 옷을 조합 수에 넣어요."
  - 판매처가 표시한 색이 있는 상품: 그 색으로 확인하거나 "아직 모름"만 고를 수 있다. 다른 색이면 기존의 '다른 색·비슷한 옷' 경로로 가고, 이때는 상품을 연결하지 않는다.
  - 상품 색이 사진에서 추정한 값뿐인 상품: 그 값을 쓰지 않고, 사용자가 색 팔레트에서 직접 고른다.
- **저장한 뒤**
  - 안내창(토스트)에 "색을 확인하면 구매 비교에도 쓰여요"가 붙는다.
  - 옷장 칸에 "색 미확인"이 표시된다.
  - 옷 화면에서 한 번 눌러 색을 확인할 수 있다. 상품 색이 있으면 그 색만 고를 수 있다.
  - 이 확인은 성별·스타일·브랜드·예산·상황을 바꾸지 않는다(테스트로 확인).
- **색을 자동으로 채우지 않는다**: 같은 상품 번호에도 여러 색이 있을 수 있어서, 카탈로그 색을 내 옷 색으로 그냥 넣지 않는다(Codex 결정 유지).

### 4. 이 기기 보관 상태와 백업 안내

공식 근거는 2026-10-15에 확인했다.
- WebKit "Full Third-Party Cookie Blocking and More"(2020-03-24)
  - Safari를 쓰는 7일 동안 사이트와 상호작용이 없으면, 스크립트로 저장한 자료(IndexedDB 포함)를 지운다.
  - 홈 화면 웹 앱은 Safari와 별도로 사용 일수를 센다.
- WebKit "Updates to Storage Policy"(2023-08-10, Safari 17)
  - Storage API를 지원한다. `persist()` 요청은 홈 화면 앱 여부 같은 기준으로 브라우저가 판단한다.
  - '오래 보관(persistent)'으로 표시된 사이트는 자동 정리에서 빠진다.
- MDN "Storage quotas and eviction criteria"(2026-01-05 수정)
  - Safari·Chromium은 알림 없이 스스로 판단한다. Firefox는 사용자에게 묻는다.

구현한 내용:
- **오래 보관 요청**: 첫 실제 저장 뒤 `navigator.storage.persist()`를 한 번 요청한다. 거절되는 경우가 흔하다.
- **백업 알림**: 실제 옷이 3벌 이상인데 백업 파일을 받은 기록이 없거나 14일이 지났으면 옷장에 알림을 띄운다.
  - iPhone Safari(홈 화면 앱이 아닐 때)에는 7일 규칙도 함께 알린다.
  - 이번 세션 동안 숨길 수 있다.
- **설정 화면**: 오래 보관 표시 여부, 사용량 추정, 마지막으로 백업 파일을 받은 날을 보여 준다.
- **"보관 안내" 화면**에는 다음을 적었다.
  - 서버 백업과 계정이 아직 없다는 사실
  - 브라우저가 자료를 지울 수 있는 경우
  - 홈 화면 앱은 저장 공간이 따로일 수 있으니, 옮길 때는 Safari에서 백업 파일을 받아 '백업 가져오기'로 불러오라는 방법
  - 근거 링크
- **"보관 보장"이라고 쓰지 않는다**: 홈 화면에 추가해도, 오래 보관으로 표시돼도 사용자가 직접 지우거나 기기를 바꾸면 자료가 사라진다.
- **마지막 백업 날짜의 의미**: 이 기기의 `localStorage`에 남긴 "백업 파일을 받은 기록"이다. 파일이 실제로 보관됐는지는 브라우저가 알려 주지 않는다.
- **추정으로 남긴 문구**: "홈 화면 앱은 Safari와 저장 공간이 따로일 수 있어요"는 위 공식 문서에 직접 나오지 않는다. 실기기 확인이 필요해서 "따로일 수 있어요"로 적었다.

### 5. 외부 분석 도구 무결성

- **Transformers.js 3.8.1 실행 파일**: 워커 안에서 먼저 내려받아 SHA-384를 확인한다. 고정한 값과 다르면 사용하지 않는다. 사용자에게 "고정한 버전과 달라 사용하지 않았어요. 종류를 직접 골라 주세요"라고 알리고, 직접 고르는 등록으로 계속한다.
- **Tesseract.js 6.0.1 스크립트**: `integrity`(SRI) 속성을 붙여 불러온다. 값이 다르면 브라우저가 실행을 막고, 라벨 글자를 직접 적는 경로로 안내한다.
- **고정 해시** (2026-10-15에 해당 URL에서 계산)
  - `transformers.min.js`: `sha384-sOua6i337lNLWtuIG44PBf5JXIvhoicFClCcI4XHDe/eHW3dwhQ3Y6t6wQjfRrkT`
  - `tesseract.min.js`: `sha384-r1ru3tcf6FhnCFR4B7pIFG+BhFF9LlFtz/P1y4pblWn3AGs9y3lBx5SKLNf4+rED`
- **남은 위험**
  - Transformers.js는 확인한 바이트를 그대로 실행하지 않는다. 확인한 뒤 같은 URL을 다시 `import`하고, 이때는 보통 HTTP 캐시가 같은 파일을 준다. CDN이 두 요청에 서로 다른 파일을 주는 공격은 막지 못한다.
    - 확인한 바이트를 blob URL로 실행하는 방법도 있다. 하지만 ONNX Runtime이 자기 위치(`import.meta.url`)로 WASM 파일을 찾기 때문에, 실제 브라우저에서 검증하기 전에는 바꾸지 않았다.
  - 라이브러리가 스스로 내려받는 파일은 버전으로만 고정돼 있고, 해시로 확인하지는 않는다. 대상은 ONNX/Tesseract WASM, OCR 워커, 언어 데이터, CLIP 가중치(HF revision `d15189d…`)다.
  - 근본적인 해결은 이 파일들을 서비스 도메인에 직접 올려 해시와 함께 배포하는 것이다(호스팅 결정이 필요하다).
- **버전을 올릴 때**: URL과 해시를 함께 바꾼다. 해시는 다음 명령으로 계산한다.
  - `curl -sS <url> | openssl dgst -sha384 -binary | base64`
  - 앞에 `sha384-`를 붙인다.

1. iPhone Safari에서 앨범 사진(HEIC로 찍은 것) 한 장을 고르고, 오류 없이 들어가는지 확인한다.
2. 옷 두 벌이 같이 찍힌 사진에서 "옷만 자르기"로 한 벌만 남겨 저장한다. 손가락으로 상자를 끄는 게 불편하지 않은지 본다.
3. 상품 목록에서 가진 옷을 하나 등록한다. 색을 건너뛰었을 때 안내가 이해되는지, 옷 화면에서 색을 한 번에 고칠 수 있는지 본다.
4. 설정 → "보관 안내 보기"에서 내용을 확인하고, 사진 포함 백업 파일을 한 번 받는다.
5. 홈 화면에 추가한 뒤, 홈 화면 앱에서 앞에서 넣은 옷이 보이는지 확인한다. 안 보이면 '백업 가져오기'로 불러와 본다.

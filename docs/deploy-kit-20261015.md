# 운영 묶음(Docker) 검증 — 2026-10-15

> 문서 시점: 2026-10-15. 당시의 검토·구현 기록을 보존한 자료입니다. 현재 결정·우선순위·운영 상태는 [최신 문서 목차](README.md)를 확인합니다. 아래의 “지금·완료·다음”은 별도 갱신 표시가 없으면 당시 기준입니다.

운영자 결정: "일단은 집 PC + Cloudflare Tunnel로 하고, 다 완성되면 클라우드를 쓰도록 미리 구성해 둔다." 이 결정에 맞춰 `deploy/`를 만들었다. 사용법은 [deploy/README.md](../deploy/README.md)에 있다.

## 구성과 이유

| 결정 | 이유 |
|---|---|
| 서버·앱을 이미지 하나로 | 앱과 서버는 같은 옷장 형식 검사를 쓴다. 따로 올리면 버전이 어긋날 수 있다 |
| 집 PC와 클라우드에서 같은 compose 파일 | 옮길 때 바꾸는 것은 `.env`와 데이터뿐이다 |
| Cloudflare Tunnel(이름 있는 터널, 토큰 방식) | 공유기 포트를 열지 않는다. VM에서 같은 토큰으로 켜면 주소(DNS)를 바꾸지 않고 옮겨진다 |
| SQLite는 Docker 볼륨, 백업만 폴더 | Windows·macOS 폴더를 직접 연결하면 WAL 잠금을 믿을 수 없다 |
| Litestream 0.5.17로 연속 복제 | 하루 한 번 수동 백업보다 잃는 범위가 몇 초로 줄어든다. 7일 전까지 시점 복구 |
| 서버는 root가 아닌 `node`(1000)로 실행 | 서버가 뚫려도 컨테이너 안 권한이 작다 |
| 이미지 버전 고정(태그+digest) | 같은 파일로 언제 만들어도 같은 이미지가 나온다 |

이미지 버전(2026-10-15 확인):
- `node:22.23.3-bookworm-slim`
- `cloudflare/cloudflared:2026.10.0`
- `litestream/litestream:0.5.17`(2026-08-31 빌드)

Litestream 0.3.13은 0.5 이전의 옛 형식이라 쓰지 않았다.

## 만들면서 찾아 고친 문제

1. **방문자 주소를 못 믿는 문제(서버 코드 수정)**
   - 서버는 시도 횟수 제한을 방문자 주소로 센다. 지금까지는 `127.0.0.1`에서 온 요청의 `CF-Connecting-IP`만 믿었다(cloudflared가 같은 PC에서 돈다고 가정).
   - Docker에서는 cloudflared가 다른 컨테이너라 요청이 `172.x` 주소에서 온다. 그러면 모든 방문자가 터널 주소 하나로 묶인다. 결과적으로 가입은 시간당 10회, 로그인은 15분에 30회를 **서비스 전체가 나눠 쓰게** 된다.
   - 고친 방법: `EOUL_TRUSTED_PROXIES`(고정 IP 목록)를 추가했다. compose는 터널 컨테이너에 고정 주소(`172.31.87.10`)를 주고 이 값을 자동으로 채운다. 자동 배정 범위는 `.128/25`로 나눠 다른 컨테이너가 그 주소를 받지 못하게 했다.
   - 같은 네트워크의 다른 컨테이너나 `localhost:8787`로 들어온 요청의 헤더는 여전히 무시한다.
   - 기존 설정(목록 없음)은 그대로 동작한다.
   - `network_mode: service:eoul`(cloudflared가 서버와 네트워크를 공유)도 검토했다. 코드를 고치지 않아도 되지만, 서버 컨테이너가 다시 시작되면 터널의 네트워크가 끊기는 알려진 문제가 있어 쓰지 않았다.
2. **백업 폴더 권한**
   - Docker가 없는 폴더를 root 소유로 만들어 Litestream(1000)이 쓰지 못했다(`mkdir /backups/eoul.db: permission denied`).
   - 시작할 때 한 번 소유자를 맞추는 `backup-dir`를 추가했다.
   - Litestream을 root로 돌리지 않은 이유가 있다. 서버가 꺼진 사이 Litestream이 먼저 DB를 열면 `-shm` 파일이 root 소유로 생겨 서버가 쓰지 못할 수 있기 때문이다.
3. **`server/.npmrc` 누락**
   - 처음 Dockerfile은 `npm ci` 전에 `.npmrc`를 복사하지 않았다. 그러면 서버 배경 지우기를 켠 빌드에서 onnxruntime이 쓰지 않는 CUDA 파일을 내려받는다.
   - `.npmrc`를 함께 복사하도록 고쳤다.

## 확인하지 못한 것

- **실제 Cloudflare 터널 연결**: 운영자의 Cloudflare 계정과 도메인이 필요하다. 터널 컨테이너가 `eoul:8787`에 닿는 네트워크 경로는 같은 고정 주소의 다른 컨테이너로 확인했다.
- **Windows Docker Desktop**: 다음은 실제 PC에서 확인해야 한다.
  - `D:/eoul-backups` 같은 경로 연결
  - 로그인 시 자동 시작
  - 재부팅 뒤 로그인 전 동작
- **서버 배경 지우기를 켠 이미지 빌드 자체**: 이 환경의 빌드 컨테이너는 외부망에 나가지 못한다. 같은 기반 이미지에서 같은 `npm ci`가 되는 것까지만 확인했다.
- **S3 호환 저장소 복제**(`litestream-s3.yml`): 설정 형식은 Litestream 문서로 맞췄지만, 실제 버킷으로 보내 보지 않았다. 업체별 무료 한도도 확인이 필요하다.
- **종료 순간의 마지막 변경분**: 옮기기 안내는 서버를 먼저 끄고 백업 컨테이너를 잠시 더 두는 순서로 이 문제를 피한다.

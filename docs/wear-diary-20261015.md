# 착용 기록과 결과 반영 — 2026-10-15

> 문서 시점: 2026-10-15. 당시의 검토·구현 기록을 보존한 자료입니다. 현재 결정·우선순위·운영 상태는 [최신 문서 목차](README.md)를 확인합니다. 아래의 “지금·완료·다음”은 별도 갱신 표시가 없으면 당시 기준입니다.

원스톱 계약의 "결과 반영" 구간에서 빠져 있던 두 가지를 구현했다.

1. 실제로 입은 옷을 날짜별로 남긴다.
2. 지난 구매 결과(반품, 안 사기, 보류, 계속 입기)를 같은 상품 옆에 보여 준다.

이 문서는 설계 판단, 저장 형식 변경, 운영 시 주의점을 남긴다.

## 무엇이 바뀌었나

| 화면 | 동작 | 근거 |
|---|---|---|
| 내 옷 상세 | "오늘 입었어요"를 누르면 그날 기록에 추가되고, 다시 누르면 뺀다. "착용 기록 n일 · 최근 날짜"를 보여 준다. | 가장 짧은 입력 경로. 같은 날 여러 벌을 누르면 한 코디로 묶는다. |
| 코디 상세(가진 옷으로 완성) | "오늘 이렇게 입었어요"는 코디 공식 ID와 함께 기록한다. 두 번 눌러도 기록은 하나다. | 코디 단위로 남겨야 다음 추천이 "최근에 입은 조합"을 알 수 있다. |
| 내 옷장 "오늘 뭐 입지?" | 최근 7일 안에 같은 옷끼리 입었다고 기록한 코디는 뒤로 보낸다. 숨기지 않으며, 순서를 바꾼 이유와 기록 날짜를 보여 준다. | 매일 같은 코디를 다시 권하지 않기 위해서다. 사용자의 기록에만 근거한다. |

| 부족한 옷 계획 ② 겹치는 옷 | 같은 종류·같은 색 옷마다 "착용 기록 n일 / 착용 기록 없음"을 보여 준다. | 겹치는 옷 중 실제로 입는 옷을 구분한다. |
| 구매 기록 "오늘 입었어요" | 계속 입기로 한 구매 옷은 착용 기록에도 하루 한 번 남긴다. 구매 기록의 착용 횟수는 기존처럼 누를 때마다 센다. | 두 기록이 따로 놀지 않게 한다. |
| 부족한 옷 계획 상품 / 상품 상세 | 같은 상품의 내 지난 기록을 보여 준다. 예: "반품 기록 · 사유 사이즈 · 옵션 L · 핏 직접 기록: 작게 맞음 · 날짜". "기록 보기"로 해당 기록을 연다. | 반품한 상품을 아무 설명 없이 다시 권하지 않는다. |
| 기록 정리 | 착용 기록 n/1000개를 보여 주고, 달 단위로 골라 두 번 눌러야 지운다. | 착용 기록은 보유 상태와 관계없어서 지워도 옷장은 그대로다. |

## 하지 않는 것 (계약 유지)

- **기록이 없는 옷을 "안 입은 옷"으로 판정하지 않는다.** 화면 문구는 "착용 기록 없음"과 "(기록하지 않았을 수도 있어요)"로 쓴다. 처분 권유나 구매 판단에 쓰지 않는다.
- **지난 반품·안 사기·자유 입력 이유로 상품 순위를 조용히 낮추거나 숨기지 않는다.** 상품을 숨기는 것은 사용자가 고른 "다시 추천하지 않기"뿐이다.
- 핏 기록은 사용자가 직접 남긴 값이다. 사이즈 예측이나 가상 착용 정확도의 근거로 쓰지 않는다.
- 예시 옷장에는 착용 기록을 남기지 않는다. 검증기는 `demo:true`이면서 기록이 있는 상태를 거절한다.
- 착용 기록을 자동으로 지우지 않는다. 1000개에 도달하면 새 착용 기록만 막는다. 이때도 옷·구매 기록 저장은 막지 않으며(`wearsFull`과 `full`을 분리), 정리 화면으로 안내한다.

## 저장 형식: schema 6

```
wears: [{ id: 'w_…', date: 'YYYY-MM-DD', garmentIds: [1..12개], lookId: 코디 공식 ID | null, note: ≤200자, at: ISO 시각 }]
```

- `date`는 이 기기의 달력 날짜다(UTC가 아니다). 입은 날의 기준이 사용자의 하루이기 때문이다.
- 검증은 엄격하다.
  - 키 6개 외의 키는 거절한다.
  - 날짜는 실재하는 2000-01-01 이후 날짜만 받는다.
  - 옷 ID는 기록 하나 안에서 중복될 수 없다.
  - 메모에는 제어 문자를 넣을 수 없다.
  - 기록 ID는 서로 겹칠 수 없다.
- 옷 ID가 옷장에서 빠져도 기록은 남는다. 화면에는 "목록에서 뺀 옷"으로 표시한다.
- 이전 형식은 다음과 같이 변환한다. 변환은 순수 함수이고 기존 값은 그대로 유지한다.
  - schema 5 → 6: `wears: []`를 추가한다.
  - schema 3·4 → 6: 구매 기록 변환과 함께 한 번에 바꾼다.
- 앱을 처음 열 때 `schema < 6` 기록을 한 번 변환해 저장한다(이전 동작과 같다).
- 구매 기록 용량 예산(600KiB, 보유 정리 680KiB)은 schema 5 이상에 적용한다. 착용 기록은 전체 850,000바이트 한도 안에서 센다. 기록 1000개는 대략 150KB 안팎이다(추정).

### 동기화·운영 주의점

- **서버는 현재 형식(schema 6)만 받는다.** schema 5 앱이 올리면 `old-app`("앱을 새로고침한 뒤 다시 저장해 주세요")으로 거절한다. 이전 앱이 착용 기록이 없는 상태로 계정 자료를 덮어써 기록을 잃는 일을 막기 위해서다.
- 계정에서 받은 자료가 schema 5이면(이전 앱이 올린 자료) 이 기기에서 6으로 바꾼 뒤 적용한다. 계정 쪽을 고르면 착용 기록은 계정 자료(빈 기록)로 바뀐다. 이것은 "어느 쪽을 쓸까요" 선택의 결과이며, 자동으로 합치지 않는다는 기존 원칙과 같다.
- schema 6을 이전 앱이 읽으면 "지원하지 않는 옷장 형식"으로 거절하고 원본을 보존한다. 배포할 때는 서버와 앱을 함께 올린다.
- 백업 파일(binary v2)에는 착용 기록이 그대로 들어간다. 복원 경로는 바뀌지 않았다.

## 검증

- 단위·번들 테스트: `app/test/wear-log.test.mjs` 9개, `app/test/wardrobe-plan.test.mjs`의 지난 기록 2개.
  - 형식 검증, 5→6 변환, 예시 옷장 거절, 같은 날 중복 방지, 토글.
  - 1000개 한도에서 다른 저장은 막지 않음.
  - 일수 기준 통계, 최근 코디 뒤로 보내기(숨기지 않음).
  - 새로고침 후 유지, 미래 날짜 거절(저장 오류로 표시하지 않음), 두 번 눌러 삭제.
  - 겹치는 옷의 착용 기록, 달 단위 정리, 구매 기록 착용과의 연동.
  - 서버가 schema 6만 받는지.
- 기존 schema 5 단정이 있던 테스트는 현재 형식(6)을 확인하도록 고쳤다. schema 3·4 fixture는 착용 기록 키를 빼도록 고쳤다.
- 실제 Chromium(390×844)에서 다음을 확인했다.
  - 계획의 반품 기록 줄, 겹치는 옷의 착용 기록.
  - 어제 입은 코디가 첫 번째에서 밀려남.
  - 착용 기록 시트의 요약·폼·목록, 옷 상세의 토글.
  - 새로고침 후 schema 6 저장, 가로 넘침 없음, 페이지 오류 없음.
- 이 확인에서 실제 버그 두 개를 찾아 고쳤다.
  - 옷 하나를 고르면 폼이 접혔다(회귀 테스트로 수정 전 실패를 확인함).
  - 체크 목록 배치가 깨져 있었다.

**검증하지 않은 것**

- 실제 휴대폰: iOS Safari의 날짜 입력, Android Chrome.
- 장기 사용 시 기록 용량.
- 착용 기록이 쌓였을 때 추천이 실제로 더 쓸 만한지.
- Acloset 대비 체감.

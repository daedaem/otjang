## 요구와 이번 변경

사용자 결정은 입력 부담을 줄이면서 실제 내 옷을 바탕으로 부족한 아이템의 브랜드·품명·가격·이유를 추천하는 것이다. Claude의 새 앱을 기본으로 삼고, 기존 앱의 기능을 모두 다시 펼치지 않는다. 사업·시스템 설계는 Claude Opus 5.5와 검토하고 구현은 Codex에서 이어간다. 사진 등록, 저장 안전성, 개발 이유와 한계 기록은 이 요구의 일부다.

최신 Claude 소스를 별도 임시 디렉터리에 읽기 전용 기준으로 추출해 Node 22에서 테스트 20개와 단일 HTML 빌드를 실행했다. 상품 배열은 918개, 브랜드 115개, 종류 68개, 스타일 8개, 코디 공식 32개다. README의 종류 69개·공식 33개 표기보다 실행한 배열을 기준으로 비교한다. 상품 가격·재고를 이번 비교에서 판매처에 다시 조회한 것은 아니다.

제품 흐름상 최신 Claude의 장점은 3개 탭, 여러 스타일·선호 브랜드, 실제 상품을 보유 옷으로 등록, 사진·색상·브랜드가 있는 개별 옷, 가진 옷만의 코디와 한 벌만 사면 되는 코디다. 기존 `core-flow`는 7개 화면과 구매·반품 후속 기록, 소수 상품 검토, 사진·상세 속성 확인을 갖췄지만 기본 흐름이 복잡하다. 최종 권고는 최신 Claude의 사용자 흐름에 검증한 저장·복구와 구매 후 기록을 통합하는 것이다. 사용자가 이 비교만으로 새 설계 전체를 승인했다고 기록하지 않는다.

최신 Claude에서 직접 확인한 개선 필요 사항:

- 최신 Claude는 같은 `eoul:v1` 키에 `v:2`, `styles`, `closet` 등을 저장한다. 본 브랜치의 구버전 이전 파서는 그 형식을 지원하지 않아 원문을 보존하고 중단한다. 최신 사진은 별도 `eoul` DB에 있으므로 `eoul-wardrobe-v2`와의 명시적 변환 검증 없이 가져오기 완료라고 말하지 않는다.

이 차이를 확인한 뒤 최신 Claude를 통합했다는 이름으로 이전 기준 빌드를 공개 미리보기에 덮어쓰지 않았다. 현재 공개 `instant-wardrobe`의 SHA는 별도 `build-info.json`을 확인한다. 새 사진·백업 구현은 소스 브랜치와 PR #11에서 검토할 수 있다.

이번 사용자 흐름은 다음과 같다.

1. 처음 열면 예시 6벌로 상품과 코디를 본다.
2. `내 옷으로 바꾸기` 또는 `옷 한 벌 추가`를 누른다.
3. 종류를 하나 고르고 저장한다. 사진과 이름은 선택이다.
4. 실제 옷 사진·이름을 옷장과 코디에서 본다. 같은 종류 두 벌도 서로 다른 옷이다.
5. 옷을 눌러 사진·종류·이름을 고치거나 두 번 확인하여 삭제한다.

첫 개인 저장이 성공할 때 예시 보유 정보가 사라진다. 실패나 편집 취소만으로는 예시가 비워지지 않는다. 상품 사진을 개인 사진으로 복사하지 않는다. 추천은 종류와 편집된 코디 공식이며 사진 분석 결과가 아니다.

## 선택한 설계와 대안

| 결정 | 선택 이유 | 선택하지 않은 대안 |
|---|---|---|
| 실제 옷별 ID + 종류 참조 | 같은 셔츠 두 벌, 사진, 나중의 구매 기록을 구별한다 | 종류 ID만 보유 목록에 저장 |
| 사진·상태를 같은 IndexedDB 트랜잭션으로 저장 | 한쪽만 남는 부분 성공을 막는다 | 사진은 IDB, 상태는 localStorage로 나누어 성공 처리 |
| 먼저 파일을 검증하고 트랜잭션을 시작 | 해시 계산 중 트랜잭션이 자동 종료되는 문제를 피한다 | 트랜잭션 안에서 임의의 async 작업 대기 |
| revision 비교 후 쓰기 | 오래 열린 탭이 다른 탭의 옷을 덮어쓰지 않는다 | 마지막 쓰기가 무조건 이김 |
| `.eoul` 단일 바이너리 백업 | 큰 사진을 모두 base64 문자열로 만들지 않는다 | 200장 전체를 하나의 거대 JSON 문자열로 만들기 |
| 알려지지 않은 필드·형식은 보존하고 쓰기 중단 | 미래 버전/손상 자료를 빈 옷장으로 오인하지 않는다 | 모르는 필드를 버리고 자동 저장 |
| 확인된 삭제·교체에서 마지막 사진 참조만 정리 | 공유 사진과 이전 자료를 지우지 않는다 | 앱을 열 때 참조 없는 사진 자동 삭제 |

이 구현은 AI가 작성했고 프로젝트 소유자가 설명·검토할 수 있도록 코드 위치와 검증 범위를 공개한다. 추천 정확도나 사용자 반응을 측정했다는 뜻은 아니다.

## 코드와 저장 계약

- `app/src/wardrobe.js`: schema 2 검증, 실제 옷 모델, 예시 보유 목록, 구버전 이전, 추천용 보유 종류 도출.
- `app/src/wardrobe-store.js`: IDB 열기/읽기/비교 후 쓰기, Blob 해시, 백업·복원 파서, 원문 회수.
- `app/src/garment-photo.js`: 사용자가 고른 JPG·PNG·WebP를 브라우저에서 축소하여 JPEG로 변환. 네트워크 호출 없음.
- `app/src/main.js`: 편집 초안, 지연된 작업 취소, 실제 저장 성공 뒤 UI 변경, 백업 확인 화면, 구버전 변경 알림.
- `app/src/engine.js`: 보유 매칭과 설명에서 실제 garment ID를 사용. 한 코디에서 같은 ID를 두 역할에 쓰지 않는다.

DB 이름은 `eoul-wardrobe-v2`, IDB 버전은 1이다. `records` store의 `current`에는 `{revision,state}`를 둔다. `photos` store는 `p_<SHA256>` → JPEG Blob이다. `revision`은 상태의 정본이 변경될 때만 증가한다. 탭/검색어/편집 초안은 정본이 아니다.

`state`에는 schema, 취향, 예시 여부, 예시 선택 목록, garments, 찜·숨김 ID, 마지막으로 확인한 `eoul:v1` 원문의 SHA256이 있다. `legacyBaseline`은 마지막으로 확인한 구버전의 owned/saved 목록이고, `legacyDismissed`는 새 앱에서 삭제하거나 찜을 취소한 구버전 ID 목록이다. `garment`에는 고유 id, kind, gender, slotId, source(user/legacy), photoId, 선택 label, attrs(null), createdAt이 있다. 일반 사진 등록은 `slotId:null`, `attrs:null`로 보관한다. 색이 없는 셔츠를 흰 셔츠나 파란 셔츠라고 이름 붙이지 않는다. 사용자가 기존 상세 종류 카드를 직접 고른 때만 그 slotId를 기록한다.

최대 200벌, 사진 입력 25MB 이하, 저장 사진은 긴 변 최대 1024px·JPEG 800KB 이하다. 실제 브라우저 할당량은 이보다 작을 수 있다. 용량 초과 시 성공으로 표시하지 않고 초안을 유지한다. 이 수치는 지원 상한이며 모바일 성능 보장이 아니다.

## 저장 실패·충돌·복구

사진 해시와 형식은 IDB 쓰기 전에 확인한다. 하나의 readwrite 트랜잭션에서 현재 revision을 읽고, 사진 put → 필요한 모든 사진 존재 확인 → 마지막 참조가 없어진 사진 삭제 → 상태 put 순으로 요청한다. `oncomplete` 이후에만 성공으로 표시한다. 어떤 요청이나 검증이 실패해도 같은 트랜잭션의 변경을 되돌린다.

충돌 시 입력 초안과 Blob을 유지한다. `입력 유지하고 최신 옷장 불러오기`는 정본을 다시 읽는다. 새 옷 초안은 최신 목록에 추가할 수 있다. 기존 옷 수정은 편집 시작 당시의 해당 옷과 비교하여 다른 탭이 이미 바꿨으면 다시 확인하게 한다. 이 비교를 생략하고 최신 revision만 붙여 덮어쓰면 안 된다.

손상/미지원 자료는 기존 상태를 쓰지 않는다. `저장 원문 받기`는 검증 전 records JSON 필드와 사진 store의 Blob(참조 없는 사진도 포함), 원래 localStorage 문자열을 `.eoul-recovery`에 담는다. 이는 개발 지원용이며 일반 복원에서는 거부한다. IDB 자체를 열 수 없는 경우, 더 높은 DB 버전, JSON으로 보존할 수 없는 임의의 외부 변조 값은 자동 복구 범위가 아니다. 원문 보존 상태에서 원인을 점검한다. DB를 지우는 방식으로 우회하지 않는다.

## 백업 파일 형식

`.eoul` 파일은 12바이트 헤더, UTF-8 JSON manifest, 사진 Blob 구간을 순서대로 연결한다.

- 0~7: ASCII `EOULBK02`
- 8~11: manifest 바이트 수, unsigned 32-bit little endian
- 그다음: `{format:'eoul-wardrobe-backup',version:2,exportedAt,state,photos}`
- photos의 각 행: `{id,type,offset,bytes}`. offset은 사진 영역 첫 바이트부터의 위치이고 연속 구간만 허용한다.
- 사진 영역: 각 JPEG의 원래 저장 바이트. base64·압축·외부 URL을 쓰지 않는다.

manifest 상한은 1MB이고, 각 사진은 `Blob.slice()`로 최대 800KB만 읽어 SHA256을 순서대로 검사한다. 형식·중복 ID·누락·추가 바이트·잘못된 구간·해시 불일치를 거부한다. 파일 전체를 `text()`/`arrayBuffer()`로 읽지 않는다. 검증 성공 후에도 사용자가 현재 옷장을 교체하겠다고 눌러야 저장한다. 소형 이전 JSON 백업(v1, 10MB 이하) 파서는 호환용으로 남긴다.

`.eoul-recovery`도 같은 프레임을 쓰지만 format은 `eoul-wardrobe-recovery`, manifest에는 records와 legacyRaw가 있다. 일반 백업과 구분하고 원문을 보존한다. 개발자가 사진을 추출할 때도 manifest 크기·구간·해시를 먼저 검사하고 별도 폴더에 쓴다.

## 이전 버전과의 경계

원래 `eoul:v1`은 읽기 전용으로 유지한다. 첫 이전의 ID는 `legacy_<slotId>`로 결정적이며, 실제 사진은 없으므로 null이다. 원문이 바뀌면 앱 시작 시 알림을 띄운다. 가져오기 확인 화면은 마지막으로 확인한 구버전 목록 이후 추가된 종류와 찜을 보여 준다. `legacyDismissed`와 현재 보유 ID도 대조하므로 새 앱에서 지운 옷·찜을 다시 추가하지 않는다. 사용자가 이미 고친 legacy ID, 현재 사진·취향도 덮어쓰지 않는다. `이번 변경 건너뛰기`는 개인 옷장을 유지하면서 비교 기준과 원문 해시만 갱신한다. 옛 버전의 삭제를 새 옷장에 전파하는 양방향 동기화는 아니다. 확인한 추가 반영 또는 건너뛰기와 비교 기준·해시 저장은 한 트랜잭션이다.

기존 `core-flow` 앱의 사진 옷장은 다른 스키마다. 이번 이전이나 `.eoul` 파서가 그 JSON을 지원한다고 표현하지 않는다. 이후 별도의 변환·원본 보존 검증이 필요하다.

## Claude 검토와 처리

2026-10-14 기존 ‘아이디어를 플랫폼으로 개발’ 대화에서 Opus 5.5 높음으로 검토했다. 처음에는 구현 설명을, 이후에는 IDB 저장의 실제 발췌와 테스트 범위를 전달했다. Claude는 저장소 전체나 기기를 직접 실행하지 않았다고 명시했다. 독립 전체 코드 리뷰나 모바일 검증으로 기록하지 않는다. 개인 사진·대화 원문은 저장소에 올리지 않는다.

채택: 실제 옷/사진을 먼저 연결, 저장 실패 무시 제거, 추천 근거 구분, 구매 기록은 그다음. 백업 메모리 부담 지적에 따라 JSON 전체 인코딩 대신 바이너리 파일로 바꿨다. 옛 앱 쓰기가 갈라질 수 있다는 지적에 따라 원문 해시와 명시적 추가 가져오기를 넣었다. 후속 설명 검토에서 제기된 삭제 기록 재등장 가능성은 코드를 확인한 뒤 구버전 비교 기준·삭제 기록·건너뛰기로 보완하고 회귀 검사를 추가했다. 사진 존재를 저장 트랜잭션 안에서 다시 확인하는 반례도 검사한다. iOS에서 사용자 정의 백업 확장자를 선택하지 못할 가능성에 대비해 파일 선택기의 확장자 필터를 제거했으며 실제 파일 형식 검증은 유지한다. 실제 iOS 선택 동작은 미검증이다.

수정 요청 후 Claude가 철회한 안: 파일럿 미실행만으로 사업 준비도를 60점에 제한, 종류 선택 하나만 있어도 UX 고득점 금지, 시작할 때 사진 자동 정리. 준비도와 실제 사업 검증을 나누고, 입력 동작과 소요시간을 측정하며, 사진 삭제는 확인된 동작 안에서만 한다.

공유 origin 지적은 운영 과제로 남긴다. IndexedDB는 경로가 아닌 origin 단위이며 현재 GitHub Pages의 다른 경로와 보안 경계가 분리되지 않는다. 이 사실만으로 사진 유출이 발생했다고 단정하지 않는다. 전용 서비스 origin 및 같은 origin의 다른 코드·서비스 워커를 확인하기 전에는 정식 서비스 격리를 완료했다고 보고하지 않는다. DB 이름을 바꾸는 것만으로 해결된다고 표현하지 않는다. 근거: [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [Blob.slice](https://developer.mozilla.org/en-US/docs/Web/API/Blob/slice).

## 검증과 미완료

Node 22.23.2, `cd app && npm test`, `node tools/build.mjs`, `git diff --check`를 사용한다. 저장 테스트용 `fake-indexeddb@6.2.5`만 추가했고 배포물에는 포함하지 않는다.

현재 41개 자동 검사 범위: 추천/검색/정확한 상품 고정, 예시 분리, 동일 종류 두 벌, 사진·이름 재시작 유지, 실패 시 초안 유지, 지연 작업 취소, 사진·메타데이터 동시 rollback, 공유 사진 참조, 두 탭 충돌, 명시적 복원, 변조/누락/미지원 자료 보존, 구버전 변경 감지 및 기존 사진 보호, 삭제한 옷·찜의 재등장 방지와 건너뛰기 유지. 최대 크기 검사는 JPEG 헤더를 가진 합성 바이트 200장×800KB로 바이너리 백업→검증→별도 IDB 복원을 수행한다. 실제 사진 디코딩/화질·휴대폰 메모리·속도를 입증하는 검사가 아니다.

실제 휴대폰 렌더링·터치·초점, 카메라·HEIC·EXIF/GPS, iOS 보관 정책·사설 모드, 장기 데이터 유지, 실제 상품 이미지 표시와 최신 가격·재고, 전용 origin은 미확인이다. 이전 자동 승인 검토에서 앱 브라우저 E2E가 허용되지 않았으므로 다른 브라우저/헤드리스/파일 URL로 우회하지 않았다. 이번 자동 검사는 Node와 IDB 대역에서 수행했다.

다음 핵심 구현은 판매처 방문과 실제 구매를 구분하고, 사용자의 ‘샀어요’가 상품 참조를 가진 실제 옷과 구매 기록을 함께 만드는 것이다. 착용/반품 결과는 그 구매와 연결한다. 3D·가상 착용과 기존 사진 옷장 가져오기, 사업 공급 경로, 실기기 검증은 별도 미완료 항목으로 유지한다.

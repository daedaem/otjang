# R22 B5a — 코디 반응 읽기·텍스트 AI 계약

기준 master는 B4 #82를 최종43348b1의 CI11개·실제174개 두 작업/Node316개·미해결 검토0 확인 후 병합한 `615ff24835e7be737889f7cfb9230c94b04f5bf6`이다. B5a는 화면보다 먼저 입력·보존·AI 응답 경계를 나눈 기반 후보다. 반응 저장 controller·코디 카드·실제 UI는 다음 B5b이며 B5 전체 완료가 아니다. 실물 기기·블라인드20·활성 배포·사업 효용을 자동 검사로 채우지 않는다.

## 왜 먼저 나눴는가

R2대로 최종 순위와 이유는 AI가 정한다. 기존 종류·색 공식은 후보와 차원별 사실을 만들 뿐이다. 실제 내 옷을 먼저 필터링한 `closetOutfits({ownedOnly:true})`로 후보를 만든 뒤, 중복 구성/체험용을 제외한다. 기존 인자가 없는 코디 수와 기본 화면 동작은 유지한다. 최대8조합/24벌/조합당12벌에서 비교하며 전체 후보 수와 이번 요청 수를 구분한다.

`buildOutfitRequest`는 ID·종류·직접 기록한 이름·색·profile·반응 집계만 고른다. 사진ID/파일/URL/상품 가격·브랜드 후보/대화 이력은 넣지 않는다. profile 출처와 AI 확인 전 표시를 보존한다. 디테일은 처음6개와 실제 생략 수(최대14)를 보내고, 원본 profile은 바꾸지 않는다.28KB를 넘으면 뒤의 조합과 사용하지 않는 옷을 줄이며 그 수는 반환된 요청에 드러난다. 질문 조건이나 속성 값을 바꿔 맞추지 않는다.

## 반응의 의미와 보존

`eoul-d12-hang:outfit-reactions:v1`의 `{v:1,reactions}`는 기존 `validateReactions`의 최대500개·ID·옷ID·좋아요/별로·이유·상황·시각을 따른다. 삭제된 옷ID의 과거 반응도 읽기에서 버리지 않는다. 미래/손상·중복 JSON 이름·잘못된 반응은 원문을 거절하고, BK에서 보관 전용 원문으로 분류한다. 새 키의 사전 검증·출처·조건부 건수를 더했으며 형식2·전체5MB·복원/undo 알고리즘은 그대로다.

`tasteSummary(...,{garmentIds})`는 옷ID 하나라도 겹치는 과거 조합의 집계다. 동일 조합만의 평가나 사람 수가 아니다. 서버가 만든 사실 줄·프롬프트·코어의 `reactionBasis`에 그 범위를 표시하며 B5b 화면도 같은 문구를 사용해야 한다. 이번 후보가 이미 평가받았다고 설명하면 안 된다.

## 서버 경계와 최종 응답

새 `/api/rank` task는 `outfit_rank`다. 인증·공유 D1 원자 한도·최대32KB·모델·max_tokens2000·재시도0·시간 제한은 기존 경로를 따른다. 유효하지 않은 사진 필드/미디어 주소·슬롯/종류 충돌·profile·현재 후보에 없는 ID·중복 구성·부풀린 반응 수는 제공자 호출/한도 예약 전에 거절한다. 클라이언트는 프롬프트나 모델을 고르지 못한다.

서버가 `outfitFactLines(outfitFacts(...))`, 출처 포함 `profileFactLines`와 겹치는 옷의 과거 반응 범위를 다시 만든다. 모르는 세부 종류·색을 격식/조화 적합으로 바꾸지 않는다. 이름이 같거나 서로 포함돼 대상이 애매한 옷은 속성 대조에서 건너뛴다. 이는 놓치는 주장이 있다는 뜻이며 ‘답 전체 검증’이 아니다.

AI 응답은 제출된 조합ID 전부를 정확히 한 번 포함해야 한다. 누락·추가·중복·알 수 없는 필드·미디어 링크는 성공한 AI 순위로 쓰지 않는다. 반환된 순위/이유는 그대로 두고 `attributeClaimCheck`의 일부 속성 대조 줄과 한계를 아래에 붙인다. 답을 고쳐 쓰거나 다시 호출하지 않는다. 연결 실패를 엔진 최종 순위로 대체해 AI라고 표시하지 않는다.

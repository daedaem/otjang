# 계정 로그인·대표 단일 관리자 연결

2026-10-29. [작업 #134](https://github.com/daedaem/otjang/issues/134), 구현 담당 Codex 어울 개발 한 곳. 기준 mastera3ef4e9이며 기존 개인 프로젝트의 미정리 변경은 건드리지 않는다.

## 사용자 결정과 이번 범위

대표가 공용 접속 비밀번호를 먼저 입력하는 입구 대신 계정 로그인 후 이용하고 본인 계정 하나만 관리자가 되도록 요청했다. 후속 응답으로 **이메일·비밀번호 먼저 사용**을 선택했다. 카카오·Google은 후속이며 이번 방식에는 제공자 키·메일 발송 서비스·새 비용이 필요하지 않다. 이메일은 로그인 ID이고 메일 소유 인증/발송 성공과 다르다.

일반 입구를 이메일 로그인으로 바꾸되 가입은 기존 초대 범위를 유지한다. 상품/사진 권리나 일반 공개 준비를 이 요청으로 완료 처리하지 않는다. 공개 커뮤니티 모드·AI 한도·원래 기기 자료·사진/백업·회원별 보관은 유지한다. 실제 관리자 계정은 본인이 새 인증정보를 직접 입력·제출해야 하며 아직 만들지 않았다.

## 설계와 선택 이유

- `MEMBER_APP_MODE=accounts`에서 로그인 없는 앱 문서 요청은 `/_member/signin`으로 간다. 로그인 페이지가 제품/개인 자료를 공개하지 않으며 API·자산은 인증 뒤에만 제공한다. 기존 invite/비활성 모드는 복귀 경로로 보존한다.
- 관리자는 COMMUNITY_DB의 `app_primary_admin` 단일 행(slot1)으로 정한다. 최초 가입자, 화면 role, 임의 이메일이나 공개 문의 주소를 권한 근거로 삼지 않는다. 기존 본인 인증을 통과한 요청만 최초 새 계정을 연결한다. 고유 제약의 plain INSERT와 계정 삽입을 같은 D1 batch로 묶어 경쟁/중간 실패가 두 관리자나 고아 계정을 만들지 않는다.
- 기존 본인 인증이 남아 있으면 최초 `/_private/admin-setup` 양식에 바로 들어간다. 없으면 그 초기 연결에만 기존 본인 인증을 요구한다. 대표가 이메일·새 비밀번호·확인을 직접 정하고 제출한다. 메일 주소는 HMAC 식별값, 비밀번호는 PBKDF2 해시/소금만 저장한다. 문의용 이메일을 로그인 ID로 자동 선택하지 않는다.
- 관리자 연결 후에는 원래 공용 비밀번호/본인 쿠키를 앱 관리자 로그인으로 사용하지 않는다. 정상 이메일 계정의 서버 세션과 단일 관리자 행을 함께 대조한다. 공개 커뮤니티의 운영 권한도 같은 계정을 따른다. 서버 role 조회 실패는 접속 거절이며 기존 비밀번호 권한으로 조용히 돌아가지 않는다.
- 연결된 관리자 계정의 내부 id를 기존 `owner` 저장 범위/커뮤니티 소유자로 해석한다. 원래 localStorage/사진 DB/기록/백업을 옮기거나 새 회원에게 복사하지 않는다. 일반 회원은 기존 m-태그 보관 범위, 사진 CSP·AI 하루10회/전체 한도를 그대로 쓴다. 표시용 meta 값은 권한 검증을 대신하지 않는다.
- 관리자의 내 계정·로그아웃을 제공한다. 로그아웃은 실제 회원 세션을 서버에서 폐기하고 두 종류 쿠키를 지운다. 마지막 관리자 계정의 셀프 삭제는409로 막고 설정 복귀 시에도 보호한다. 계정 삭제 검사 중 없던 관리자 표를 만드는 부작용은 읽기 전용 존재 확인으로 보완했다.
- 계정/관리자 연결은 성공했으나 마지막 세션 생성만 실패하면201/loginRequired로 일반 로그인을 안내한다. 이미 만든 계정을 다시 만들거나 관리자 행을 지우지 않는다. 이메일·비밀번호로 다시 들어갈 수 있음을 합성 오류 주입으로 검사한다.
- 신규 관리자 양식은 요청 중 입력/제출을 잠그고 실패하면 입력을 남긴다. 정상 관리자 로그인은 기존 owner 활성 표식을 사용하고, 일반 회원 전환 때 오래 열린 본인 탭이 쓰지 못하게 하는 보호도 유지한다. 비밀번호 입력/값은 로그·Git·분석 이벤트로 보내지 않는다.

## 운영자 표시 정보

검토 채팅의 실제 사용자 응답을 읽어 운영자명/문의 주소 표시 승인을 확인했다. 값은 Git 코드·문서에 기록하지 않고 COMMUNITY_OPERATOR/COMMUNITY_CONTACT 런타임 변수에만 넣었다. Cloudflare 저장 후 실제 앱의 문의 줄과 약관/개인정보 책임자 표시를 확인했다. 개인 연락처가 있는 실제 캡처는 로컬 검증 자료에만 둔다. 공개 모드·새 계정·관리자 권한·약관 동의를 이 표시 정보로 승인하지 않는다. keep_vars를 유지하며 새 배포 후에도 두 값의 보존을 확인한다.

## 검증 상태

초기 단일 관리자4개를 실패 커밋29223d6에 먼저 남겼다. 현재 전체 Node532/532·skip0, TypeScript/Vite99파일이 통과했다. 실제 처리기/서명·PBKDF/메모리 SQLite로 일반/관리자 구분, 기존 소유권, 옛 비밀번호 차단, 경쟁·롤백, 세션 실패 후 재로그인, 로그아웃/마지막 관리자 삭제 보호와 공개 커뮤니티 권한을 대조한다. 기존 config 검사는 새 사용자 결정의 정확한 accounts 값으로 바꾸고 전용 DB 분리/회원 한도 검사를 더했다. 기존 삭제 실패의 원문 비교 기대는 유지했다.

새 브라우저6개가 두 엔진에서 통과(16.2초)했다. 실제 Worker와 합성 HTTPS/브라우저 쿠키를 쓰며 본인 옷장 원문·2px 합성 사진 digest 보존,503 입력 보존/중복 잠금, 관리자 로그아웃·재로그인, 일반 회원 빈 옷장·이전 탭 잠금을 확인했다. 최초 본인 인증 경로2개를 더한 새8개와 기존 계정/역할·커뮤니티·운영 점검을 합친 마지막70개도 두 엔진에서 모두 통과(1.7분)했다. 역할/기기 자료/사진의 원문 검사를 삭제하지 않았으며 이전 커뮤니티74개와 검사 파일 범위가 다르다. 최종 전체 원격 CI는 별도다.

QA 한계도 구분한다. WebKit의 route.fulfill은303을 지원하지 않아 Node에서 실제303/목적지를 검사하고 브라우저 QA에서는 같은 출처 HTML 이동으로 다음 페이지를 잇는다. 외부 이동은 거절한다. 합성 HTTPS의 쿠키가 WebKit 요청 메타데이터에서 빠지는 경우는 그 브라우저의 동일 출처 쿠키 저장소 값을 전송한다. 인증 결정은 가짜로 대체하지 않고 실제 서명/DB를 통과시킨다. 남은 요청은 unrouteAll(wait)로 끝낸다. 최초 전송/아이콘 이름 선택 오류를 제품 실패나 실물 기기 성공으로 쓰지 않으며 timeout/retry/skip 완화는 없다.

## 배포와 본인 입력 단계

현재는 코드/로컬 QA 후보이며 최종 PR/CI·실제 계정 모드 배포 전이다. 실제 운영자 표시 정보는 이미 저장·화면 확인했고, 일반 계정과 관리자 연결은 실제 완료로 쓰지 않는다. 마지막 head 검사·리뷰 뒤 기존 Worker에 배포하고 정상 로그인 입구·관리자 최초 연결 양식을 확인한다. 기존 본인 인증이 살아 있는 검증 탭에 양식을 준비해 본인이 이메일/새 비밀번호/확인을 직접 입력·제출하도록 넘긴다. 새 인증정보 입력과 관리자 권한 연결의 최종 제출을 도구가 대신하지 않는다.

이메일 발송·소유 인증/자동 비밀번호 찾기, 카카오·Google 실제 설정/응답, 실물 폰, 상업용 상품/날씨 권리·일반 공개는 후속이다. 이 한계를 일반 서비스 완성으로 바꾸지 않는다. 유료 AI 추가 호출/개인 사진 외부 전송은 없다.

## 복구·운영 주의

- COMMUNITY_DB와 app_primary_admin/member_accounts/member_sessions를 임의로 초기화하거나 다른 DB로 바꾸지 않는다. 원래 RANK_DB/CROWD_DB와 내부 서명 seed/Secret도 보존한다. 새 배포가 실제 회원·자료 이관이 아니다.
- 최초 연결 전 오류는 기존 본인 인증으로 다시 양식에 들어간다. 계정은 만들어졌고 세션만 실패한201이면 같은 이메일·비밀번호로 로그인한다. 관리자 행을 지워 다시 시작하지 않는다.
- 자동 비밀번호 찾기는 아직 없다. 관리자가 인증정보를 잊었을 때 이메일/문의 주소만으로 권한을 주지 않는다. Cloudflare 계정 소유자가 기존 확인된 비공개 버전a3ef4e9·회원 앱 off/본인 인증 session/커뮤니티 private 설정으로 안전하게 되돌려 기존 본인 자료에 접근/백업하는 비상 복귀와, 새 계정의 비밀번호 복구는 별개다. 이전 코드에는 새 단일 관리자 보호가 없으므로 비상 복귀에서는 회원 로그인을 열지 않는다. 바인딩/DB/키를 그대로 두며 새 관리자 행 생성이나 계정 삭제로 해결하지 않는다. 계정 복구 구현·본인 확인을 마친 뒤에만 accounts로 다시 전환한다.
- 실제 계정 생성/새 비밀번호 변경·권한 회복은 본인이 인증정보를 입력·제출하고 실제 결과를 확인한 경우만 완료로 기록한다.

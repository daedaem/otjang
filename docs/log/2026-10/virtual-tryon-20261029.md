# 내 사진 가상 착용: 핵심 흐름 구현과 실제 검증 경계

## 결정과 현재 상태

대표가 후루츠패밀리 Fit check 캡처를 제시하며 “저희도 저정도는 해야죠 저희는 저게 핵심기능”이라고 직접 요청했다(2026-10-29). 사진 선택→옷 입히기→원본과 비교를 핵심 구매 흐름으로 재개한다. 이전 무료 로컬 FASHN1.5 결과 불만/영상 보류를 정지 착용 기능 전체의 영구 보류로 적용하지 않는다. 영상은 정지 사진 품질을 확인한 뒤다. 원스톱 추천·옷장 선택 입력·내 옷 비교·구매·기록이라는 목표는 유지한다.

작업 #141, 담당 Codex 이 채팅 한 곳, 브랜치 `codex/virtual-tryon-20261029`. 구현 코드3c933cc와 승인 후 병합한 샘플 기록을 보존한26bc012를 기준으로 확인했다. 시작 master052e3ff, 새 master48e8dd4를 통합했다. #140은 처음 병합이 자동 승인 검토에서 거절된 뒤 대표가 **PR #140 병합 허용**을 회신했으며, 같은 head7fa74c2/CI15개·미해결0을 확인해48e8dd4로 병합했다. 거절을 다른 경로로 우회하지 않았다.

**현재는 구현·모의 검증 후보다. 실제 FASHN 호출0회, 실사 합성 품질·실물 폰·새 기능의 운영 배포는 미확인이다.** API키·새 비용 집행·개인 사진 외부 시험을 개발 요청만으로 대신 승인하지 않는다. 권리 미확인 상품을 복제하거나 외부AI 입력으로 쓰지 않는다. R20·R22의 외부 처리/권리 경계를 지킨다. 생성된 가상 인물 입력이 존재한다는 사실을 실제 가상 착용 성공으로 쓰지 않는다.

## 사용자 흐름과 선택 이유

1. 상품 상세 사진 위의 **내 사진에 입혀 보기**에서 스크롤 없이 시작한다. 기존 거울/실측/활용·소장/구매 결정 화면도 유지한다. `#/tryon?id=상품id` 직접 진입과 Back을 연결했다.
2. 내 사진과 입혀 볼 옷 사진을 선택한다. 이미 이 기기에 보관한 body 사진을 재사용하고, 같은 상품에 직접 연결한 내 옷 사진이 있으면 불러온다. 권리가 확인되지 않은 판매처 사진을 자동으로 내려받거나 합성 입력으로 보내지 않는다. 그 경우 직접 찍었거나 사용할 권한이 있는 파일을 선택해야 한다. 모든 판매처의 ‘버튼 한 번 합성’이 완성된 것은 아니다.
3. 사진을 선택한 것만으로 전송하지 않는다. 외부 제공자 FASHN·사진 처리 조건을 설명하고 **내 사진과 합성에 사용할 수 있는 옷 사진을 FASHN으로 보내는 데 동의**를 받는다. 사진을 바꾸거나 새 생성 요청을 시작하면 동의를 다시 받는다. 접수한 작업에는 동의 안내 버전·사용 권한에 대한 작성자 확인도 기록한다(권리를 운영자가 검증했다는 뜻은 아님). 버전 기록이 빠진 반례를 먼저 실패시켜 보완했다.
4. 버튼을 누르면 서버가1건을 예약하고 생성/결과 상태를 확인한다. 확실한 한도 거절은 사진을 유지하고 대기 상태를 지운다. 접수 응답을 잃으면 같은 요청의 결과 조회로 이어가고 자동으로 새 생성 요청을 보내지 않는다.
5. 결과에서 **입힌 모습 / 입기 전 / 옷 원본**을 전환한다. 다운로드와 기존 내 옷 비교로 연결한다. 추천에서 이미 확인한 AI 이유가 있으면 그대로 재사용하며 사진만 보고 임의 Match점수·새 스타일 판정을 만들지 않는다.

Blender/3D로 상품을 다시 만드는 대신 사진 기반 생성 어댑터부터 연결했다. 상품·인물 사실을 유지하는지를 같은 입력으로 비교하기 쉽고, 이미 있는 원스톱 상품 화면에 작은 진입점으로 연결할 수 있기 때문이다. 일반 채팅 API로 이미지를 생성할 수 있다고 가정하지 않았다. FASHN을 후루츠가 사용한다는 근거는 확인되지 않았고, 여기서는 별도 구현 후보로 선택했다.

## 사진·계정·저장 경계

- PNG/JPEG/WebP·8MB·1,200만 화소 이하를 읽고, 전송용 사본은 긴 변1536px 이하/1MB 이하 JPEG로 canvas에서 만든다. 전송용 위치/촬영 메타데이터는 제거한다. 원본은 변경하지 않는다.
- ‘내 사진을 이 기기에 기억하기’는 기존 계정별 IndexedDB 사진 저장소와 body 레코드 형식을 사용한다. 기존 원본의 해시/메타데이터는 덮어쓰지 않는다. 옷장·거울 초안·보정점·기존 백업 키/스키마는 바꾸지 않는다. 원본은 기존 사진 포함 백업에 포함되며 사진 없는 JSON만으로 복원되는 것은 아니다.
- 마지막 body 레코드를 기기에서 다시 읽는다. 같은 바이트가 이미 다른 역할로 보관된 경우 기존 불변 메타데이터를 우선한다. 이는 기존 사진 저장 계약이다. 파일을 다시 선택할 수 있다.
- 결과 이미지는 화면 메모리에만 두며 내려받기는 명시적 버튼으로 한다. 생성 결과를 기존 백업에 자동 추가하지 않는다. 새로고침 시 원본 옷 사진을 기억하지 않았으면 ‘옷 원본’ 비교를 제공하지 않는다.
- sessionStorage에는 계정 scope와 상품별로 작업UUID·만료 시각·기억한 사진 id만 둔다. 사진/base64·키·이메일은 넣지 않는다. 새로고침/응답 손실 후 같은 결과를 찾기 위한 참조다. 오래된 창은 기존 계정 활성 검사와 서버 scope 검사로 거절한다.
- 서버는 개인 사진/결과 원문을 DB나 로그에 넣지 않는다. 기존 RANK_DB의 새 `tryon_jobs`에 불투명 회원/작업 id·입력 전체의 SHA256·처리 상태·시각·예약 크레딧·제공자 작업 id만 둔다. 원래 테이블을 ALTER/초기화하지 않는다.90일 지난 작업 메타데이터는 다음 유효 제출 때 정리한다. 사진 보관 기간과 작업/예산 원장 기간을 혼동하지 않는다.
- FASHN 입력/출력은 base64만 사용하며 결과 URL을 따라 가져오지 않는다. 제공자 입력 처리 사본은 요청 종료 시 삭제/최대 하루 정리, base64 결과는 완료 후60분 조회, 요청 상태/파라미터 기록은 자동 삭제되지 않는다는 정책이다. 학습은 별도 동의 없이는 하지 않는다고 안내한다. [공식 처리 정책](https://docs.fashn.ai/api-overview/data-retention-privacy), 확인2026-10-29. 제공자 기록까지 우리 서버가 즉시 지우는 것으로 쓰지 않는다.

## 서버 계약·비용·오류

`GET /api/try-on/config`, `POST /api/try-on/jobs`, `GET /api/try-on/jobs/:UUID`. 인증은 기존 Worker가 확인한 actor만 넘긴다. 본인/초대/계정 모드를 유지하며 POST는 같은 출처·현재 계정 scope가 필요하다. 클라이언트가 보내는 회원 id/role/URL·임의 모델/이미지 수는 받지 않는다.

생성은 `tryon-max`, `quality`, `1k`, `num_images=1`, JPEG, `return_base64=true`로 고정한다. 공식 단가3크레딧, On-Demand 1크레딧US$0.075 기준 **1장 US$0.225**다. [모델 계약](https://docs.fashn.ai/api-reference/tryon-max), [가격](https://fashn.ai/pricing), 확인2026-10-29. API는 앱의 무료10크레딧과 별개이며 공식 안내의 API 최소 구매는US$7.50/100크레딧이다. [발급 절차](https://docs.fashn.ai/getting-started/api-setup). 자동 충전·구독·결제를 대신 등록하지 않는다.

| 설정 | 의미 |
|---|---|
| FASHN_API_KEY | 런타임 Secret. Git/채팅/브라우저 코드/응답에 넣지 않는다 |
| TRYON_MODE | 없음/off는 호출 금지. private는 본인 관리자만. members는 별도 승인 뒤에만 확장 |
| TRYON_DAILY_CREDITS | 서비스 전체 UTC 일일 예약 상한 |
| TRYON_MONTHLY_CREDITS | 서비스 전체 UTC 월간 예약 상한 |
| TRYON_MEMBER_DAILY_CREDITS | 한 계정 UTC 일일 예약 상한. 본인도 적용 |

세 한도는 모두 명시적3~10000 정수여야 한다. 키·기존 예산 DB·허용 모드·세 한도 중 하나라도 없으면 제공자 호출 전503이다. 안전하지 않은 ‘기본 무제한’은 없다. 기존 Claude 상담/추천 한도는 변경하지 않는다. 원격 Secret/변수는 아직 추가/변경하지 않았다.

한 번의 조건부 INSERT가 전역/계정 예산과 동시 실행(전역2/계정1)을 원자 예약한다. 동일 UUID/동일 입력 재전송은 재생성하지 않고, 같은 UUID의 바뀐 입력은409다. UUID는 인증된 계정에 묶이며 다른 계정의 결과는404다. 요청1건은3크레딧을 예약하고 불명확한 접수/실패의 예약도 자동 반환하지 않는다. **우리 앱의 보수적 예약 한도와 FASHN이 실제 성공 결과에 청구한 사용량은 다를 수 있다.** 운영자가 제공자 기록을 대조한 뒤 예산을 판단한다.

제공자 접수의20초 제한·오류/응답 손실 시 unknown으로 두고 자동 재전송하지 않는다. 제공자 작업 id 저장에 실패해도 예약을 유지한다. 결과 조회는3초당1회만 제공자에 보내고, 화면은 최대45회/3.5초 간격 뒤 수동 결과 확인으로 바뀐다. 이는 새 생성 요청이 아니다. 결과 조회는1시간 이내다. 결과는 한 개의 제한된 JPEG base64만 받으며 임의 CDN/사설 URL을 서버가 fetch하지 않는다. 제공자/DB 원문 오류·키/사진을 응답/로그에 노출하지 않는다.

## 마지막 검토에서 고친 반례

- 처음 구현한 진입 버튼은 비교 도구 아래에 있었다. 핵심 기능을 찾으려고 스크롤하지 않도록 상품 사진 위로 옮기고, 두 엔진에서 버튼 전체가 첫 viewport 안에 있는지 확인했다.
- 동일 탭에서 주소만 바꿀 때 기존 화면으로 돌아가는 실패를 먼저 재현했다. 처음에는 캡처 도구 문제로 보고 새로고침을 시도했지만 해결되지 않았다. 실제 원인은 앱이 외부 주소 전환을 게시판에만 등록하고 새 착용 주소를 빠뜨린 것이었다. externalRoute/경로 비교에 tryon만 추가해 기존 guard/스택 코드는 유지했다. 직접 주소와 Back, 기존 게시판의 주소/편집 취소 보호를 함께 검증했다. 캡처 도구의 불필요한 새로고침/디버그 우회는 제거했다.
- 주변 앱 상태 갱신 때 착용 컴포넌트를 새로 마운트해 고른 사진과 동의가 사라지는 반례도 먼저 실패시켰다. 같은 후보/같은 화면의 단순 갱신은 기존 컴포넌트를 유지한다. 다른 후보·주소·Back으로 떠나는 생명주기는 그대로다.
- 동의 버전을 확인만 하고 작업에 남기지 않던 반례는 실제 SQLite 행의 누락으로 실패를 확인한 뒤 동의 버전/사용 권한에 대한 작성자 확인을 메타데이터로 남겼다. 사진은 추가로 저장하지 않는다.

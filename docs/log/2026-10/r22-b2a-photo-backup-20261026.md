# R22 B2a 사진 보관과 사진 포함 백업 — 2026-10-26

대표가 승인한 B1→B2a→B2b→B3·B4→B5→B6 순서를 계속한다. B1 #76은 CI11개/읽기 전용 검토와 head를 확인한 뒤 master469255a에 병합했다. 기존 임시 폴더에 원인 미확인 tracked41개 파일 누락이 있어 그 상태를 되돌리거나 stage하지 않고, 깨끗한 기존 worktree에서 새 브랜치를 시작했다. 개인 원본 폴더·사진은 사용하지 않았다.

## 보존 설계

사진은 SHA256 주소의 불변 원본 바이트로 IndexedDB에 보관하고 읽을 때 Blob을 재구성한다. 데이터베이스2의 photo-index는 메타데이터만 읽고 원본은 필요할 때 한 장씩 읽는다. 기존1의 Blob 행은 수정하지 않고 색인만 보강해 읽는다. 같은 사진 재수입은 재사용하고 다른 사진으로 같은 ID를 덮지 않는다. 사진 묶음 백업은 기존 format2 글자 백업을 포함하되 별도 봉투다. 기존 글자5MB 한도는 유지하고 사진 묶음은 별도 크기·형식·해시·중복 검사로 제한한다. 누락 참조와 연결되지 않은 사진을 모두 알린다. 일반 JSON 복원과 되돌리기는 이전 사진 Blob을 삭제하지 않는다.

사진 복원은 IDB 복구 저널을 먼저 보관하고 동기 pending 표식을 남긴 뒤 진행한다. 표식이 있으면 코어/초안/개인 자료의 새 저장을 막고 복구 화면을 연다. 사진은 추가만 하며 이전 원문·STASH/NEXT를 복구 저널에 남긴다. 글자 적용·보관본 승격·표식 정리가 끝나기 전 완료로 표시하지 않는다. 재시작 시 끝난 거래는 정리만 하고, 미완료 거래는 이전 글자 원문/복구 지점으로 되돌린다. 새 사진은 연결되지 않은 보관본으로 남을 수 있다.

앱은 사진을 서버·AI로 전송하지 않는다. 상품 사진 URL을 사진 저장 함수에 받지 않는다. 이 단계는 사진 백업·복구 기반이며 실제 사용자 사진 입력·레일은 B2b에서 연다. 합성 PNG/가짜 저장소와 실제 브라우저 IndexedDB만으로 먼저 검증한다.

## 묶음 형식과 복구 경계

기본 사진 파일은 `.otjang`이다. 처음8바이트 EOULPH01, 다음4바이트 big-endian 머리글 길이, UTF-8 JSON 머리글, 선언한 순서의 원본 사진 바이트를 잇는다. 머리글은8MB, 사진 한 장은8MB, 전체 파일은1GB/2000장으로 상한을 둔다. 원본을 base64로 모두 복사하지 않으며 가져올 때 File.slice로 한 장씩 검사한다. 길이·중복·MIME·원문 SHA256·미래 버전·금지 키를 검사한 뒤에만 저장한다. 구형 시험용 JSON 사진 봉투는64MB 한도로 별도 읽는다. 기존 글자 백업은5MB 그대로다. 사진만 있는 묶음은 기존 글자 자료를 유지하고 사진만 보관한다.

사진이 있으면 기본 내보내기에 포함하고 기본 복원 버튼도 묶음을 인식한다. 글자만 복사는 계속 사진을 포함하지 않는다. 미리보기는 원문 보관·기존 활성 자료 유지·보관 후 교체/제거와 누락/고아 사진을 함께 알린다. 새 파일 선택 즉시 이전 확인 권한을 없애고 선택 epoch가 다른 지연 응답을 버린다. A 정상→B 손상에서 A 버튼이 남는 문제를 두 실패로 먼저 재현했고 사진/글자/용량 초과 교체 경로를 보완했다.

저널 slot은 IDB 트랜잭션에서 소유 ID를 비교하고 cleanup도 기대 ID가 같을 때만 지운다. 사진 복원·되돌리기·복구와 일반 JSON 복원·undo는 같은 Web Lock을 쓴다. 잠금 미지원 브라우저는 사진 복원을 안전하게 거절한다. 이미 열린 탭의 코어·초안·등록·상담·날씨 쓰기는 pending 표식을 확인하고, 다른 탭은 저장 경고와 inert 화면을 표시한다. 저널 작성과 비동기 사진 보관 뒤에 snapshot/STASH 변경을 다시 확인하며 바뀌었으면 글자를 덮지 않는다. 보통의 두 탭 동시 편집 전체에 서버급 원자 버전 관리를 도입한 것은 아니다.

#74/#76의 apply 보상·stash·undo 본문은 유지하고 동기 capability adapter 안에서만 사진 저널의 글자를 적용한다. 사진은 추가만 하므로 undo 뒤의 새 사진도 고아 보관본으로 남을 수 있다. 임의 정리/초기화로 공간을 비우지 않는다. 장기 보관은 사용자 버튼의 navigator.storage.persist 결과를 허용/거절/미지원으로 안내하며 영구 보장을 하지 않는다.

## WebKit의 실제 저장 오류

최초 실제 사진 검사에서 Chromium은 통과했으나 WebKit은 photos:add에서 UnknownError를 반환했다. 실제 cause는 `Error preparing Blob/File data to be stored in object store`였고 quota로 단정하지 않도록 진단 이름/원인/실패 요청을 보존했다. [공식 Playwright #42795](https://github.com/microsoft/playwright/issues/42795)는 ephemeral WebKit의 Blob/File 저장 미지원을 같은 오류로 설명한다. 그 보고는1.63이고 현재1.57이므로 버전 전체를 동일 원인으로 단정하거나 일반 iPhone Safari 실패로 확대하지 않는다.

저장 표현을 원본 ArrayBuffer+MIME로 바꿨고 실제 IndexedDB·재시작·다운로드/복원·원본 바이트 동일 검사를 그대로 실행해 두 엔진 모두 통과했다. mock/skip으로 바꾸지 않았다. 별도의 실제 persistent 브라우저에서는 기존 Blob 행을 만들어2로 이전해 원본 바이트/보관 시각이 유지되는 것도 확인했다. 일반 기본 검사는 기존 비공개 격리 context 그대로다.

## 실행 결과와 남은 범위

초기 새8개는 미구현으로 모두 실패했고 실패 우선 커밋6a8b1fe에 남겼다. 보강한 새15개와 기존 항목을 합친 lite271/271, TypeScript/Vite 빌드, Chromium35/WebKit35=70개가 통과했다. 두 연결이 모두 새 해시가 없다고 읽은 상태를 실제로 관찰한 뒤 동시 최초 삽입, 늦은 저널 cleanup, 다른 탭/일반 JSON의 우회 차단, 원문 격리 UI, 장기 보관 안내, 방문 뒤 실제 origin 정지 오프라인도 포함한다. 기존 검사 삭제·retry/timeout 완화는 없다.

전후 캡처는 동일 합성 옷장/사진·모바일/PC 크기에서 별도로 기록한다. 최종 head/CI는 PR과 후속 인계로 확인한다. 이것은 사진 보존·백업 단계이며 옷장 레일이나 전체 화면 React 전환 완료가 아니다. 실제 사용자 사진·실기기 대용량 성능·실제 Safari/PWA 권한·재설치/기기 이동은 미검증이다. 실제 사진 입력은 B2b에서 열며 R20 미확인 상품 사진 가공이나 서버 전송은 없다.

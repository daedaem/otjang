# R22 B3a — 옷 정보 편집의 초안·출처·저장 경계

기준 master는 B2b #78 병합 `43a14d610d61da8dea12c67c65a79cc75fad1277`이다. 이 PR은 다음 React 보유 옷 편집 화면이 사용할 **저장 기반**이다. 아직 사용자 편집 화면·후보 사이즈 비교·수집 진열장을 연결하지 않았으며, 데이터 기반을 화면 완료로 쓰지 않는다.

## 왜 먼저 나누나

보유 옷 편집과 새 옷 등록은 서로 다른 작업이다. 실측을 적다 `72.`에서 멈춘 값은 확정된72cm가 아니고, 같은 출처/값을 그대로 열었다 닫았다고 AI 추정이나 판매처 표기를 사용자 확인으로 바꾸면 안 된다. 또 오래 열어 둔 화면이 최신 옷장/구매 기록을 통째로 덮어쓰지 않아야 한다. 이런 경계를 먼저 확인한 뒤 편집 UI를 붙인다.

## 형식과 출처

- 새 초안 위치는 `eoul-d12-hang:profile-drafts:v1`이다. 기존 등록 초안 `eoul-d12-hang:input-draft:v1`과 분리한다. B3b의 실제 저장/재개 controller가 이 형식을 사용한다. 이 단계에서 자동으로 초안을 만들거나 기존 개인 자료를 이전하지 않는다.
- 봉투는 `{v:1, edits:{[garmentId]: edit}}`다. edit은 대상ID/종류, 편집 전 `baseProfile`, 원문 form, 수정 시각을 가진다. form은 실측 문자열·각 실측 출처·속성 문자열·디테일·목적/컬렉션·기준 표시·명시적 추정 확인 목록이다.
- 초안에서는 `72.` 같은 미완성 입력을 그대로 읽는다. 실제 저장용 profile로 바꿀 때 읽을 수 없으면 거절한다. 미래 버전/알 수 없는 필드·누락 필드·잘못된 종류/출처·중복JSON 이름을 거절하고 원문은 쓰거나 정규화하지 않는다. 최대1000개 edit, 디테일 초안1000자 등의 읽기 한도는 내부 형식 방어이며 실제 등록 가능 옷 수(기존200벌)를 바꾸지 않는다.
- 값과 출처가 바뀌지 않은 실측/속성은 원래 출처를 보존한다. 같은70cm라도 사용자가 출처를 ‘판매처 표기’에서 ‘직접 잼’으로 명시적으로 바꿀 수 있다. AI 추정 속성은 다른 실측을 고쳐도 AI로 남고, 해당 확인을 누르거나 값을 직접 고칠 때만 사용자 값이 된다. AI 실측은 기존 profile 규칙대로 허용하지 않는다.

공유 원본은 `app/lite/src/domain/profile-edit.js`, 코어 통로는 `profileEditDraft`/`profileFromEdit`/`readProfileDrafts`/`canReadProfileDrafts`/`applyProfileEdit`다. React에서 도메인과 카탈로그를 다시 묶지 않도록 기존 브라우저 코어를 통한다.

## 실제 저장의 보호

`applyProfileEdit`은 현재 저장 원문을 읽기만 해 메모리 상태와 대조한다. 다른 탭이 옷장·구매 기록을 바꿨거나 원문을 읽지 못하면 `storage_changed`로 거절하며 어느 쪽도 덮어쓰지 않는다. 사용자가 최신 기록을 다시 읽은 뒤에도 편집 대상 profile이 시작 때와 다르면 `profile_changed`로 거절한다. 종류가 바뀌거나 대상이 사라졌거나 체험용이면 실제 보유 옷으로 적용하지 않는다.

새 값이 이미 저장된 값과 같으면 재시도는 쓰기 없이 현재 옷을 돌려준다. 실제 변경은 B1의 `updateGarmentProfile` 한 번으로 저장하므로 종류별 기준 옷 전환·쓰기 실패 rollback·사진 참조/다른 속성/등록 영수증 보존을 유지한다. 읽기 전용 대조와 실패에서 새 등록 이력을 만들지 않는다.

이 대조는 서버 수준의 모든 일반 편집 경합을 해결하는 구현이 아니다. B3b controller는 기존 저장 잠금·사진 복구 표식과 함께 사용하고, 구형 탭은 갱신한 뒤 복구해야 한다. UI의 초안 쓰기/재개/정리 실패 처리도 다음 PR에서 검증한다. 여기에는 아직 그 controller가 없다.

## 백업 경계

BK는 새 초안의 공통 reader를 호출해 읽을 수 있는지 확인한다. 미래/손상 초안은 format2의 원문 보관으로 분류한다. 보관 전용 초안이 들어오면 현재 정상 활성 초안은 유지한다. 원문은 새 옷으로 활성화하지 않으며 미리보기는 ‘옷 정보 초안 N개’로 별도 집계한다. 기존 등록 이력 집계는 바꾸지 않는다.

#78 대비 BK의 검사/출처 이름/조건부 초안 건수만 확장했다. 적용·복원·되돌리기 구간은 원문 대조 결과 동일했다.

| apply→restore 전 | c2a30adb786c8965bb0b0438179b841b7238e00dcb7674326aab2caa635da182 |
| restore→stash 전 | b849f6f685971a60d116d73cfcddcec4c58b9dbda1cc3a4c3d802bdd90870ff5 |

코어 snapshot2·등록 영수증2·등록 초안2, 기존 저장 키와 사진 IDB2를 변경하지 않는다. 기존 원문 보관과 사진 포함 백업을 제거하거나 구버전 로직으로 되돌리지 않는다.

## 검증 범위

실패 우선 커밋 `720e1f5`는 미구현6개 모두 실패했다. 추가된 Node8개는 미완성 원문/미래·손상·중복 이름/출처 보존·명시 확인/실패·재시도/실제 별도 코어의 최신 기록/백업 원문과 별도 집계를 검사한다. 기존280개를 삭제하지 않았다.

브라우저 새4실행은 실제 BK에서 등록 초안과 옷 정보 초안을 동시에 보존하고, 미래 초안 복원에서 현재 활성 초안·옷장 원문·등록 초안이 유지되는지 확인한다. Chromium은 실제 생성된 다운로드 파일을 읽고, 파일 공유 가능한 WebKit은 생성된 File을 공유 API 경계에서 수신해 MIME/문자열을 검사한다. 이것을 실제 iPhone 공유 창 조작·파일 앱 저장 성공으로 확대하지 않는다. 초기 검사 스크립트의 모호한 미리보기 선택과 ‘붙여 넣은 글자 확인’ 누락은 실제 화면 순서대로 바로잡았다. 제품 검사를 skip/retry/timeout으로 완화하지 않았다.

현재 로컬 Node288/288·집중 브라우저4/4·전체94/94·빌드를 통과했다. 기존90개를 유지하고 새4개를 더했다. 같은 최종 head CI 결과는 PR에서 별도 대조한다. 실제 개인 사진/키/운영 API를 사용하지 않았다. 아직 편집 UI나 실제 기기 재개를 검사한 것은 아니다.

## 콘셉트

1위 안 '스타일리스트 대화'를 뼈대로 쓴다. 해석은 직렬화할 수 있는 Intent JSON으로 하고, 결정 표로 만든 되묻기는 최대 1장만 둔다. 이해한 조건은 칩 줄 하나로만 보여 준다. 여기에 다른 두 안의 좋은 점을 붙인다. 하나는 '답 먼저' 안의 화면 구조와 낮은 구현 위험이다. 결과 첫 화면은 조건을 지킨 상품 3개(답 1 전체 폭 + 다른 방향 2)이고, 기존 stampFacts 미리보기 경로를 재사용하며, 하단에 결정 바를 고정한다. 다른 하나는 '옷장 무대' 안의 시그니처 장면이다. 상품 시트와 저장 보상에 '나란히 걸기' 레일을 두어, 후보 옷이 내 옷(또는 '갖고 계세요?' 답) 옆에 걸리는 모습을 보여 준다. 고정 4자리 무대는 쓰지 않는다. 원피스·셋업·소품이 깨지고 첫 방문자에게 '빈칸 숙제'로 보이기 때문이다. 대신 '요청한 옷 1벌 + 함께 입을 옷 0~3벌'이 가로로 걸리는 가변 레일을 쓴다. 자리 이름은 그 옷의 role(상의/하의/원피스/신발/소품)을 따른다.
되묻기는 결과를 막지 않는다. 종류가 해석됐으면 결과를 먼저 보여 주고, 확인 질문은 칩 줄 바로 아래에 '좁히기' 1줄로 붙인다. 결과를 가리고 질문 카드로 대신하는 것은 understood=false(종류도 상황도 없음)일 때뿐이다. 이렇게 '자꾸 묻는 앱'과 '첫 답 지연' 위험을 막는다. 사진은 모두 contain + 종이 배경으로 처리한다. cover 크롭은 쓰지 않는다. 그래야 상품을 정확히 보여 준다.
서비스 문장: 대충 말한다 → 조건을 지킨 한 벌이 먼저 온다 → 내 옷 옆에 걸어 본다 → 살게요/보류/안 살게요 → 구매 여정이 기록되고, 받은 옷은 옷장에 걸린다. 태그라인은 '대충 말해도, 딱 맞는 한 벌'이다. 이름은 미정이므로 BRAND.name은 유지하고 tagline과 heroTitle만 바꾼다.
제약은 모두 지킨다. 저장·백업·동기화·구매 기록 형식(wardrobe-store, zip-store, account sync, purchase-journey의 JOURNEY_DECISIONS/STAGES/FITS/RETURN_REASONS, state.demo/demoSelected 필드)은 바꾸지 않는다. '갖고 계세요?' 답은 source:'preview'로 메모리에만 두고 저장 경로가 거부한다. LLM은 같은 Intent 스키마를 내는 어댑터 인터페이스만 두고, 기본은 꺼짐이며 네트워크 코드는 없다. 사진은 외부로 보내지 않는다. 가격 표기는 늘 '수집 가격'이고 '최저가/현재가'는 금지어 테스트로 막는다. 공개 배포는 하지 않는다.

## 흐름

- 첫 방문 홈(0탭, 774px 안): 워드마크 + 질문 H1 '어떤 옷 찾으세요?' + 입력창 + 예시 칩 3개 + 실제 사진이 있는 '이렇게 답해요' 카드 1장 + 옷장 안내 한 줄. 예시 배너·성별 이중 칩·12벌 고르기·코디·구매 후보·분석은 없다. 탭 배지는 실제 옷·진행 중 여정만 센다(첫 방문 0이면 배지 숨김).
- 한 줄 요청: 입력하거나 칩을 탭하면 parseQuery가 Intent JSON을 낸다. engine.search(Intent)가 하드 필터(종류·예산·상황·제외 색)를 적용하고, 완화했으면 relaxNote를 낸다. 결과 화면은 0.3초 안에 렌더하고(엔진 2.5ms), 제출 후 결과 H2로 포커스를 옮기고 role=status로 '셔츠 3개 골랐어요'를 알린다.
- 이해 칩 줄(유일한 조건 표시): [셔츠 ×] [출근 ×] [10만원 이하 · 한 벌 기준 ×] [+ 조건]. 칩의 ×를 누르면 그 조건을 빼고 바로 다시 찾는다. 칩을 누르면 바꾸기 팝오버가 열린다. homeHeader의 '추천 조건' 요약은 결과 화면에서 없앤다.
- 좁히기(필요할 때만, 최대 1줄): 종류가 해석됐으면 결과는 그대로 두고 칩 줄 아래에 질문 1줄 + 칩 2~4개 + '상관없어요'를 붙인다(모호한 부정, 이해 못 한 체형 말, 성별 미정, 미지원 조건). 결과를 가리는 것은 understood=false일 때뿐이고, 그때는 상품 대신 '어떤 옷을 찾으세요?' 카드 1장을 보여 준다.
- 답 카드: 답 1 '가장 맞아요'(전체 폭, 사진 높이 300 contain) + 다른 방향 2장(반폭, 라벨 '더 싸게 · 이 목록 안에서' / '더 격식 있게' / '다른 색' 중 Intent에서 자동으로 고른 축). 모두 조건을 지키고, 이유는 상품별로 생성하며 같은 결과 안에서 같은 문장은 금지한다. 그 아래 접힌 '조건 맞는 셔츠 n개 더 보기'(1열 행)와 접힌 '이 셔츠로 입는 법'(요청 품목 포함 코디). 수집일 메타는 섹션 하단에 1회 둔다.
- 답 탭 → 상품 시트(한 시트에서 상세·비교·결정): sticky 헤더 안의 닫기, 사진 최대 min(46vh,360px) contain, 브랜드·품명·가격 + '10월 13일 수집 가격', '왜 맞나요' 2줄, 판매처 버튼(첫 화면 안), 그리고 '내 옷 옆에 걸어 보기' 레일(시그니처).
- 내 옷 옆에 걸어 보기(어떤 상태에서도 바로 판정): 옷장이 있으면 레일에 후보 + 함께 입을 내 옷 2~3벌이 걸리고, 판정 줄과 숫자 3칸(생기는 코디/어울리는 내 옷/겹치는 옷)이 나온다. 옷장이 없거나 예시 상태면 레일의 빈 자리에 '갖고 계세요?' 칩 질문 2개(하의 종류+대표색 자동, 비슷한 옷 여부)를 두고, 탭하면 그 자리에 참고 사진이 걸리며 판정이 바로 나온다. 등록 시트로 보내지 않는다. 판정은 stampFacts/compareCandidate의 preview 경로를 재사용한다.
- 결정: 시트 하단 고정 바 [살게요] [보류] [안 살게요]. 판정 전에도 누를 수 있다. 누르면 createPurchaseJourney → transitionPurchaseJourney(buy|hold|skip)로 기존 형식 그대로 기록하고, 시트 안에 결과 한 줄을 남긴다('살게요로 정했어요 · 구매 여정에 담았어요 [판매처에서 주문하기 ↗]'). quickCompare/preview 판정 자체는 기록하지 않는다.
- 구매 여정 탭(기존 saved 탭, 데이터 동일): 세그먼트 [고민 중 n] [샀어요 n] [끝난 기록]. 행마다 단계 바 + 다음 동작 버튼 1개(주문했어요 → 받았어요 → 계속 입을게요/반품했어요). '받았어요'를 누르면 기존 트랜잭션(받음 + 옷 생성)이 실행되고 '옷장에 걸렸어요' 장면 카드로 끝난다. 찜은 '고민 중' 아래 접힌 '찜한 상품'으로 합친다.
- 선택형 옷장: 옷장 탭의 기본 진입은 '가진 옷 골라 걸기' 12칸 그리드다(색은 사진 색이 기본, 그리드 밖 하단 색 행에서 바꾼다, 하단 고정 '3벌 걸기'). 시트의 '이 답을 옷장에 걸어 두기' 링크로도 넣을 수 있다. 저장하면 시트를 자동으로 열거나 토스트를 띄우지 않고, 보상 카드('3벌을 걸었어요 · 이렇게 입을 수 있어요' 레일 + 코디 1장 + 아까 본 상품의 판정 갱신)를 보여 준다.
- 재방문 홈: 입력창 + 이어지는 카드 최대 2장('지난번 보류한 셔츠, 다시 걸어 볼까요?' / 옷장이 있으면 '오늘 꺼낼 코디' + [입었어요] → 기존 wear-log). 그 외 섹션은 없다.

### G. 설정 · 말 해석 방식 (LLM 선택 옵션 자리)
- 목적: 대표가 결정하기 전에 LLM 어댑터가 들어올 자리만 보여 준다.
- 레이아웃: 설정 시트의 한 행: 토글 비활성(준비 중) + 설명 12~13px 2줄. 빌드 플래그 BRAND.intentAdapter=null(기본). 사진 끄기 시험 플래그 BRAND.photos=false도 같은 시트의 개발 행(dev 빌드만)에 둔다.
- 문구: 말 해석 도우미 (준비 중)
켜면 규칙으로 못 알아들은 말만 해석 서버로 보내요. 옷장·사진·구매 기록은 보내지 않아요. 상품 선택과 가격은 앱이 정해요.
- 상호작용: 현재 빌드에서는 누를 수 없다. 코드에는 interpret(text) → Intent 인터페이스, enum 검증(slot id·색 키·상황 키)만 있고 네트워크 호출은 없다.

## 시각 방향

톤은 '조용한 종이 위에 걸린 옷'이다. 장식은 걷어 내고 사진, 한 줄 이유, 레일 하나만 남긴다.
토큰(styles.css :root, 다크 2중 가드 유지): --bg #FAFAF8, --surface #FFFFFF, --paper #F3F2EF(사진·되묻기·sunk 카드), --ink #16161A, --ink-2 #5A5A63, --line #E6E4DF, --rail #B9B2A6, --accent #1F4D3A(주 버튼·'가장 맞아요'·'내 옷'·'사도 좋아요'), --warn #9A5B13('비슷한 게 있어요'), 보류는 --ink-2. 다크: --bg #121214, --surface #1B1B1E, --ink #F2F2F0. 사진 타일만 --paper-dark #E9E7E2(radius 12 + 1px --line)로 두는 '종이 카드' 규칙을 쓴다. 주 버튼은 흰 블록 반전 대신 배경 #1F2A24 + 글자 #8FD0AE. 비교 시트 상품명은 --ink이고 브랜드는 --ink-2로 한다(위계 뒤집힘 수정).
사진 문법: 모든 상품·옷·참고 사진은 종이 배경 + object-fit:contain이다. 라이트에서는 mix-blend-mode:multiply로 흰 배경 컷을 녹이고, cover 크롭은 금지한다. 비율은 답 1 높이 300 고정, 반폭·그리드·행은 1:1, 레일은 4:5. --photo-ratio 4/5 + 좌우 회색 띠 규칙은 없앤다. 사진 실패·권리 미확인·BRAND.photos=false일 때는 같은 크기의 .photo--none 카드(대표색 면 + 선형 종류 실루엣 + 품명 2줄)를 쓴다. 레일 빈 자리와 같은 문법이라 사진을 전부 빼도 레이아웃이 유지된다.
타입 4단을 고정한다. 화면 제목 28/700(홈 H1·탭 제목만), 섹션·카드 제목 20/600(품명·가격 큰 표시는 17~20), 본문·이유 15/400(행간 1.5), 브랜드·라벨 13. 12px은 수집일·출처·면책 메타에만 쓰고 11px은 폐기한다. --text-hero 40, --text-display 32 섹션 제목, 24·30 제목은 없앤다. 가격은 tabular-nums.
면책은 섹션당 1회 12px로 줄인다. 사진마다 붙던 '비슷한 상품 사진' 캡션 띠와 타일 '예시' 배지는 없앤다.
카드: 그림자 없이 radius 12, 간격 16, 패딩 16. 쇼핑몰식 2열 6장 그리드는 기본 화면에서 쓰지 않는다. 이유 줄은 초록 6px 점 + 15px 잉크(초록 글자 3줄 금지). 판정은 상태 점 + 문장으로 표현하고 색만으로 구분하지 않는다.
시그니처 모션은 '걸림'(translateY -8→0 + rotate 1.5°→0, 240ms ease-out) 하나뿐이고, 레일에 옷이 걸릴 때만 쓴다. 나머지는 120ms 페이드다. prefers-reduced-motion이면 모두 끈다.
터치 영역은 44px 이상이고, 칩은 36px + 상하 4px 히트 확장이다. 헤더 버튼은 아이콘 버튼으로 바꿔 줄바꿈을 원천 차단한다. 시트 닫기는 sticky 헤더 바 안에 두어 본문과 겹치지 않는다.

## 리스크

- 하드 필터 때문에 결과가 0~2개로 줄 수 있다. 완화 순서(색 → 상황 → 예산 +10%)를 고정하고, 완화했으면 relaxNote와 카드 라벨로 반드시 밝힌다. 골든 세트로 '3개 미만' 비율을 재서 10% 미만을 목표로 한다. 상황 태그는 slot 단위라서 플란넬 같은 이질 상품은 품명 키워드 감점을 함께 쓴다.
- 되묻기가 귀찮아질 위험: 종류를 해석했으면 결과를 막지 않고, 질문은 요청당 1줄만 묻고 '상관없어요'를 늘 보여 준다. clarify 노출률(로컬 계측)이 30%를 넘으면 규칙을 조인다.
- 옷장 없음 판정은 칩 답 1~2개에 기대므로 근거가 얇다. 판정 문장에 '말씀하신 옷 기준'을 명시하고, preview 판정은 기록하지 않는다. 기록은 결정 바를 누를 때만 기존 journey로 남긴다.
- preview 옷이 실제 옷장에 섞이면 기록이 오염된다. source:'preview'는 메모리 전용이고 저장·동기화·zip 직렬화에서 거부하는 가드와 테스트를 둔다(형식 변경 아님). '걸어 두기'를 누를 때만 makeGarment로 저장한다.
- 레일 자리 규칙의 예외(원피스·셋업·가방·소품)는 role 기반 자리표로 처리한다. 원피스는 자리 '신발·가방', 소품 후보는 '상의·하의'다. 여성 하객룩 질의를 골든 세트와 e2e에 넣는다.
- demo 해석 변경: 기존 demo:true 사용자가 예시 옷 6벌이 사라졌다고 느낄 수 있다. 1회 안내를 띄우고 demoSelected 데이터는 지우지 않는다. 백업 복원·동기화 테스트는 수정 없이 통과해야 한다. wardrobe-first.test.mjs의 화면 기대값(570-571, 687-688)만 바꾸고 커밋을 분리한다.
- 상품 단위 순위와 Intent 리팩터로 engine·ask-search 테스트 기대값이 대량으로 바뀐다. 단계 1·2의 완료 조건을 골든 세트 diff 리뷰로 두어 의도된 변경과 회귀를 구분한다.
- main.js 5,441줄과 innerHTML 전체 재렌더 구조: 부분 렌더는 #intent-bar와 #picker 두 곳만 replaceSection으로 한정한다. 이벤트 위임과 시트 key 규칙은 유지한다. 단계 0의 e2e를 먼저 고정한 뒤 화면 단계(5~9)를 한 작업자가 순서대로 PR로 진행한다.
- 상품 사진 권리 미확인: 사진 중심 설계라 사진을 빼면 첫인상이 약해진다. .photo--none을 1급 상태로 같은 크기로 설계하고 BRAND.photos=false 빌드로 매 단계 캡처를 확인한다. 공개 배포 전에 권리 확인이 필요하다. 로고 컷은 브랜드 미정 옷 썸네일에서 제외한다.
- 이유 문장의 사실성: 데이터 필드(색·가격 차이·종류·출처 있는 태그·평점·후기 수)에서만 만든다. 핏·소재처럼 데이터에 없는 말은 쓰지 않는다. '더 싸게'는 '이 목록 안에서 · 수집 가격' 차이만 쓰고, '최저가·현재가·가장 싸요'는 린트로 금지한다.
- 홈에서 구매 후보·코디·분석을 빼면 재방문 사용자가 기능을 찾지 못할 수 있다. 옷장 탭 '오늘 꺼낼 코디'와 여정 탭으로 옮기고, 2주간 홈 옷장 행에 이동 안내 1줄을 둔다.
- LLM 해석은 대표 결정 전이다. 인터페이스와 enum 검증만 만들고 기본은 꺼짐, 네트워크 코드는 없다. 켜더라도 질의 텍스트만 보내고 상품 선택·가격은 앱이 정한다는 규칙을 테스트로 고정한다. 유료 API와 외부 전송은 이번 범위 밖이다.
- 번들 1,067KB(카탈로그 391KB)는 이번 범위에서 줄이지 않는다. 첫 화면 사진 1~3장만 eager로 받고 나머지는 lazy로 둔다. 카탈로그 분리 캐시는 후속 과제다.
- 계측은 로컬 sessionStorage 집계뿐이라 실사용 전환율은 알 수 없다. '퇴화' 판정은 e2e 수치(높이, 첫 상품 y, 탭 수)로 대신하고, 외부 집계는 대표 결정 뒤로 미룬다. 질의 원문은 저장하지 않는다.

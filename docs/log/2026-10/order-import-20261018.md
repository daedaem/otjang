# 쇼핑몰 구매내역 가져오기 · 로컬 시험판

> 문서 시점: 2026-10-18. 당시의 검토·구현 기록을 보존한 자료입니다. 현재 결정·우선순위·운영 상태는 [최신 문서 목차](../../README.md)를 확인합니다. 아래의 “지금·완료·다음”은 별도 갱신 표시가 없으면 당시 기준입니다.

2026-10-18. 사용자 요청: 무신사 등 쇼핑몰 주문내역을 가져와 입력 부담을 줄이고 구매 장부와 옷장에 연결한다. 원스톱 추천 목표는 유지한다.

## 사용자 피드백 · 고객용 흐름은 미완성

사용자가 Windows PC에서 경로를 찾을 수 없다고 알린 뒤, Acloset보다 너무 불편하다고 평가했다. 로컬 기술 검사 통과와 고객이 편하게 사용할 수 있는 상태를 구분한다. 앞서 제공한 ZIP 링크는 Mac 로컬 파일 경로이며 Windows에서 다운로드되는지 검증하지 않았다.

현재의 개발자 모드 설치·복사/파일 내보내기·별도 HTML 열기·붙여넣기·재선택은 고객용 기본 동선으로 채택하지 않는다. 확장 설치는 최초 준비지만, 복사와 앱 이동·재선택은 매번 발생하는 마찰이다. Acloset PC판도 확장을 쓰므로 확장 자체와 그 뒤의 반복 작업을 구분한다.

다음 개선의 판단 기준: 설치와 배포 경로를 실제 Windows에서 검증하고, 가져올 항목을 한 번 고르면 같은 서비스의 옷장 확인 화면으로 이어지게 한다. 읽은 브랜드·품명·옵션을 재입력시키지 않고, 불확실한 항목만 선택적으로 수정하게 한다. 실제 보유 확인은 한 곳에서 받고 취소·반품 상태 보호는 유지한다. 이를 위해 필요한 전송·계정 연결 방식을 아직 구현하거나 확정한 것은 아니다. 모바일에서의 입력 경로도 별도 설계·검증이 필요하다.

## 기준과 변경 범위

- Claude 최신 수신 기준: `06826756ed493c455d7d46f19c00638da0591679`.
- 작업 브랜치: `feat/order-import-20261018`. 이전 로컬 브랜치 `feat/editorial-mobile-20261013`은 유지했다.
- 공개 배포·GitHub push·실제 주문 상태 변경·결제·개인 사진 전송은 하지 않았다.
- 기존 `wardrobe.json`, `wardrobe-with-photos.json`과 개인 HTML은 수정하지 않았다. 최신 브랜치에서 옛 개인 파일이 실수로 Git에 들어가지 않도록 두 경로를 제외 목록에 추가했다.

## 사용 흐름

1. PC Chrome에서 본인이 무신사에 로그인하고 주문 내역을 연다.
2. 로컬 확장프로그램에서 **현재 주문내역 읽기**를 누른다. 현재 페이지에 렌더링된 주문 카드만 읽는다.
3. 가져올 항목을 선택하고 **복사**하거나 **파일로 받기**를 누른다.
4. 앱의 내 옷장 또는 구매 여정 → **구매내역 가져오기**에서 붙여넣거나 파일을 연다.
5. 중복·상품명·옵션·금액·상태를 보고 선택한 내역만 장부에 추가한다. 이 시점에는 실제 보유 옷을 만들지 않는다.
6. 현재 보유 중인 주문에서 **지금 가진 옷으로 연결하기** → 종류 확인 → **확인한 옷을 내 옷장에 연결**을 누른다. 색은 모르면 비워 둔다. 같은 상품이 이미 있으면 기존 옷 연결과 별도의 새 한 벌 추가 중에서 선택해야 한다.

취소·반품·교환 진행·상태 미확인 내역은 기본적으로 장부에만 보관한다. 배송 완료나 구매 확정은 현재 보유의 증거로 승격하지 않는다. 수량 여러 개인 주문도 자동으로 여러 벌을 만들지 않는다. 이 시험판의 구매 여정 하나에는 한 벌만 연결하며 추가 수량은 각각 확인해 등록한다.

## 왜 이렇게 구현했는가

- 구매자용 공식 주문내역 API가 확보된 상태가 아니므로 API 자동 연동을 약속하지 않았다. 사용자 실행 시 열린 페이지를 읽는 Chrome Manifest V3 확장으로 시작했다. 실제 쇼핑몰 DOM 확인과 유지 보수는 별도다.
- 확장은 `activeTab`, `scripting`, `clipboardWrite`만 요청한다. 상시 호스트 권한·쿠키·로그인 정보·브라우저 이력·원격 API·사진 다운로드가 없다. 주문번호는 중복 식별용 SHA-256으로 바꾸며 원문 번호·주소·연락처·결제수단을 내보내지 않는다. 해시는 익명화의 보장이 아니다.
- 쇼핑몰 상태와 사용자의 현재 보유 확인은 다르다. 장부 저장은 기존 구매 여정의 `created` + `imported`로 남기고 원래 상태·주문일·수량·화면 금액·읽은 시각은 `imported`의 당시 정보에 보존한다. 과거 주문·수령·반품 이벤트나 사유를 생성하지 않는다.
- 현재 보유를 명시적으로 확인하면 오늘의 사용자 확인 시각으로 주문/수령/보관 확인과 옷 연결을 **한 트랜잭션**에 저장한다. 실패 시 일부 상태나 옷만 남지 않는다. 원 주문일은 원래 정보로 따로 보존한다.
- 기존 스키마 7의 검증된 이력 필드를 이용해 저장·백업·계정 형식을 바꾸지 않았다. 원래 정보는 최초 `imported` 이력에서 읽으므로 나중에 메모를 수정해도 보존된다. 이 단계는 별도 회계 장부 스키마나 모든 쇼핑몰의 통합 주문 모델을 완성한 것이 아니다.
- 주문의 화면 금액은 현재 판매가·상품별 최종 실결제액과 다를 수 있어 `candidate.price`에 넣지 않는다. 최초에는 가격·색·종류를 확인 전으로 남긴다. 브랜드·품명은 주문 카드에서 읽은 관찰 정보이며 검증 카탈로그 상품으로 승격하지 않는다.
- 반복 가져오기는 주문 식별자로 중복을 건너뛰고 기존 메모·옷·사진을 덮어쓰지 않는다. 같은 상품의 다른 주문은 별개로 보존한다. 주문번호가 보이지 않으면 중복 식별 신뢰도가 낮으므로 자동 선택하지 않는다. 원래 내역의 상태 변경도 자동 반영하지 않는다.
- 같은 상품의 반품 완료 내역은 새 비교에서 출처를 붙여 보여 줄 수 있지만 반품 이유·사이즈 적합성은 추정하지 않는다.

## 구현 위치

- `app/src/order-import.js`: 외부 파일 엄격 검증, 순수 가져오기 계획, 중복, 원래 정보 읽기, 명시적 보유 연결.
- `app/src/musinsa-order-reader.js`: 화면에 렌더링된 주문 카드 추출. 추천 상품·숨긴 요소·신청 버튼과 완료 상태 구분.
- `app/src/main.js`: 확인 시트, 선택, 파일/붙여넣기, 장부 표시, 보유 연결. 기존 저장 함수로 커밋한다.
- `extensions/musinsa-orders/`: 확장 팝업 소스. 복사/파일 내보내기 전 선택을 받는다.
- `app/tools/build-order-extension.mjs`: 앱과 공유하는 추출기·검증 계약을 확장에 묶는다. 계약을 두 벌 수작업으로 관리하지 않는다.

## 검증

- 전체 앱 테스트 **574개 통과, 실패 0**. Node 22.23.2. 임시 loopback 서버를 쓰는 기존 통합 검사는 샌드박스 밖에서 실행했다. 실제 사용자 DB는 쓰지 않았다.
- 새 자동 검사 12개: 선택·미확인 값 보호, 전 상태 보유 분리, 반복 가져오기, 잘못된 형식·주소, 저장 한도, 기존 사진·취향·전체 백업 보존, 명시적 보유 연결, 기존 옷 사진 보존, UI 취소·재실행, 저장 실패, 계정/옷장 교체, 늦은 파일 읽기.
- 실제 Chrome의 **합성 DOM**에서 추출 관련 10개 검사 통과. 실제 주문 DOM을 검증한 것과 구분한다.
- 실제 Chrome 앱: 합성 주문 5개 확인 → 3개 선택 저장 → 새로고침 유지 → 배송 완료 1개만 종류·색 확인 후 보유 연결. 취소·반품은 장부에 유지. 390px 화면에서 가로 넘침 없음 확인.
- 문법 검사와 앱/확장 빌드 성공. 증거: `pc-verification/order-import-20261018/`.

## 실주문 검증 상태와 남은 일

- 사용자가 로컬 설치·실제 주문내역 검증을 승인했다.
- 브라우저 도구가 `chrome://extensions/` 접근을 보안 정책으로 차단했다. 우회하지 않았다. 사용자가 직접 로컬 확장을 로드하는 단계와 무신사 로그인은 대기 중이다.
- 사용자는 현재 Windows PC를 사용한다고 정정했다. 앞서 Mac 폴더를 안내한 것으로 Windows 설치가 된 것은 아니다. 새 앱 HTML·확장·Windows 설치 안내를 포함한 `app/dist/eoul-orders-windows-20261018.zip`을 별도로 만들었다. 개인 사진·구매내역·비밀번호는 없다. Google Drive 전송은 비공개 코드의 외부 전송이라는 자동 승인 검토 결과로 거절되었고, 이후 사용자가 업로드 대신 Windows에서 하는 방법 안내를 요청했다. Drive 업로드나 GitHub push는 하지 않았다.
- **실제 무신사 주문 카드 추출, 확장 컨텍스트의 실행/복사/파일 다운로드는 아직 미검증**이다. 현재 추출기는 보수적인 시험 구현이며 실주문 DOM에 맞춰 보완할 수 있다. ‘무신사 연동 완료’로 표현하지 않는다.
- 실주문 검증 시 이름·주문번호·주소 등 원문이나 개인 구매내역을 테스트 fixture, 로그, Git에 넣지 않는다. 필요한 일반 구조만 합성 자료로 재현한다.
- 현재 페이지에 로딩된 카드만 읽으며 자동 페이지 넘김·전체 기간 수집·백그라운드 동기화는 없다. 삭제·교환·부분 반품의 항목별 정합성은 실주문으로 확인해야 한다.
- 모바일 네이티브 앱 연동, iPhone Safari 확장, 다른 쇼핑몰, 공식 제휴 API·약관 검토는 미완료다. 공공 서비스로 낼 준비가 끝났다는 의미가 아니다.
- 수익·반복 사용·추천 효용은 이번 기술 검사로 증명하지 않는다. 계정이 연결된 앱에서는 기존 구매 기록 동기화 정책이 적용된다.

## 다시 빌드하기

```sh
cd app
npm ci --ignore-scripts
npm test
npm run build:order-extension
node tools/build.mjs --out /private/tmp/eoul-order-import-preview/index.html
```

확장 폴더: `app/dist/musinsa-orders-extension`. Chrome 확장 관리 화면에서 개발자 모드 → 압축해제된 확장 프로그램 로드로 **사용자가 직접** 선택한다. 사진이 포함된 개인 HTML이나 `app/data/`를 이 폴더에 복사하지 않는다. 확장과 빌드 HTML은 Git에 넣지 않는다.

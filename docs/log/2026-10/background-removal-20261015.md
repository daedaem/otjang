# 배경 지우기 시험과 적용 (2026-10-15, Claude)

> 문서 시점: 2026-10-15. 당시의 검토·구현 기록을 보존한 자료입니다. 현재 결정·우선순위·운영 상태는 [최신 문서 목차](../../README.md)를 확인합니다. 아래의 “지금·완료·다음”은 별도 갱신 표시가 없으면 당시 기준입니다.

**목표**: 옷 사진에서 배경을 지워 옷장 화면을 깔끔하게 만든다. 사진은 기기 밖으로 보내지 않는다.

**사전에 정한 통과 기준**(`toolkit-20261014.md` 3절)
- 코드와 가중치 모두 상업적으로 써도 되는 라이선스
- 처음 내려받는 양 20MB 이하
- iPhone에서 사진 1장 5초 이내
- 실패해도 원래 사진으로 등록을 계속할 수 있음

20MB와 5초는 Claude가 제안한 값이고, 사용자가 아직 확정하지 않았다.

## 시험한 것

**시험 사진**: 개인 사진은 쓰지 않았다.
- 상품 목록에 있는 공개 상품 사진 7장(셔츠, 치노, 트러커, 니트, 티셔츠, 해링턴, 데님)을 골랐다.
- 상품 사진의 배경을 덜어 정답 영역을 만들었다.
- 그 옷을 나무·이불 느낌의 질감과 줄무늬가 있는 배경(900×1200) 위 임의 위치에 합성했다.
- 모델이 옷을 입은 사진 2장(니트, 데님)은 정답 영역이 사람 전체로 잡혀 정확도를 매길 수 없어서 빼고, 눈으로만 확인했다.

**정확도 기준**: 정답 영역과 모델이 찾은 영역이 겹치는 비율(IoU)이다. 1.0이 완전히 일치.

| 후보 | 크기 | 방식 | 정확도(IoU, 5장) | 속도 |
|---|---|---|---|---|
| SlimSAM-77 (`Xenova/slimsam-77-uniform`, Apache-2.0) | 13.8MB(q8) | 사용자가 옷을 누름 | 0.93~0.98. 단, 아래 고르는 규칙을 썼을 때. 가장 높은 점수를 고르는 규칙만으로는 해링턴이 0.00 | 브라우저 WASM 스레드 1개: **9~14초**/장. 서버 네이티브 1.2~3.5초 |
| **U-2-Netp** (`BritishWerewolf/U-2-Netp`, Apache-2.0 / rembg 변환 MIT) | **4.6MB** | 자동 | **0.95~0.99** (셔츠 0.953, 치노 0.966, 트러커 0.981, 티셔츠 0.984, 해링턴 0.991) | 브라우저 WASM 스레드 1개: **1.6~1.9초**/장. 서버 네이티브 0.4~0.8초 |

**SlimSAM의 마스크 고르기**
- 한 번 누를 때마다 후보 영역 3개가 나온다.
- 점수가 가장 높은 것, 가장 넓은 것, 마지막 것 중 어느 규칙도 5장을 모두 맞히지 못했다.
- "넓이 2~80%인 후보 중 점수가 가장 높은 것"으로 고르면 5장 모두 0.93 이상이었다.

**측정 환경**
- Chromium 141(Playwright), 2.1GHz 서버 vCPU 4개, WASM 스레드 1개
- 스레드를 1개로 둔 이유: GitHub Pages는 여러 스레드에 필요한 교차 출처 격리(COOP/COEP) 헤더를 보낼 수 없다.
- 모델과 런타임 파일은 받아 둔 같은 바이트를 브라우저에 그대로 제공했다.

**앱에서 실제로 돌린 결과** (390px 화면, 해링턴 합성 사진)
- 동의하기 전에는 아무 파일도 받지 않았다.
- 처음 1회(도구 준비 포함) 2.8초, 두 번째 1.9초
- 결과의 모서리는 흰색(255,255,255), 가운데는 재킷 색
- '원래 배경으로'로 되돌린 뒤 다시 지웠을 때 동의를 다시 묻지 않았다.
- 저장하면 흰 배경 사진이 옷장 칸에 보였다.
- 페이지 오류 0건

**처음 내려받는 양** (2026-10-15 jsDelivr·Hugging Face 응답 기준)

## 결정

**U-2-Netp를 채택한다.**
- 사전 기준 중 라이선스, 내려받는 양(약 7MB), 실패 시 원본 유지를 충족한다.
- 속도는 이 서버 브라우저 기준 1.6~1.9초다. **iPhone에서 5초 이내인지는 측정하지 못했다.**

**SlimSAM은 넣지 않는다.**
- 브라우저 기준 9~14초로 5초 기준을 크게 넘는다.
- 대신 누른 옷만 골라낼 수 있어서 여러 벌이나 입은 사진에는 더 맞다. 여러 스레드나 WebGPU를 쓸 수 있게 되면 다시 검토한다.

## 앱 동작

**처음 쓸 때**
- "배경 지우기"를 누르면 먼저 동의를 묻는다: "도구(약 7MB)를 처음 한 번 내려받아요. 사진은 이 기기에서만 처리해요."
- 동의는 그 세션 동안 유지한다. 도구는 별도 작업 공간(module Worker)에서 한 번에 사진 1장만 처리한다. 120초가 지나면 멈춘다.

**처리 과정**
- 지금 사진(잘랐으면 자른 사진)을 320×320으로 줄여 옷이 있는 영역(마스크)을 만든다.
- 그 영역을 원래 크기로 부드럽게 늘려, 옷 테두리를 기준으로 6% 여백을 두고 자른다.
- 흰 배경 위에 옷을 놓은 JPEG로 만든다.
- 옷이 차지하는 면적이 3% 미만이거나 97% 초과면 "옷을 배경과 구분하지 못했어요"라고 알리고, 사진은 바꾸지 않는다.

**결과를 보고 고르기**
- 결과를 미리 보여 준다. '원래 배경으로'로 되돌릴 수 있다.
- 나중에 자르면 원래 사진에서 다시 시작하므로, 배경 지운 결과는 사라진다.
- 저장되는 것은 마지막에 보이는 사진 한 장뿐이다.

**실패해도 입력은 남는다**
- 실패, 거부, 시간 초과 때 사진, 종류, 이름이 그대로 남고, 다시 시도할 수 있다.
- 브랜드, 품명, 색은 이 기능으로 바꾸거나 추정하지 않는다.

**무결성**
- 받는 파일 4개(런타임, glue, WASM, 모델)를 모두 SHA-384로 확인한다. 다르면 쓰지 않는다.
- WASM과 모델은 확인한 바이트를 그대로 쓴다(`wasmBinary`, `InferenceSession.create(bytes)`).
- JS 2개는 확인한 뒤 같은 URL을 다시 `import`한다. ONNX Runtime은 자기 위치로 glue를 찾는데, blob: URL에서는 시작되지 않았다(실제 Chromium에서 확인). 그래서 CDN이 두 번의 요청에 서로 다른 파일을 주는 경우는 막지 못한다.
- 런타임 바이트를 바꿔치기하면 사용을 거부하는 것을 실제 Chromium에서 확인했다.

## 확인하지 않은 것

- **실제 iPhone·Android에서의 속도와 메모리**: 5초 기준 충족 여부를 모른다.
- **실제 사용자 사진**
  - 시험 사진은 깨끗한 상품 사진을 합성한 것이다.
  - 구겨진 옷, 침대·바닥 무늬, 옷걸이, 어두운 조명, 흰 옷을 흰 배경에 둔 경우는 시험하지 않았다.
- **입은 사진과 여러 벌이 함께 찍힌 사진**: 자동 방식은 가장 두드러진 물체를 고른다. 먼저 '옷만 자르기'로 한 벌만 남기기를 권하고, 이 경우는 시험하지 않았다.
- **배포 환경에서 실제 CDN·Hugging Face 응답으로 끝까지 실행되는지**: 이 환경에서는 같은 바이트를 로컬에서 제공해서 확인했다.

## 사용자 실기기 확인

1. iPhone에서 옷 한 벌을 바닥이나 침대에 놓고 찍는다.
2. "배경 지우기" → "내려받고 배경 지우기"를 누르고, 결과가 나올 때까지 걸린 시간을 잰다. 처음 한 번과 두 번째를 따로 잰다.
3. 결과 테두리가 잘리지 않았는지 본다. 이상하면 '원래 배경으로'를 눌러 원래 사진이 그대로 돌아오는지 확인한다.
4. 같은 사진을 '옷만 자르기'로 자른 뒤 배경 지우기를 다시 해 보고, 결과가 나아지는지 본다.

# 상품 검색 등록 본문 React 전환

기준은 #87을 병합한 master `f0645ca6933f117ea595a215a9c04fb89d631a3b`다. #87 최종42cf47e의 Node350개·CI11개·실제254개 두 실행(10.2분/10.1분)·미해결 검토0을 확인한 뒤 병합했다. [이전 기준 검사](react-add-search-baseline-20261027.md)와 직접 진입/Back 수정을 유지한다. R22 B7(L1)은 이 화면의 이름이 아니며 C4 검증 전 보류다.

## 이전 범위와 남은 공유 UI

`src/add-search`는 검색 입력·카탈로그·사용자 등록·공개 상품 정보(OPF)·수동 등록 진입을 지연 React entry로 렌더링한다. 도메인의 `findProducts`/`addOwnedProduct`, 기존 Input/등록 영수증·BK·사진·구매 명령은 UI에서 다시 만들지 않는다. 최근 옷의 기기 사진은 기존 `OwnedPhoto`를 사용하고, 상품은 원본 원격 표시만 한다.

**전체 React 완료가 아니다.** `RetailBridge`는 기존 국내/라쿠텐 패널 HTML/controller를 임시 재사용한다. 고정 옷장 막대·색 선택·메뉴·설명/확인 sheet도 기존 공통 코드다. 검색 결과와 공유 판매처 패널, 마지막 공통 단계에서 옮겨야 한다. 코디의 `WeatherSlot`도 같은 잔여 범위다. 실제 기기·복구 검증 전 바닐라/fallback은 제거하지 않는다.

## 유지한 사용자 계약

- 검색만으로 옷장·구매 결정·최근 요청을 쓰지 않는다. 입력 중의 로컬 공개 정보 검색과 명시 제출의 서버/판매처 검색을 나눈다. 입력이 달라지면 이전 제출 결과를 비우고, 요청 세대/화면 수명으로 늦은 응답을 무시한다.
- 실제 보유 선언은 기존 명령을 따른다. 공개 정보 선택만으로 보유/구매 완료를 만들지 않고 원래 OPF draft 변환기와 Input으로 보낸다. 별도 미완성/미래 등록 초안은 기존 계약으로 보호한다.
- 반대 성별 상품 표기, 사용자 등록의 종류·색·확인 수, OPF 코드/출처·가격/재고 없음·ODbL/데이터 링크를 유지한다. 확인 수를 읽지 못하면 1명으로 추정하지 않고 ‘확인 수 모름’으로 표시한다. 공개 공급 결과의 내부 제어 필드(savedGarment 등)는 받아들이지 않는다.
- React 클릭은 구형 전역 이벤트와 중복 실행되지 않는다. 직접 등록의 호환 표식 `data-reg-open`은 유지하고 이벤트 전파를 제어한다. 입력 전용 JS/CSS가 직접 등록 전에는 로드되지 않는지도 검사한다.

## 기존 공동 등록의 두 번 저장

옛 공동 등록은 옷 추가와 `eoul-d12-hang:reg` 부가정보 저장이 두 번이다. 이번 UI 이전은 이를 새 포맷/새 원자 명령으로 바꾸지 않는다. 저장 action을 공유 함수로 분리하되 기존 metadata 필드·개인 확인 수를 유지한다.

부가정보만 실패하면 같은 저장된 garment ID와 입력을 RAM에 남겨 다시 보관한다. Back/재실행의 입력 손실을 경고하고, 명시적으로 이 입력만 내려둘 수 있다. 내려두기는 옷/사진을 만들거나 지우지 않는다. 같은 대상 재시도가 두 벌을 만들지 않는지 확인한다.

검토 중 저장된 옷을 다른 창에서 삭제한 뒤 재시도하면 성공으로 표시하던 반례를 재현했다. 현재 보유 대상과 ID·종류·이름·생성 시각을 다시 확인해, 사라지거나 바뀐 대상은 성공 처리/재생성/다른 옷으로 대체하지 않는다. 입력과 오류 설명을 남긴다. 이 보호와 원자적인 snapshot 등록 영수증을 같은 기능으로 부르지 않는다.

## 구형 브랜드·링크 원문의 보호

원래 런타임 reader/writer는 BK가 거절하는 v99도 읽고 `{items,catalog}`만 다시 써서 미래 원문을 잃을 수 있었다. 실패 우선 `ca86e4e`의 새6개가 모두 실패한 뒤 보완했다.

`legacy-registration.js`의 경량 순수 reader를 코어의 읽기 API로 노출한다. 무버전/v1은 지원하고 알 수 없는 정상 추가 필드는 보존한다. 미래/손상·중복 JSON 이름·잘못된 필드/URL은 거절한다. 런타임 초기 읽기와 저장 직전 모두 같은 reader를 쓰고, 현재 원문이 처음 읽은 값과 달라졌으면 덮지 않는다. 읽기 실패도 쓰기 차단으로 처리한다. 지원하지 않는 값을 빈 객체로 고쳐 저장하지 않는다.

이 비교는 **구형 metadata 전체 원문을 기준으로 한 충돌 거절**이며 다른 창의 변경을 자동 병합하지 않는다. 최신 기록을 확인/재실행해야 한다. 이전 버전으로 열린 탭까지 새 writer처럼 동작한다고 보장하지 않는다. 원문 보관 후 새로 시작은 기존 명시 복구 경로이고, 원문을 읽지 못한 상태에서 임의 초기화하지 않는다.

새 reader import/API 외 코어 본문과 BK 전체(검증·분류·형식/한도·적용·복원·undo), Input/등록 영수증·사진 복구·인증/AI 비용 한도·공통 라우터는 [원문 대조](evidence/add-search/preserved.json)로 확인한다. 기존 저장 키/스키마·사진 형식·예산/구매 명령을 변경하지 않는다.

## 실제 검증과 미검증

- Node356개/fail0/skip0, metadata 집중24개와 빌드 통과. 기존 VM 검사에는 새 순수 reader의 실제 구현만 주입했고 기존 assert는 유지했다.
- 전환 전14개와 새 React의 같은14개가 통과했다. 추가 브라우저 검사에는 종류/색/성별 표기, metadata 실패/같은 대상 재시도·다른 창 삭제, 외부 제어 ID 무시, 미래 원문의 초기/저장 전 보호·실제 파일 백업, 바닐라/런타임 실패 복귀, 글자 두 배/키보드, 실제 origin 중단 뒤 로컬 검색 재실행을 포함한다.
- 초기 전체272개는268개 통과/4개 실패였다. 실패 지점은 구형 직접 등록 버튼 표식이었다. 표식을 복구하고 지연 로딩 검사를 입력 전용 entry로 구분했으며, 실제 서버 정지 후 재실행을 포함한 해당4개가10.1초에 통과했다. retry/timeout/skip 설정은 바꾸지 않았다. 최종 전체 CI는 따로 확인한다.
- WebKit 백업은 기본 공유 경로 때문에 download 이벤트가 없었다. 현재 문서의 canShare를 고정해 **파일 내보내기 경로**에서 실제 JSON 안에 보호 원문 문자열(공백/개행 포함)이 그대로 들어 있는지 두 브라우저에서 확인했다. 실물 공유 창 검증으로 쓰지 않는다.
- [전후 캡처 원장](evidence/add-search/manifest.json)은 같은 viewport/검색·합성 공동 등록 정보, 사진 표시 끔으로 만든4장이다. 실제 API·개인 사진·키·새 배포는 사용하지 않았다. 사진 없는 행의 ‘사진 없음’/태그 표시는 전후 차이다. 실제 기기/사진 성능·C1/C2·AI 블라인드20·C4/L1·공개 출시/사업 효용은 미검증이다.

재현: `npm --prefix app/lite test`, `npm --prefix app/lite run build`, `npm --prefix app/lite run test:e2e -- e2e/add-search.spec.ts e2e/input.spec.ts`. 전후 캡처는 기준 커밋의 `app/lite`를 별도 임시 폴더로 내보내 빌드한 뒤 `CHROMIUM_PATH=... node app/lite/tools/capture-add-search.mjs BEFORE_DIST`로 만든다. 포트8796/8797은 loopback 전용이다.

# R22 B4 — 활용·수집 축과 내 진열장

기준 master는 B3c #81의 최종 head8fded37을 CI11개·실제150개 두 작업·미해결 검토0 확인 후 병합한 `1a401f1bcc936505085bb031044a10cccd3dc313`이다. 이 브랜치의 수집 기능은 후속 후보이며 활성 배포·실물 기기·사업 효용과 구분한다. B5 조합 AI·B6 거울 및 기존 화면 전체 React 전환은 남아 있다.

## 왜 나눴는가

착용을 늘리는 가치와 모으는 즐거움을 하나의 점수로 합치지 않는다. 후보 상세의 ‘활용·소장 가치 비교’에서 목적(모름/착용/소장/둘 다)과 직접 정한 시리즈를 적는다. `valueAxes`의 요약과 두 축을 따로 보여 준다. 소장 목적이면 같은 옷·낮은 착용 기록을 감점으로 쓰지 않는다. 희소성·한정·단종은 새로 추정하지 않는다.

새 조합 수는 실제 보유 옷만 기존 코디 공식 엔진으로 비교한다. 체험용을 제외하고 후보 색이 사진 추정이면 수치를 확정하지 않는다. 이는 최종 AI 순위·이유가 아니며 종류·색의 편집 규칙임을 표시한다(R2). 속성 모름/AI 확인 전은 동일하다는 근거로 쓰지 않는다. 비교 속성을 지어내지 않는다.

옷장의 ‘내 진열장’은 실제 보유 옷의 `profile.series`로 모은다. 후보 메모·목표·체험용을 보유 수에 넣지 않는다. 사용자 목표가 없으면 빈칸을 만들지 않고, 직접 정한1~100벌 목표만 표시한다. 빈칸은 필수품·구매 권유가 아니다. 목표 삭제는 보유 옷과 그 시리즈를 지우지 않는다. 같은 이름의 키는 기존 `detailKey`로 정규화해 중복 목표를 막는다.

## 저장과 실패 경계

`eoul-d12-hang:collection:v1`은 `{v:1,candidates,goals}`다. 후보별 목적·시리즈 원문(40자)·수정 시각과 명시 목표만 담는다. 최대1000개 후보·100개 목표이며 옷장200벌 한도를 늘리지 않는다. 새 코덱은 누락·미래/손상·중복 JSON 이름·모호한 목표 이름을 거절하고 원문을 덮지 않는다.

`collection/session.js`는 공유 저장 잠금에서 대상별 CAS로 적는다. 관련 없는 다른 후보/목표는 합치지만 같은 대상이 다른 창에서 바뀌면 현재 RAM 입력을 남기고 거절한다. 실패한 대상의 최초 기준을 다른 대상의 저장 성공으로 바꾸지 않는다. 이 반례를 읽기 전용 검토자가 독립 Map fixture로 재현했고, 로컬 회귀도 추가해 실패→수정을 확인했다. 쓰기 뒤 검증 읽기만 실패한 경우 정확히 같은 저장값은 재시도 시 다시 쓰지 않고 성공으로 확인한다.

보관하지 못한 후보와 아직 제출하지 않은 목표는 Back/내부 이동·재로드 전에 알린다. B3c의 여러 화면 이동 보호를 재사용해 보유 옷 편집창을 열어도 부모 입력 보호를 유지한다. 미래 원문은 백업 경로로 안내한다.

BK는 새 키의 사전 검증·출처 이름·조건부 메모/목표 건수만 확장했다. 원문 격리·format2·전체5MB·사진 IDB2·복원/undo 알고리즘은 유지한다. 사진은 보내지 않고 원본 상품 사진을 가공하지 않는다. 새 React entry는 코어 통로만 사용해 카탈로그를 다시 포함하지 않는다. 방문한 JS/CSS는 기존 런타임 그래프로 오프라인 캐시한다.

## 구매 기록과 연결

새 `collectionRecord`는 후보 메모와 실제 옷 정보의 목적을 구분하는 읽기 전용 문맥이다. 사용자가 보유 옷에서 고른 목적이 이전 후보 메모보다 우선한다. 후보 메모를 실제 소유 속성으로 자동 기록하지 않는다. 주문/수령/보유/착용/반품 command와 journey 형식은 바꾸지 않았다. 소장 목적에는 ‘계속 소장’과 기록한 착용 수를 표시하며, 기록0을 실제 미착용·실패로 바꾸지 않는다. 보유 편집창에서도 실제 기록 수와 한계를 표시한다.

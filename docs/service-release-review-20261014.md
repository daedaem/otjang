## 최소 운영 구조 제안

제품 범위를 새로 확정한 결정이 아니라, 기존 요구를 출시 가능하게 만들기 위한 제안이다.

1. 개인 옷/사진은 우선 기기 내 저장을 유지할 수 있다. 계정이 없다는 이유만으로 결함으로 평가하지 않는다. 대신 저장 범위, 삭제, 브라우저 초기화 시 한계, 백업·장애 복구를 사용자가 이해하고 실제로 수행할 수 있어야 한다.
2. 추천은 확정 보유/세부 속성 미확인/부족을 구분한다. 확인되지 않은 슬롯으로 구매 후보를 숨기지 않는다. 색·브랜드·소재를 추측으로 확정하는 대신 구매 판단에 필요한 경우 짧은 확인 질문 하나를 제시하는 방향을 검토한다.
3. 상품 공급 어댑터는 판매처 ID·상품 ID·상품명·브랜드의 근거·종류/색의 근거·가격 확인일·옵션/판매 상태의 확인 여부·원본 링크·이용 가능 범위를 관리한다. 없는 필드를 이름/사진 추측으로 채워 ‘공식 값’처럼 표시하지 않는다.
4. API 키를 사용하는 경우 서버에서 호출한다. 현재 정적 HTML에 키를 넣지 않는다. 서비스 운영비와 상품 API 비용은 별도 계산하고 유료 플랜이나 계약을 자동으로 신청하지 않는다.
5. 정식 앱은 다른 실험 앱과 저장 origin의 운영 경계를 확인한다. 전용 origin을 권고하되 새 주소로 이동하기 전에 옛 자료의 백업·이전·되돌리기 절차를 준비한다. 경로와 DB 이름만 바꿔 격리됐다고 표현하지 않는다.

IndexedDB는 같은 origin 정책을 따르고, 브라우저 용량/삭제 정책은 기기마다 다르다. 이는 데이터 유출 사고가 발생했다는 판단이 아니다. [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [브라우저 저장 용량과 삭제 정책](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

## Claude 검토 기록

사용자가 저장·이전 코드/구조의 Claude 전송을 승인해 Opus 5.5 높음에 전달했고 답변을 확인했다. Claude는 발췌 두 개와 설명만 읽었으며 전체 PR/저장소를 읽거나 실행하지 않았다고 명시했다. 발췌 범위에서 공개 검토용 알파를 막는 확정 문제는 없다고 했지만 정식 출시를 승인한 것은 아니다.

조건부 지적은 `indexedDB.open('eoul')`이 빈 구형 DB를 만드는 부작용이었다. 실제 어댑터는 `onupgradeneeded`에서 abort한다. 새 fake-indexeddb에 필요한 사진을 요청한 뒤 `databases()`가 빈 배열인 것을 확인해 해당 조건은 현재 코드에 적용되지 않음을 검증했다.

이후 사용자의 정식 서비스 검토 요청과 위 재현 실패·무료 API 공식 조건을 함께 전달해 출시 순서 및 사업·시스템 설계 검토를 요청했고 답변을 확인했다. Claude는 Node 재현 결과와 조사 요약만 근거로 검토했다. 공식 API 링크를 읽으려 했으나 실패했으므로 API 조건의 독립 재확인으로 계산하지 않는다. Codex의 공식 출처 확인과 구분한다.

## 제품 목표와 역할

- **사용자 결정:** 내 옷장의 빈틈 발견 → 실제 상품 후보 찾기 → 내 옷과 매칭 → 구매 지원 → 착용·반품 결과를 한 흐름으로 연결한다.
- **사용자 결정:** Claude Opus 5.5는 사업·제품·시스템 설계를 검토하고 Codex는 기능을 구현·검증한다.
- **인계 요구:** 공간에서 옷을 살펴보는 3D 옷장 경험을 유지한다. 데이터 안정성 작업의 우선순위가 3D 비전의 폐기를 뜻하지 않는다.
- **미검증 가설:** 이 흐름이 다른 패션 앱을 병행하는 수고를 줄이고 반복 사용으로 이어진다. 임의의 B2B 전환은 설계 범위에 없다.

**제안:** 기존 PWA, 모듈 경계를 둔 Spring 단일 서버, PostgreSQL을 유지한다. 계약 손실과 같은 계정 내 동기화를 먼저 해결하므로 서버·UI 전면 재작성이나 서비스 분리는 선행하지 않는다.

## 첫 변경: followup 계약 2와 손실 방지

관련 이슈: [반품·사이즈 기록의 서버 왕복 계약과 동기화 보호 #9](https://github.com/daedaem/otjang/issues/9). 아래 구현을 서버·Node 검사와 빌드로 확인했으며 브라우저 통합 검증은 별도 완료 기준이다.

1. V8은 기존 열·날짜를 보존하면서 `returned`, `sizeResult`, `returnReason`을 추가한다. DB에도 어휘·조건·필드 존재 제약을 둔다.
2. `/api/meta`가 계약 2 지원을 알린다. 새 서버의 데이터 쓰기는 `X-Eoul-Contract: 2`가 없으면 `409 CLIENT_UPGRADE_REQUIRED`로 거부한다.
3. 의미 없는 세부 값과 구 자료의 빠진 키는 `unknown`으로 정규화한다. 의미 있는 자리에 알 수 없는 어휘, 잘못된 날짜·판정이 오면 서버는 코드와 경로를 담은 422를 반환한다.
4. 클라이언트는 지원 확인 전에 반품·사이즈·사유가 있는 자료를 구 서버로 보내지 않는다. 높은 스키마의 파일도 정리·적용 전에 거부한다.
5. 정확히 성공한 push 본문 또는 적용한 pull 스냅샷으로 acknowledged baseline을 저장한다. 응답을 기다리는 동안 바뀐 로컬 값을 성공한 본문으로 간주하지 않는다.
6. baseline은 서버 origin·인증 계정·revision과 판정별 정규형 followup을 묶는다. 판정 없음, followup null, followup 있음은 서로 다르게 취급한다.
7. 첫 변경의 pull 병합은 판정별 followup에 한정한다. baseline·현재 로컬·원격을 비교하고 적용 직전에 다시 확인한다. 상태와 baseline은 같은 저장 단위로 기록한다.

| 비교 결과 | 적용 |
| --- | --- |
| 로컬만 변경 | 로컬 값을 유지 |
| 원격만 변경 | 계약·출처·revision 확인 뒤 원격 값 적용 |
| 양쪽 변경, 값 동일 | 동일한 값을 유지하고 baseline 갱신 |
| 양쪽 변경, 값 다름 | 판정별로 사용자가 서버 값 받기 또는 내 값 유지 선택 |

`내 값 유지`는 원격 기준점을 갱신하되 내 수정은 남겨 다음 push로 보낸다. 선택을 자동으로 대신하지 않는다. 기준점이 없거나 출처·revision·원격 필드가 불확실하면 손실 가능한 교체를 막는다. 기준점 없는 초기 복구는 검증한 완전 서버 자료를 기준으로 이 기기 결과 유지만 직접 선택할 수 있다. 성공한 upsert push는 원격 부재를 증명하지 못하고, 손실 없이 읽은 완전 pull만 이를 증명한다. 명시적인 원격 null은 키 누락과 구분해 직접 선택한다. 원격 목록의 누락을 삭제로 추정하지 않는다.

로컬 복원·파일 가져오기·초기화는 baseline을 무효화한다. baseline은 인증 계정과 서버 origin이 일치할 때만 사용한다. 같은 계정의 재로그인·새로고침은 검증한 기준점을 유지하고, 다른 계정이나 출처로 전환하면 이전 기준점으로 덮어쓰기를 허용하지 않는다. DB 복원 후 revision 재사용을 구분하는 서버 epoch는 후속 제안이며, 도입 전 DB 복원을 동기화 안전성이 보장된 행동으로 표시하지 않는다.

날짜는 양쪽에서 실제 달력을 검증한다. 기존 `before.at`, `after.at`, `followup.at`은 날짜 정밀도를 유지하며 없는 시각을 만들어 넣지 않는다. 시각/날짜 정밀도의 분리는 PurchaseCase 이전 단계에서 다룬다.

## 후속 구현 순서와 통과 조건

첫 용량 변경은 [record-limits.json](../contracts/record-limits.json)의 생성 한도(옷·판정·상품 각 500, 추천 기록 1,000, 비교 옷장 6)와 기존 목록 읽기 상한(각 2,000)을 분리한다. 이 값은 알파 운영 가정이다. 기존 501·600건을 절단하지 않고 수정·백업하며, 새 ID가 생성 한도를 넘는 일반 가져오기는 전체 거부한다. 엄격한 전체 백업 복원은 읽기 상한까지 허용하는 명시적 예외이고 백업의 역사적 계정 출처를 인증하지 않는다. 상한 초과·손상 원문은 자동 저장을 막고 원문 보관과 CAS 전체 복원으로 회복한다. 선택 정리는 백업·직접 선택·지문 확인을 요구하며 서버 삭제 전파는 포함하지 않는다.
브라우저에서 여는 복원 파일은 50 MiB 이하이며 형식·개별 사진 제한도 통과해야 한다. 사진이 많은 자체 백업이 이 파일 제한을 넘으면 앱 복원은 거부될 수 있다. 수량 상한만으로 저장 공간이나 모든 2,000건 백업의 복원을 보장하지 않는다.

같이 변경한 상품 흐름은 실제 추천 카드 → 후보 저장 성공 → 해당 상품과 내 옷의 비교 판정으로 이어진다. 현재 자동 상품 제안은 편집 카탈로그의 `white-tee` 범위다. 미지원 종류나 조건에 맞는 상품 부재를 임의 상품으로 채우지 않는다. 이 연결이 상품 수집·실시간 가격 검증이나 사진 착용을 구현한 것은 아니다.

받기 저장 실패 보호는 전체 state를 예전 사본으로 덮는 복구를 없애고 시작한 계정·state의 이번 변경만 선별 복구한다. 뒤 큐가 저장한 잠정 사본은 마지막 성공 원문과 그 저장 시점의 제출 출처·성공/실패 상태를 확인해 CAS 보상하며, 새 계정·복원과 사용자 중간 편집을 보존한다. 사진/상품 확인, 후속 결과/item 생애 상태/rack, 분류/종류/실측은 일관된 묶음으로 처리한다. 같은 값의 새 제출도 구분하고 실패한 제출을 건너뛰어 마지막 성공 후속 결과를 보존한다. 판정 객체의 참조를 유지하고 실제 후속 callback도 계정·state·시도를 확인한 뒤 성공 UI를 적용한다. 대기 중 생성 수는 복구될 기록까지 예약하고 적용 전 목록별 기존/받을 ID 합집합이 2,000개를 넘으면 변경·저장 없이 거부한다. 보상 자체의 실패 가능성은 안내하며 원자적 sync라고 부르지 않는다(ADR-17).

현재 일반 pull은 followup 이외의 미전송 로컬 기록을 서버 목록으로 교체할 수 있다. 로컬 삭제도 upsert 전송으로 서버에 전파되지 않으며 다시 받으면 항목이 나타날 수 있다. 용량 회귀 통과를 이 두 동기화 문제의 해결로 해석하지 않는다. `pickToCand`·구매·선택 정리의 뒤 큐 보상 저장도 실패할 수 있으므로 원자적 처리나 outbox 완료로 표시하지 않는다.
단계 A는 전체 기록의 내용·필요한 사진 지문을 기준점에 기록해 실제 송수신 범위를 비교하는 후속 설계다. 순수 모듈 초안은 별도 실험이며 앱의 실제 송수신에 통합하지 않았고 이번 게시에서 제외한다. 단계 B는 owner·종류·ID의 영구 삭제 보호를 서버에 두고 응답에서 오래된 tombstone을 줄여도 ID 재생성을 막는다. 최신 서버 목록에 없다는 사실이나 최신 If-Match만으로 삭제 여부를 확정하지 않는다. 명시적 복원은 generation을 바꿔 이전 세대 쓰기를 거부하는 설계이며 단계 B는 미구현이다.

v2 sync는 묶음 전체를 한 트랜잭션으로 적용한다. 실패 시 변경·성공 영수증을 남기지 않는다. 같은 본문 재시도는 같은 키를 사용하고, 수정한 본문은 새 묶음 키와 해당 op 키를 쓴다.

PurchaseCase는 현재 상태 행과 append-only 이벤트를 같은 트랜잭션에서 갱신한다. 상태 변경 이벤트는 `expectedCaseVersion`을 검사하며, 판매처 열기·앱으로 돌아오기는 상태를 바꾸지 않는다. 순서는 서버가 부여한 `server_seq`로 결정하고 기기 시각으로 덮어쓰지 않는다. 기존 `pickLog.returned`를 상품 반품으로 옮기지 않는다.

상품 추천은 확인한 판매처·조건·시점을 표시한다. 검증하지 않은 브랜드나 상품명을 사진으로 확정하거나, 확인한 범위 밖까지 포함한 최저가를 주장하지 않는다. 거친 사진의 속성·상품 동일성은 모름/추정/사용자 확인을 구분해야 한다.
실사 착용은 자연스러움, 원래 상품의 형태·색·무늬, 인물·자세·가림 물체의 보존을 같은 입력으로 평가한다. FASHN v1.5의 현재 결과는 채택 보류(ADR-14)이며 생성 성공을 품질 통과로 처리하지 않는다. Blender 자산·다른 합성 도구의 도입도 통합 화면과 이 기준의 검증이 필요하다. 합성 이미지가 실제 사이즈나 핏을 보증하지 않는다.

## 출시 전 판단

기술 완성도와 사업 가설은 따로 판단한다. 위 미완료 항목이 남은 상태는 플랫폼 개발 완료나 출시 준비 완료가 아니다. 코드 수정·테스트·브랜치 push·배포·공개 화면 확인도 각각의 증거로 남긴다.

사업 테스트는 실제 옷장으로 필요한 옷을 찾고, 근거가 있는 후보를 비교하고, 구매 또는 보류 이유를 설명할 수 있는지부터 확인한다. 반복 사용·차별화·수익 구조는 아직 가설이며 별도 실험이 필요하다. 서비스 시작 전 점수에 사용자 수·거래량·매출을 결핍 점수로 넣지 않고, 수치나 향후 점수를 예측해 채우지 않는다.

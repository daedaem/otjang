## 문제와 결과

기존 비교 화면의 판매처·가격·배송비·옵션·확인 시각은 별도 `localStorage(eoul:offers:v1)`에만 있었다. 옷장 백업과 다른 기기 로그인에서 이 기록이 빠졌고 계정 옷장을 교체해도 같은 기기 가격 캐시가 그대로 보였다.

schema 6 한도에 닿은 자료도 그대로 승급하도록 새 빈 필드 18바이트의 여유를 두었다(현재 850,018바이트, 기존 schema 4~6은 850,000바이트).

schema 7의 `offerRecords`를 옷·구매·착용 기록과 같은 스냅샷에 넣었다. 기존 IndexedDB 원자 저장, revision/epoch 충돌 검사, `.eoul` 백업/복원과 계정 동기화를 사용한다. API가 없는 정적 앱도 기기 저장·백업은 동작한다. 가격만 기록한 예시 체험에도 개인 데이터가 있으므로 빈 옷장으로 판정하지 않는다.

별도 가격 API·자동 병합 대신 기존 옷장 전체 충돌 선택을 유지한다. 가격 기록은 회원 코디 공유 데이터로 내보내지 않는다.

## 저장 계약

- 상품별 `{ref, requested, offers, refresh, touchedAt}` 배열. 상품 ID 또는 원 상품 HTTPS 주소를 유지한다.
- 상품 100개·상품당 12곳·가격 기록 200KiB. 필드·중복·원문을 바꾸는 정규화는 엄격히 검증한다.
- 상한에서 직접 기록을 자동 삭제하지 않는다. 비교 화면과 프로필 기록 정리에서 상품별로 확인 후 지운다.
- 가격 증가 쓰기는 전체 상태에 64KiB를 남긴다. 가격이 줄거나 그대로인 옷·보유 상태 변경은 이 가격 예산에 막히지 않는다.
- 검증한 전체 백업/계정 스냅샷 교체는 `replacingOffers`로 이 여유 예산만 건너뛴다. schema·총량·CAS 검사는 유지한다.
- schema 2~6은 가격 기록 없이 엄격 승급한다. 구형 백업을 교체 복원하면 가격 기록도 비우고, schema 7 백업은 파일의 가격 기록으로 교체한다. 서버는 현재 형식만 쓰기로 받는다.

## 기존 자료 이전과 장애 복구

1. 초기화/schema 7 미만 승급에서만 구형 가격 원문을 읽어 같은 저장에 포함한다. 구형 누락 사진을 확인 후 가져오는 경로도 같다.
2. 원문을 삭제하지 않는다. 실패하면 원래 기록을 유지하고 성공 후 재시작은 schema 7 경계로 중복 이전하지 않는다.
3. 손상/용량 초과 가격 때문에 정상 옷장 사용을 막지 않는다. 가격 이전만 보류하고 관리 화면에 사유와 원문 JSON 받기·명시적 재시도를 제공한다. 먼저 원문과 옷장 백업을 각각 보관하고 기록을 정리한다.
4. 백업 복원/계정 교체 뒤 남은 원문을 자동 재수입하지 않는다. 수동 재시도도 새 가격 기록이 있으면 자동 병합하지 않는다.
5. 전체 삭제는 구형 가격 원문도 보호된 삭제 범위에 포함한다. 삭제 실패 시 `erase-pending`을 남겨 부팅 시 재수입을 차단한다. 로그아웃·계정 삭제 시 기기 자료 유지 정책은 기존과 같다.

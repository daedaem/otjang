별도 가격 API·자동 병합 대신 기존 옷장 전체 충돌 선택을 유지한다. 가격 기록은 회원 코디 공유 데이터로 내보내지 않는다.

## 저장 계약

- 상품별 `{ref, requested, offers, refresh, touchedAt}` 배열. 상품 ID 또는 원 상품 HTTPS 주소를 유지한다.
- 상품 100개·상품당 12곳·가격 기록 200KiB. 필드·중복·원문을 바꾸는 정규화는 엄격히 검증한다.
- 상한에서 직접 기록을 자동 삭제하지 않는다. 비교 화면과 프로필 기록 정리에서 상품별로 확인 후 지운다.
- 가격·착용 기록의 합계 바이트가 늘 때에는 구매 여정이 향후 보유 변경용 680KiB까지 차는 경우와 옷 몫 64KiB를 합쳐도 전체 한도 안에 들어가야 한다. 이미 꽉 찬 스냅샷의 읽기·감축과 기록 합계가 늘지 않는 변경은 유지한다.
- 검증한 전체 백업/계정 스냅샷 교체는 `replacingNotes`로 이 여유 예산만 건너뛴다. schema·총량·CAS 검사는 유지한다.
- schema 2~6은 가격 기록 없이 엄격 승급한다. 구형 백업을 교체 복원하면 가격 기록도 비우고, schema 7 백업은 파일의 가격 기록으로 교체한다. 서버는 현재 형식만 쓰기로 받는다.

## 기존 자료 이전과 장애 복구

1. 초기화/schema 7 미만 승급에서만 구형 가격 원문을 읽어 같은 저장에 포함한다. 구형 누락 사진을 확인 후 가져오는 경로도 같다.
2. 원문을 삭제하지 않는다. 실패하면 원래 기록을 유지하고 성공 후 재시작은 schema 7 경계로 중복 이전하지 않는다.
3. 손상/용량 초과 가격 때문에 정상 옷장 사용을 막지 않는다. 가격 이전만 보류하고 관리 화면에 사유와 원문 JSON 받기·명시적 재시도를 제공한다. 먼저 원문과 옷장 백업을 각각 보관하고 기록을 정리한다.
4. 백업 복원/계정 교체 뒤 남은 원문을 자동 재수입하지 않는다. 수동 재시도도 새 가격 기록이 있으면 자동 병합하지 않는다.
5. 전체 삭제는 구형 가격 원문도 보호된 삭제 범위에 포함한다. 삭제 실패 시 `erase-pending`을 남겨 부팅 시 재수입을 차단한다. 로그아웃·계정 삭제 시 기기 자료 유지 정책은 기존과 같다.

## 비동기 입력 보호

- 편집/삭제 확인의 계정, epoch, 외부 스냅샷 세대, 상품 기록을 확인한다. 다른 계정/탭의 옷장으로 바뀐 뒤 오래된 입력이나 삭제 확인을 적용하지 않는다.

### Opus 리뷰 반영

Opus는 별도 작업 공간에서 첫 커밋의 앱 476개/서버 34개(모델 1개 생략)를 직접 재검증했다. 필수 수정은 가격과 착용 기록이 향후 반품·수령 저장 공간을 밀어내는 문제였다. 기존의 ‘지금 64KiB 남기기’만으로 미래 구매 기록 600/680KiB를 보장하지 못한다는 지적을 수용해 위 공유 예산으로 바꿨다. 기존 사진·기록을 자동 삭제해서 공간을 만들지 않는다.

증가 쓰기의 계산은 `전체 JSON 바이트 + max(0, 696320 - 구매 여정 JSON 바이트) + 65536 <= 850018`이다. 가격과 착용 기록 합계가 증가할 때 한 곳에서 검사한다. 200KiB 가격과 착용 1000개는 각각의 최대 상한이며 동시에 모두 채울 수 있다는 보장이 아니다. 큰 기존 스냅샷은 읽기·백업·감축을 허용하고, 명시적 백업/계정 교체는 전체 검증 한도 안에서 보존한다. 옷·취향 등 다른 메타데이터를 무제한 늘릴 공간까지 보장하지 않는다.

새 회귀 검사는 이전 코드가 허용하던 초기 대용량 가격과 착용 메모를 각각 거부하고, 허용된 혼합 기록과 옷 200벌을 먼저 저장한 뒤 600KiB를 넘는 실제 반품 전환이 680KiB 안에서 성공하는지 확인한다. 격리한 이전 코드에서는 거부 검사 두 개가 실제로 실패했다.

두 번째 리뷰는 이 보호 문제의 해결을 확인했고, 한도 거절을 저장 고장으로 표시하는 화면을 추가 지적했다. `offer-budget`은 저장 오류 상태로 올리지 않는다. 착용 기록 저장에서는 기존 자료 보존 안내와 기록 정리·백업을 보여 주고, 가격 입력에서는 입력을 유지하며 같은 정리 경로를 제공한다. 가격·착용 기록 사용량/현재 한도/추가 여유는 저장 검사와 같은 계산으로 표시한다. 전체 메타데이터 사용량이 낮아도 메모 예산의 90%에서 정리 안내를 보여 준다. 기록 정리 후 실제 착용 재시도 성공까지 번들 회귀 시험으로 고정했다.

### 최종 리뷰와 브라우저 확인

Opus는 구현 커밋 `0be8f3d`를 별도 환경에서 다시 검사해 앱 482개/서버 34개(모델 1개 생략)를 확인하고 PR #24의 필수 지적이 해결됐다고 승인했다. 100벌·전체 사용량 약 10%인 메모 한도 사례를 재현했고, 자신의 Chromium 390px에서 한도 안내·기록 정리 수치와 가로 넘침/페이지 오류도 확인했다고 보고했다. 이는 Opus 환경의 보고이며 실제 휴대폰 확인은 아니다.

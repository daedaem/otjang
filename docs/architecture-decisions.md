# 설계 선택과 다시 검토할 조건

기준일: 2026-10-14. 실제 소스의 선택과 Claude Opus 5.5의 후속 설계 제안을 구분한다. `현재`와 `이번 구현`은 코드 구조, `제안`은 후속 설계다. 자동 검증 결과는 [검증 기록](verification-2026-10-13.md)을 따르며 실제로 하지 않은 토론·승인·측정을 합의로 기록하지 않는다.
읽기 연결: [개발자 인수인계](developer-handover.md), [알파 실행 순서](system-design-alpha.md), [서버 현재 계약](../server/OPERATIONS-BETA.md). 최초 Claude 검토는 `76eb156` 소스 기준이었으며 당시 실행 없는 점수는 현재 코드 평가로 재사용하지 않는다.

## ADR-01 · 기존 PWA와 Spring/PostgreSQL 유지

- **문제:** 제품 흐름을 확장하면서도 반품 손실·동기화 계약을 먼저 고쳐야 한다.
- **고른 것:** 현재 PWA/HTML·JS와 Spring Boot 4.1.1/Java 21/PostgreSQL 16 유지. identity/wardrobe/purchase/catalog/evidence/sync/ops의 모듈 경계 강화는 제안이다.
- **대안 보류:** React·네이티브 전면 재작성이나 마이크로서비스 분리는 데이터 계약 결함을 바로 해결하지 않고 배포·트랜잭션 경계를 늘린다.
- **비용·제약:** app.html에 상태·화면 책임이 모여 있다. 서버는 단일 프로세스 운영과 owner 단위 잠금의 한계를 갖는다.
- **코드 근거:** [build.mjs](../app/build.mjs), [pom.xml](../server/pom.xml), [OtjangApplication](../server/src/main/java/otjang/OtjangApplication.java).
- **검증 범위:** 서버 라이브러리 컴파일·PostgreSQL 테스트 확인. 실제 기기 성능·운영 확장성은 미검증이다.
- **재검토 조건:** 측정된 성능 병목, OS 공유 기능 요구, 독립 배포 필요가 생길 때 해당 경계만 비교한다.

## ADR-02 · 순수 규칙과 JS/Java 교차 검증

- **문제:** 서버 없는 계산과 서버 API 계산이 같은 입력에 다른 판단을 내릴 수 있다.
- **고른 것:** 현재 판정·코디·상품 순위의 핵심 규칙을 순수 모듈에 두고 골든 결과로 교차 비교한다.
- **대안 보류:** 모든 계산을 서버 호출로 옮기면 로컬 사용이 네트워크에 의존한다. 공통 WASM/별도 규칙 서비스를 도입할 근거는 아직 없다.
- **비용·제약:** 두 언어의 코드와 어휘를 함께 유지해야 한다. `needs.js`·편집 추천 `pick.js`·실제 상품 추천 `discovery.js` 전체에 대응 Java가 있는 것은 아니다.
- **코드 근거:** [judge.js](../app/src/judge.js), [domain/](../server/src/main/java/otjang/domain/), [GoldenParityTest](../server/src/test/java/otjang/domain/GoldenParityTest.java).
- **검증 범위:** 골든 사례의 결과 일치는 확인한다. 그것이 추천 정확도나 사용자 취향 적합성을 증명하지는 않는다.
- **재검토 조건:** 언어 간 누락이 반복되거나 규칙 변경 비용이 실제 병목이 되면 공통 표현을 평가한다.

## ADR-03 · 모름·속성 초안·상품 동일성 분리

- **문제:** 대충 찍은 사진이나 비슷한 상품 이미지에서 브랜드·품명·속성을 확정하면 잘못된 비교가 된다.
- **고른 것:** 현재 모르는 값은 비워 두고 `assessment`로 보류/부분 판단한다. 색 초안과 사용자 확인, 상품 후보와 동일 상품 확인을 구분한다.
- **대안 보류:** 사진만으로 브랜드·상품명·핏을 자동 확정하는 기능은 근거와 검증이 없다. 기본 유료 AI 호출도 사용자 결정 없이 넣지 않는다.
- **비용·제약:** 사용자 확인 단계가 필요하고 초반 추천 범위가 좁아질 수 있다. 사진 품질 안내는 범용 상품 식별·블러 측정 모델이 아니다.
- **코드 근거:** [wardrobe.js](../app/src/wardrobe.js)의 `assessment`/사진 전이, [photo-intake.js](../app/src/photo-intake.js), [judge.js](../app/src/judge.js).
- **검증 범위:** `readiness`·`intake-integration`·`colorguess` 및 Java `UnknownAssessmentTest`가 계산 경계를 확인한다. 실제 사진 품질은 별도 확인이다.
- **재검토 조건:** 허용된 모델/상품 근거와 실사진 평가가 마련되면 동의·비용·실패 시 모름 처리를 포함해 제안한다.

## ADR-04 · API 거부와 로컬 정규화의 경계

- **문제:** 서버 cleaner가 알 수 없는 반품 결과를 null로 정리하면 성공 응답 뒤 기록이 사라진다.
- **고른 것:** 이번 계약 2는 의미 있는 잘못된 값을 API에서 422로 거부한다. 오래된 로컬 자료의 빠진 키·해당하지 않는 enum은 정규화한다.
- **대안 보류:** 모두 조용히 정리하면 데이터 손실이 성공으로 보인다. 반대로 모든 옛 파일을 거부하면 정상 백업 호환성을 잃는다.
- **비용·제약:** 로컬 cleaner와 서버 validator의 차이를 명시해야 한다. 높은 파일 스키마는 cleaner 호출 전에 차단한다. 날짜는 실제 달력의 날짜 정밀도를 유지한다.
- **코드 근거:** [FollowupWriteValidator](../server/src/main/java/otjang/api/FollowupWriteValidator.java), [wardrobe.js](../app/src/wardrobe.js), [beta.js](../app/src/beta.js), [공유 fixture](../contracts/followup-contract.json).
- **검증 범위:** 88개 유효/정규화/거부 사례와 API 코드/path, 무변경 검사를 포함한다. 전체 동기화 UI 통과는 아직 별도다.
- **재검토 조건:** 새 outcome·enum·스키마 도입 시 서버 확장·클라이언트 이전·구버전 보호 순서를 다시 정한다.

## ADR-05 · 추가 전용 DB 확장과 DB 불변식

- **문제:** 앱/API 검사를 빠뜨려도 기존 기록과 후속 필드 조합을 DB가 지켜야 한다.
- **고른 것:** V8은 반품 outcome과 두 enum 열을 추가하고 기존 날짜·메모를 보존한다. enum 범위·조건·NULL 존재 관계를 check로 제한한다.
- **대안 보류:** 기존 날짜에 가짜 시각을 채우거나 실행된 V5를 편집하지 않는다. PurchaseCase 이전의 시간 정밀도 설계는 별도 변경이다.
- **비용·제약:** 새 필드 없는 기존 후속 기록은 `unknown`이다. 제약과 정리기를 함께 바꾸고 이전된 행의 무손실을 확인해야 한다.
- **코드 근거:** [V8](../server/src/main/resources/db/migration/V8__followup_contract_two.sql), [DecisionEntity](../server/src/main/java/otjang/persistence/DecisionEntity.java), [ItemMapper](../server/src/main/java/otjang/service/ItemMapper.java).
- **검증 범위:** PostgreSQL에서 V7→V8 이전과 잘못된 조합 거부를 검사했다. 운영 DB 이전·롤백·복구 실행은 별도다.
- **재검토 조건:** 새로운 계약을 추가할 때 먼저 expand와 이전 계획을 마련하고 기존 행·구버전의 동작을 확인한다.

## ADR-06 · 브라우저 저장의 현재 형태와 단계별 정본

- **문제:** 개인 사용은 서버 없이 가능해야 하고, 로그인 계정·저장 실패로 자료가 섞이거나 오래된 복사본이 올라오면 안 된다.
- **고른 것:** IndexedDB 상태 JSON을 계정별 마지막 성공 원문과 비교한 뒤 저장한다. 같은 탭은 직렬화하고, 다른 탭은 CAS와 Web Lock으로 비교한다. 검증된 읽기 뒤 쓰기만 실패한 경우 localStorage로 복구한다. 계정 키는 origin+인증 ownerId다. 알파는 브라우저 우선, 베타의 서버 정본/cache/outbox는 제안이다.
- **대안 보류:** 지금 모든 로컬 기록을 서버 정본이라고 선언하거나 DB 실패를 메모리 성공으로 숨기지 않는다. 사진/outbox의 별도 store 분리는 후속이다.
- **비용·제약:** 저장 시 전체 상태와 data URL을 다시 쓴다. revision만 비교하면 같은 번호의 다른 자료를 놓치므로 원문도 비교한다. 읽기 실패를 빈 값으로 낮추거나 충돌을 대체 저장으로 우회하지 않는다. Web Lock 없는 LS 쓰기는 중단하고 전체 파일 보관을 안내한다.
- **코드 근거:** [storage-cas.js](../app/src/storage-cas.js), [app.html](../app/src/app.html)의 `load`/`save`, [beta-ui.js](../app/src/beta-ui.js)의 `accountScope`/`enterAccount`.
- **검증 범위:** helper 14개와 실제 save/직전 저장 검사 함수 6개를 합성 어댑터로 검증했다. 실제 브라우저·물리적 두 탭 실행은 미검증이다.
- **재검토 조건:** 사진 크기·저장 지연·동시 수정이 측정되거나 비공개 베타를 시작할 때 별도 photos/outbox와 서버 정본 전환을 검증한다.

## ADR-07 · exact ack와 followup 3방향 비교

- **문제:** 손실 가능한 pull을 항상 막으면 정상 정정을 받지 못한다. meta 지원만 믿고 교체하면 미전송 로컬 수정을 잃는다.
- **고른 것:** baseline은 정확히 성공한 전송 본문/받은 스냅샷으로 만든다. 판정별 followup의 base/local/remote를 비교하고 진짜 충돌과 명시적 null 정정은 사용자가 직접 선택한다. 완전한 pull만 원격 부재를 증명한다. 기준점 없는 복구는 이 기기 값 유지 선택만 허용한다. 재로그인 후 `syncStamp`가 누락·무효여도 같은 origin·인증 owner의 유효한 ack가 있으면 그 `serverVersion`을 보내기 기준으로 복구한다.
- **대안 보류:** 자동 LWW와 기기 날짜 순서, 무조건 교체, 무조건 차단을 선택하지 않는다. 첫 변경에서 일반 필드 병합·outbox까지 확장하지 않는다.
- **비용·제약:** 적용 직전 재검사·정규형 fingerprint·저장 실패·baseline 무효화를 처리해야 한다. 알려진 ack revision 7을 최신 조회 revision 8로 바꾸면 다른 기기의 정정을 덮어쓸 수 있어 이전 기준을 유지하고 409로 멈춘다. 다른 계정·출처·손상 ack는 기준으로 사용하지 않는다. 서버 복원 epoch는 후속이며 누락을 삭제로 추정하지 않는다.
- **코드 근거:** [sync.js](../app/src/sync.js)의 ack/merge 함수, [app.html](../app/src/app.html)의 sync/확인 화면, [sync.test.cjs](../app/test/sync.test.cjs).
- **검증 범위:** 계약/병합과 실제 sync 함수의 합성 HTTP 회귀를 전체 Node 테스트에 포함했다. 실제 상태 정리·계정 진입을 거치는 재로그인 회귀를 더해 `sync-flow.test.cjs` 7개와 전체 188개를 확인했다. 정상 stamp는 기존에도 보호했고 누락·무효 stamp 예외를 수정했다. 실제 충돌 UI·두 기기 E2E 통과를 주장하지 않는다.
- **재검토 조건:** tombstone/변경 피드가 준비되면 이 임시 경계를 엔티티별 변경 적용으로 이전한다.

## ADR-08 · 조건부 쓰기·멱등과 동기화 원자성

- **문제:** 오래된 전체 상태의 덮어쓰기와 같은 import 재시도가 중복 데이터를 만들 수 있다.
- **고른 것:** 현재 owner 행 잠금/트랜잭션, If-Match, 응답 revision, owner+멱등 키/본문 해시 영수증을 쓴다. 계약 헤더 검사는 업무 변경·영수증 처리보다 먼저 한다.
- **대안 보류:** 무조건 덮어쓰기는 손실을 만든다. 현재 두 import를 v2 원자 묶음이라고 부르지 않는다. 후속 v2는 전부 성공/전부 롤백과 성공 시만 영수증을 제안한다.
- **비용·제약:** 서로 다른 엔티티의 수정도 owner 버전 충돌이 날 수 있다. wardrobe 성공 후 catalog 실패 가능성과 타임아웃 후 결과 불확실성이 남는다. 외부 exactly-once는 보장하지 않는다.
- **코드 근거:** [AuthenticatedRevisionFilter](../server/src/main/java/otjang/security/AuthenticatedRevisionFilter.java), [RevisionService](../server/src/main/java/otjang/service/RevisionService.java), [WardrobeService](../server/src/main/java/otjang/service/WardrobeService.java).
- **검증 범위:** API·동시성·오류 롤백·영수증 검사를 서버 테스트에서 확인했다. v2 sync/outbox/삭제 전파는 미구현이다.
- **재검토 조건:** 기기간 사용을 확대하기 전에 엔티티 version, op/batch 영수증, tombstone과 오프라인 재시도를 함께 검증한다.

## ADR-09 · 인증 owner 격리와 비공개 사진 수명

- **문제:** 계정 자료·개인 사진은 다른 계정에서 읽을 수 없어야 하고 실패한 저장 뒤 파일만 남을 수 있다.
- **고른 것:** 현재 초대 가입, BCrypt, 해시 bearer 세션, 인증 owner 조회, 비공개 `PhotoStore`를 사용한다. `PhotoLifecycle`이 잠금·참조·할당량·커밋/롤백 뒤 수거를 조정한다.
- **대안 보류:** 공개 사진 URL·클라이언트 ownerId 신뢰·평문 세션 저장을 사용하지 않는다. 객체 저장소와 다중 인스턴스 제한은 베타 이후 제안이다.
- **비용·제약:** DB와 파일을 함께 백업해야 한다. 강제 종료 고아 파일의 주기적 수거, 비밀번호 복구·기기 세션 관리·공유 rate limit은 남아 있다.
- **코드 근거:** [OwnerScope](../server/src/main/java/otjang/security/OwnerScope.java), [AuthService](../server/src/main/java/otjang/security/AuthService.java), [PhotoLifecycle](../server/src/main/java/otjang/store/PhotoLifecycle.java).
- **검증 범위:** 합성 계정 격리와 사진/API 테스트를 실행했다. 외부 보안 검토·실제 운영 장애·복구 검증은 수행 완료로 표시하지 않는다.
- **재검토 조건:** 비공개 베타 운영·복수 서버·스토리지 이동 전에 격리/삭제/복구 계약을 다시 검증한다.

## ADR-10 · 백업 범위를 구분하고 엄격히 복원

- **문제:** 공유 파일·브라우저 백업·서버 백업의 범위가 달라 복원 후 일부 기록이 없을 수 있다.
- **고른 것:** 현재 형식을 구분하고 높은 스키마는 사전 거부한다. 정상 옛 필드 누락은 알려진 기본값만 채우며 손상 자료를 조용히 일부 복원하지 않는다. 서버 restore는 확인·If-Match·트랜잭션을 요구한다.
- **대안 보류:** 공유 export를 전체 백업으로 쓰거나 복원 범위가 같다고 주장하지 않는다. 복원 전 snapshot/되돌리기와 통합 백업은 후속이다.
- **비용·제약:** 서버에는 pickLog/prefs/rack/others가 없어 브라우저 백업도 필요하다. 사용자 백업은 인증·세션·영수증이나 운영 DB/파일 복구를 대체하지 않는다.
- **코드 근거:** [beta.js](../app/src/beta.js), [TenantDataService](../server/src/main/java/otjang/service/TenantDataService.java), [백업 계약](../server/OPERATIONS-BETA.md#전체-백업과-계정-삭제).
- **검증 범위:** 옛 schema 2와 API backup/restore·거부 검사가 있다. 운영 덤프·사진의 빈 환경 복구, 복구 목표 시간은 미확인이다.
- **재검토 조건:** PurchaseCase/outbox/사진 저장소 변경 때 백업 범위·이전·되돌리기를 함께 갱신한다.

## ADR-11 · 실제 상품과 가격 근거를 입력 데이터에 한정

- **문제:** 사용자는 구체적인 브랜드·상품명·가격·추천 이유·구매 링크를 원하지만 자동 수집과 전체 시장 최저가는 미완료다.
- **고른 것:** 현재 편집/사용자 입력 상품의 출처·확인일·가격·사이즈 근거를 사용한다. 빌드가 카탈로그 구조/만료를 검사하고 재확인 실패 시 확인일을 갱신하지 않는다.
- **대안 보류:** 이름 유사성으로 동일 상품 확정, 없는 상품 생성, 검증 범위 밖 최저가 표현을 하지 않는다. 공식/제휴 수집의 현재 조건은 별도 확인한다.
- **비용·제약:** 목록 범위와 수동 확인에 추천이 제한된다. 후속 Product/Variant/Offer/Snapshot 구조와 판매처 조건 검증이 필요하다. 예전 공급자 조사 결과를 현재 정책으로 확정하지 않는다.
- **코드 근거:** [picks.json](../app/data/picks.json), [pick.js](../app/src/pick.js), [validate-catalog.mjs](../app/tools/validate-catalog.mjs), [recheck.mjs](../app/tools/recheck.mjs).
- **검증 범위:** 구조·만료·실패 날짜 보존은 자동 검사 대상이다. 상품 원문의 사실성, 결제 가능 재고/최종 가격은 판매처와 실사용 확인이 필요하다.
- **재검토 조건:** 허용된 공급 데이터·가격 조건·재확인 운영이 마련되면 상품 동일성과 offer별 출처를 분리해 도입한다.

## ADR-12 · 3D 경험 유지와 실사 핏 주장 제한

- **문제:** 공간에서 옷을 보고 싶은 비전과 현재 형태 자산의 표현 수준 사이에 차이가 있다.
- **고른 것:** 현재 Blender로 구운 방·옷 형태/빛/원단과 Three.js 표시를 유지한다. 종류로 그린 모습과 실제 상품·실사 착장을 구분한다.
- **대안 보류:** 데이터 계약 우선 작업을 3D 비전 폐기로 해석하지 않는다. 사진 한 장에서 실제 상품 형태·소재·정확한 핏을 재현한다고 주장하지 않는다.
- **비용·제약:** 지원 형태·자리·자산 크기가 제한되고 구운 빛은 천 흔들림에 따라 변하지 않는다. 시각 품질과 실제 모바일 성능은 별도 개선·측정 대상이다.
- **코드 근거:** [closet/index.js](../app/src/closet/index.js), [cloth.js](../app/src/closet/cloth.js), [Blender 제작 안내](../blender/README.md), [build.mjs](../app/build.mjs).
- **검증 범위:** 자산 포함/분리 빌드와 코드 검사는 표현의 설득력·핏 정확도를 입증하지 않는다. 실제 기기와 사용자 시각 평가가 남아 있다.
- **재검토 조건:** 품질 목표·비교 장면·기기 성능 기준을 정한 뒤 자산 개선, 2D 착장, 3D 표현의 역할을 사용자와 평가한다.

## ADR-13 · 구매 저장의 완료와 보상

- **문제:** 비동기 저장 실패를 기다리지 않고 완료를 알리면 구매 기록·보유 옷·화면이 실제 저장소와 달라진다. 기다리는 동안 다른 편집과 계정 전환도 일어날 수 있다.
- **고른 것:** 구매 버튼이 `saveBought`를 await하고 같은 계정·state의 중복 요청을 막는다. 저장 성공 뒤 해당 구매와 UI가 아직 유효할 때만 완료·초점 이동을 적용한다. 실패는 시도한 값과 동일한 구매 필드·객체만 되돌린다.
- **대안 보류:** 전체 이전 snapshot을 덮어쓰면 대기 중 다른 편집·새 계정·받은 자료를 잃는다. UI를 먼저 완료하거나 실패를 성공 토스트로 숨기지 않는다.
- **비용·제약:** 뒤의 고정 저장 큐가 잠정 구매를 포함하면 같은 계정의 수정된 사본을 마지막에 보상 저장한다. import-add가 배열을 바꾸며 같은 잠정 객체를 공유한 경우도 그 객체만 복구한다. 보상 저장까지 실패하면 저장소에 잠정 구매가 남을 수 있어 전체 백업·상태 확인을 안내한다. 이 동작을 원자적 저장이나 일반 outbox로 부르지 않는다.
- **코드 근거:** [app.html](../app/src/app.html)의 `saveBought`/구매 버튼/`save`, [purchase-persistence.test.cjs](../app/test/purchase-persistence.test.cjs).
- **검증 범위:** 실제 함수와 버튼·저장 큐를 합성 환경에서 실행한 회귀 15개, 최신 전체 Node 203개와 기본·모바일 빌드를 확인했다. 실제 브라우저·물리적 두 탭은 미검증이다.
- **재검토 조건:** 실패·다중 동작의 실제 브라우저 재현을 확인하고 구매 상태를 PurchaseCase로 통합할 때 작업 단위와 영속 보상/outbox를 함께 검토한다.

## ADR-14 · 가상 착용의 실행 성공과 채택 품질

- **문제:** 가상 착용 파일이 생성돼도 상품의 넓은 실루엣·소매·색·질감이 달라지거나 가림물이 사라지면 구매 판단에 쓸 수 없다.
- **확인한 사실:** 비공개 Windows GPU 시험에서 FASHN VTON v1.5 출력은 생성됐다. 대표 비교 이미지의 상품 실루엣·소매·색·질감을 직접 확인했고, 입력만 바꾼 제한 비교도 로컬 시험 기록에서 핏·소매 차이와 가림물 소실을 보고했다. 결과 보고서는 착용 품질 불합격으로 정정됐다. 원문 사진·결과·개인 촬영 정보는 이 저장소에 포함하지 않는다.
- **고른 것:** 현재 FASHN v1.5 결과의 서비스 채택을 보류하고 같은 방식의 반복 생성을 종료한다. “실제로 입지 않고 내 모습에 새 옷이 어울리는지 보여 주기”는 핵심 목표로 유지하며, 후기·실측은 이를 보조한다. 자연스러움, 상품 동일성, 원래 포즈·가림물·배경 보존을 각각 확인한다. 원본에서 보이지 않는 체형은 검증 불가로 남기며, 생성 이미지를 실측 핏·사이즈의 증거로 사용하지 않는다.
- **다음 비교의 조건:** 동일한 사람 사진과 동일한 상품 사진으로 정지 결과를 먼저 비교한다. 목선·어깨·소매·기장·품, 색·로고·무늬, 포즈와 가림물의 실패를 확인한다. 박시한 품 축소·소매 변경·휴대폰 소실은 평균 점수로 상쇄하지 않는다. 통과한 정지 결과가 있어야 영상화를 검토하며, 새 장면·닮은 모델·영상이 더 자연스럽다는 주장은 시험 전 가설로 남긴다. 모델 실행·사진 수신·품질 통과·웹앱 연결을 별개의 상태로 기록한다.
- **역할과 미검증 대안:** Blender의 공간형 옷장·옷 자산 제작 방향은 유지한다. Higgsfield의 [옷 교체 기능](https://higgsfield.ai/ai-clothes-changer)은 다음 비교 후보이며, 이번에 생성하거나 앱에 연결하지 않았다. 공식 설명도 세부 무늬·로고와 얼굴·몸의 차이가 남을 수 있음을 안내한다. 두 도구를 함께 쓴다는 사실만으로 착용 정확도가 입증되지는 않는다.
- **재검토 조건:** 사용자가 자연스럽다고 평가하고 상품의 형태·색·가림물 보존을 같은 기준으로 확인한 뒤, 전송 동의·제공자 조건·비용·작업 상태·실패 처리를 검증하고 앱 연결을 판단한다. 이 시험 결과로 알파 완성도나 사업 점수를 올리지 않는다.

## ADR-15 · 신규 생성 제한과 기존 기록 보존

- **문제:** 생성 한도를 읽기·정리 함수에도 적용하면 기존 옷·판정·상품이 조용히 잘린다. 추천 기록을 최근 100건만 남기는 방식도 구매 판단과 후속 결과의 근거를 잃는다. 잘못된 최신 저장 사본을 빈 예시 상태로 대체해 자동 저장하면 원문까지 잃을 수 있다.
- **고른 것:** [공유 계약](../contracts/record-limits.json)으로 신규 옷·판정·상품 500건, 추천 기록 1,000건, 비교 옷장 6묶음과 기존 자료 읽기 상한 2,000건을 구분한다. 신규 고유 ID가 늘어날 때만 생성 제한을 적용하고, 기존 초과 자료의 수정·후속 기록은 허용한다. 수치는 알파 운영 가정이며 실제 기기 성능·저장 공간의 보장이 아니다. 3D 자리 6개는 별도의 표시 제약이다.
- **가져오기·복원:** 일반 가져오기는 추가 또는 바꾸기 결과의 새 ID를 검사하고 초과하면 전체 거절한다. 기존 ID로 구성된 자료의 바꾸기는 읽기 상한 안에서 허용한다. 엄격한 전체 백업 형식의 명시적 복원과 기존 저장·완전 서버 snapshot은 2,000건까지 보존한다. 백업 형식은 과거 계정의 진위를 인증하지 않으며, JSON 파일의 50MB 제한도 별도로 적용한다.
- **원문 복구:** 상한 초과·읽기 실패·잘못된 저장 revision·동일 revision의 상이한 사본이면 해당 저장 범위의 편집과 동기화를 멈춘다. 원문을 그대로 내려받고 정상 전체 백업을 명시적으로 고른 뒤 기존 사본과 비교하는 CAS 저장이 성공해야 복구 잠금을 해제한다. 다른 계정 전환을 이전 복구 상태가 덮지 않는다.
- **정리와 저장 실패:** 오래된 기록을 자동 삭제하지 않는다. 사용자가 백업·선택·자료 지문·확인을 거쳐 고른 기록만 정리한다. 후보 등록·정리의 저장을 기다리고 실패하면 해당 변경을 되돌린다. 뒤의 저장 큐가 임시 변경을 포함했으면 같은 계정의 복구 사본을 마지막에 저장한다. 복구 저장도 실패할 수 있어 잔존 가능성을 알린다. 서버 삭제 동기화와 일반 outbox는 아직 없으므로 정리한 원격 기록이 다시 나타날 수 있다.
- **서버 경계:** 계정 행 잠금과 트랜잭션 안에서 신규 고유 ID와 기존 수를 먼저 검사한다. 한도 초과는 `422 ACCOUNT_LIMIT`이며 사진·행·receipt·revision을 일부 저장하지 않는다. 직접 서비스 호출도 같은 잠금을 사용한다. 엄격한 전체 복원은 일반 생성 경로와 분리한다.
- **코드 근거:** [app.html](../app/src/app.html)의 `chooseStoredCopy`/`canAdd`/`restoreRecovery`/`cleanupSelected`, [wardrobe.js](../app/src/wardrobe.js), [beta.js](../app/src/beta.js), [AccountCapacity.java](../server/src/main/java/otjang/service/AccountCapacity.java), [RecordLimits.java](../server/src/main/java/otjang/domain/RecordLimits.java).
- **검증 범위:** 실제 앱 함수와 저장 큐를 합성 어댑터로 실행한 용량 회귀 22개를 포함해 Node 231개가 통과했다. PostgreSQL 16 Testcontainers 서버 141개가 통과했다. 서버와 프런트 독립 소스 검토에서 추가 확정 P0/P1은 없었고, 프런트 집중 회귀 43개를 독립 재실행해 통과했다. 기본·웹·모바일 빌드와 생성 script 구문·계약 주입 검사를 통과했다. 검토자는 전체 테스트·빌드를 재실행하지 않았다. 실제 브라우저·물리적 기기·운영 용량 검증은 미실행이다.
- **재검토 조건:** 일반 미전송 자료의 pull 보존과 명시적 삭제/tombstone을 구현하고, 실제 자료 크기·사진 수·기기 성능과 복원 시험을 근거로 한도를 다시 정한다. 생성 한도 안이라는 이유로 전체 백업 크기나 브라우저 quota를 보장하지 않는다.

## ADR-16 · 추천한 실제 상품을 같은 후보로 비교

- **문제:** 필요한 옷 종류와 실제 상품을 보여 줘도 다시 상품명·브랜드·가격·링크를 입력해야 하면 옷장부터 구매 판단까지 이어지는 흐름이 끊긴다.
- **고른 것:** 실제 상품 카드의 `이 상품을 내 옷과 비교`가 표시된 상품을 그대로 후보에 넣고 저장 성공 뒤 그 후보의 판정 화면을 연다. 브랜드·상품명·가격·확인일·판매처 링크를 보존하고 추천 기록의 `candidateId`로 연결한다. 같은 상품의 중복 후보를 만들지 않는다.
- **실패·계정 경계:** 진행 중인 동일 후보 등록은 같은 저장 결과를 기다린다. 실패·거절이면 판정 화면으로 이동하지 않는다. 기다리는 사이 state나 계정이 바뀌면 새 계정에 같은 상품이 있어도 이전 작업이 이동시키지 않는다. 저장 실패 뒤 큐 복구의 한계는 ADR-15와 같다.
- **범위와 제약:** 현재 검증 카탈로그가 지원하는 흰 티 상품 흐름을 잇는다. 다른 필요한 종류의 상품을 만들어 내지 않으며, 전체 시장 최저가·실시간 재고·옷의 실사 착용 결과를 추가한 것이 아니다. 판매처 링크에서 현재 조건을 확인한다.
- **코드 근거:** [needs-ui.js](../app/src/needs-ui.js)의 `needOfferCard`/`compareNeedOffer`, [app.html](../app/src/app.html)의 `pickToCand`, [needs-offer-flow.test.cjs](../app/test/needs-offer-flow.test.cjs).
- **검증 범위:** 실제 카드·연결 함수의 합성 회귀 6개가 정확한 상품 속성·중복·상품 부재·실패·대기 중 계정 전환을 확인한다. Node 전체 231개와 빌드 검사에 포함되며 실제 브라우저 동선과 사용자 구매 판단 개선은 미검증이다.
- **재검토 조건:** 공급자와 상품 종류를 확대할 때 상품·판매 제안을 구분하는 영속 ID로 연결하고, 상품 변경·가격 갱신·실제 구매/후속 결과까지 같은 흐름으로 검증한다.

## ADR-17 · 받기 저장 실패의 범위와 편집 보존

- **문제:** 받기 저장이 실패하면 이전 state 전체를 돌려놓던 경로가 있었다. 로그아웃 응답을 기다리는 동안 시작한 받기가 나중에 실패하면 계정 자료로 개인 옷장을 덮을 수 있고, 뒤 저장 큐가 성공했어도 대기 중 사용자가 편집한 자료를 화면에서 없앨 수 있었다. 저장 실패의 복구와 정상 받기의 일반 자료 병합은 서로 다른 문제다.
- **고른 것:** `applySyncPull`은 시작한 state 객체·계정 저장 키·서버 출처·토큰을 고정하고, 같은 작업이 설치한 값만 선별 복구한다. 새 계정·새 state의 화면과 저장 안내는 바꾸지 않는다. 뒤 큐가 잠정 받기를 저장했으면 그 계정 키의 마지막 성공 원문과 target, 그 저장 시점의 제출 값·객체 참조·성공/실패 상태를 확인한 뒤 큐 끝에서 CAS 보상 저장한다. 명시적 전체 복원·가져오기로 기준점이 바뀐 새 작업은 이전 받기가 덮지 않는다.
- **연관 값:** 표시 사진과 상품 확인·출처를 함께 복구하고 개인 사진은 별도로 보존한다. 후속 결과와 연결 옷의 보유/처분 상태·구매 연도·3D 자리, 옛 follow와 구매/보류 선택, 분류·종류·실측도 서로 맞는 묶음으로 유지한다. 값이 같은 새 후속 제출도 객체 참조로 구분하되 실패한 제출을 성공 의도로 보존하지 않는다. 연속 제출 실패는 앞선 실패를 건너뛰고 마지막 성공 결과를 복구한다. 대기 중 폼이 참조하는 판정 객체는 유지하며, 연결 item 상태·연도·rack은 해당 시도가 설치한 값에 한해서 되돌린다. 복구할 예전 3D 자리는 사용자가 차지한 자리를 중복 점유하지 않는다.
- **용량 경계:** 받기 대기 중에는 복구할 기존 기록을 생성 수에 예약해, 원격 목록이 일시적으로 작아졌다는 이유로 새 기록을 한도 이상 만들지 않는다. 적용 전 옷·판정·상품 각각의 기존/받을 ID 합집합이 읽기 상한 2,000개를 넘으면 상태 변경·저장 0건으로 전체 거부한다. 기존 ID의 수정은 계속 허용하고 원문·전체 백업과 명시적 정리 경로를 안내한다.
- **대안 보류:** 전체 snapshot 복구는 다른 편집·계정 자료를 잃는다. 필드별 값만 복구하면 개인 사진에 옛 상품 확인 정보를 붙이거나 반품 결과와 보유 상태를 섞을 수 있다. 복구 시점의 최신 제출 의도를 과거 성공 사본에 적용하면 다른 실패한 제출과 섞이므로 저장마다 출처를 고정한다. 용량을 맞추려고 기록을 자르거나 최신 revision만 올려 쓰지 않는다.
- **비용·제약:** 보상 CAS도 충돌·실패·예외로 끝날 수 있다. 계정 범위별로 임시 받은 자료의 잔존 가능성을 안내하고 완전 복구를 주장하지 않는다. pending 중복 적용·보내기·받기·취소는 막는다. 이 보상은 일반 outbox나 원자적 동기화가 아니다.
- **코드 근거:** [app.html](../app/src/app.html)의 `applySyncPull`/`undoPullSnapshot`/`repairPullSnapshot`/`save`/`saveCommandProvenance`/`undoFollowupAttempt`/`canAdd`, [beta-ui.js](../app/src/beta-ui.js)의 실제 후속 제출 callback, [pull-persistence.test.cjs](../app/test/pull-persistence.test.cjs).
- **검증 범위:** 검증 대상 코드 `2cef23332dcae2270df5eb97512298fa0f8be6d7`의 신규 회귀 47개를 포함한 게시 범위 Node 278개가 통과했고 코드 3개 파일의 동결 원문/커밋 blob 바이트·SHA-256과 GitHub 기능 브랜치·초안 PR #10의 코드 SHA가 일치했다. 독립 검토자는 관련 회귀 90개를 직접 재실행하고 제보했던 연속 제출 예외의 해결을 확인했으며 추가 확정 P0/P1을 찾지 못했다. 전체 278개·빌드는 로그 확인이며 독립 전체 재실행은 아니다. 기본·웹·모바일 빌드와 각 HTML 14 scripts 구문·계약/복구/제출 출처 주입 검사도 통과했다. 소스 SHA·실행 근거와 중간 검토 이력은 [검증 기록](verification-2026-10-13.md)을 따르며 원격 코드 게시·실제 브라우저 검증·운영 배포를 구분한다.
- **재검토 조건:** 정상 받기에서 아직 남은 새/수정 옷·판정·상품의 미전송 자료 손실을 단계 A의 전체 기록 baseline·3방향 병합으로 해결한다. 단계 A 순수 모듈 초안은 앱 미통합이며 이번 게시 범위에 없다. 단계 B의 영구 삭제 ID 보호·조회·복원 generation과 실제 브라우저·두 기기 검증도 별도 완료가 필요하다.

## ADR-18 · 간단한 보유 등록과 실제 상품 추천을 하나의 흐름으로 연결

- **문제:** 사용자가 가장 중요하게 여긴 기능은 보유 옷을 쉽게 넣고, 그 옷과 어울리거나 등록 목록에서 빠진 종류의 실제 브랜드·품명 상품을 찾는 것이다. 앞선 간단 등록 시안은 사진·종류만 저장해도 조합에 쓸 속성이 부족했고, 기존 자동 상품 연결은 흰 티셔츠 중심이라 다른 종류는 상세 상품 입력을 다시 요구했다. 저장 보호 작업만으로 이 제품 문제를 해결했다고 판단하지 않았다.
- **고른 것:** `openEasyEntry`로 사진과 종류를 저장한다. 사진 없이 종류만 시작할 수도 있다. 보유 옷의 브랜드·품명·가격·실측은 필수가 아니다. 추천에서는 등록한 범위의 실제 상품을 먼저 보여 주고, 조합에 필요한 정보가 부족하면 `openAttributeCheck`로 우선 1~2벌의 빠진 종류·색·밝기·무늬·입을 느낌을 선택 카드로 확인한다. 이미 확인된 값과 사진·상품 확인·실측은 유지한다. 계절을 골랐을 때만 필요한 계절 정보도 묻는다.
- **추정과 확인:** `ColorGuess`·`PhotoIntake`는 이 브라우저에서 사진의 대표 색과 품질 안내를 제안한다. 사용자의 명시적 선택 전에는 확인된 속성으로 계산하지 않는다. 어둡거나 단색에 가까운 사진에서 근거가 부족하면 색 제안을 만들지 않는다. 「잘 모르겠어요」는 null/미확인으로 남기며 사진으로 브랜드·상품명·실측을 알아냈다고 표시하지 않는다.
- **상품 사실과 편집 분류:** [discovery-products.json](../app/data/discovery-products.json)은 2026-10-14 공식 한국 판매 페이지를 읽어 작성한 작은 수동 시드다. 12개 상품·9종류·6브랜드, 당시 표시 가격 확인 11개이며 UNIQLO 니트 가격은 null이다. H&M 의류 6개는 공식 무늬 설명까지 읽어 비교 속성을 구성했다. 밝기·격식·활용 계절 등은 `attrEvidence`에 편집 판단으로 표시한다. 다른 의류의 미확인 무늬를 무지로 채우지 않는다. 구조 검사는 출처 페이지를 독립적으로 다시 읽은 사실 검증을 대신하지 않는다.
- **추천 경계:** `WardrobeDiscovery.recommend`는 보유 기록만 사용한다. 확인된 의류 속성으로 추가 조합을 만들 수 있는 상품, 정보 확인 뒤 비교할 탐색 상품, 이미 가진 역할·강한 겹침·확인 전 같은 종류라 구매를 보류할 상품을 구분한다. 부족함은 「등록된 범위에 없음」이다. 편한 차림으로 확인된 옷을 단정한 출근·약속 역할까지 충족한다고 처리하지 않는다. 신발은 등록 목록에 없는 기능적 종류만 제안하며 신발 색 어울림·코디 수·착화감은 계산하지 않는다. 근거가 없으면 구매를 강제하지 않는다.
- **같은 상품 비교와 저장:** `compareDiscoveryProduct`는 표시된 상품을 현재 시드에서 다시 검사하고 브랜드·품명·품번·가격·확인일·판매 링크를 보존한 후보를 저장한다. 저장 성공 뒤 해당 후보의 판정 화면을 연다. 동일 상품 중복 탭·재시도는 같은 후보를 재사용하며, 실패·계정/state 전환·다른 탭 충돌이면 성공 이동하지 않는다. 실패한 잠정 변경만 되돌리고 뒤 큐의 같은 계정 사본에 CAS 보상을 시도한다. 이후 편집·연결된 후보는 보존한다. 보상도 실패할 수 있으므로 원자적 저장이나 outbox라고 부르지 않는다.
- **비교 진입의 입력 축소:** 상품 후보를 저장한 뒤에도 기존 `beforeForm`이 구매 전 마음 입력을 요구하는 추가 장애가 남았다. 새 카탈로그 후보는 `renderJudge`에서 `renderVerdict(..., null)`로 바로 결과를 보여 준다. 수동 후보도 「입력 없이 비교 결과 보기」를 선택할 수 있다. 미리보기는 새 `before`/판정 기록을 만들지 않고, 이미 사용자가 남긴 실제 before·진행 중/완료 판정의 경로는 유지한다. 미리보기의 계정·state·후보를 고정하고 오래된 버튼은 다른 기록을 바꾸지 못하게 한다. 결과 화면의 후보 수정·삭제 도구도 같은 경계를 따르며 상품 목록의 브랜드/확인가를 「직접 입력」으로 잘못 표시하지 않는다.
- **호환성:** 앱의 기존 저장 키를 유지한다. 별도 `easy-entry` 시안의 저장 namespace를 이식하거나 기존 사용자 자료를 초기화·이전하지 않는다. 기존 상세 편집과 흰 티셔츠 비교는 보조 경로로 남긴다.
- **대안 보류:** 입력 폼을 여러 화면으로만 쪼개는 것으로는 실제 상품 부족이 해결되지 않는다. 브랜드·품명 자동 인식, 미확인 기본값의 자동 확정, 확인 범위 밖 상품·가격·최저가 생성은 채택하지 않는다. 첫 추천 전에 10벌을 등록하게 하는 제안도 채택하지 않았다. 사진 여러 장 일괄 등록의 새 흐름은 후속 검토다.
- **코드 근거:** [entry-ui.js](../app/src/entry-ui.js)의 `openEasyEntry`/`openAttributeCheck`/`commitEasyChanges`, [discovery.js](../app/src/discovery.js)의 `inspectCatalog`/`recommend`, [needs-ui.js](../app/src/needs-ui.js)의 `wardrobeDiscovery`/`compareDiscoveryProduct`/`renderNeeds`, [build.mjs](../app/build.mjs)의 모듈·상품 시드 삽입과 검증.
- **검증 범위:** 첫 통합 코드 `3f80f6a4f23aa4fb1e8ca6b862408935274d3444`의 게시 대상 Node 350개가 통과했고 신규 72개(등록 27·순수 추천 30·상품 UI 15)는 독립 재실행했다. 실제 등록 → 짧은 속성 확인 → 실제 상품 카드 → 동일 후보 저장/비교의 합성 회귀도 포함한다. 독립 검토가 재현한 대기 중 객체 직접 편집 손실은 before/after 역변경 사본을 불변 복사해 해결했고 재현으로 확인했다. 실제 시드의 선택적 `attrEvidence` 복사 경로가 존재하지 않는 `W.clone`을 호출하던 문제도 고쳐 실제 시드·빌드 검사를 통과했다. 후속 결과 우선·사진 색 확인 UI 코드 `296eaf2bcbc7929bf2beb3736e0dae473fb9bfdd`는 게시 대상 Node 353개·독립 신규 75개(등록 29·순수 추천 30·상품 UI 16)와 세 빌드를 통과했고 두 P1 해결 이후 추가 확정 P0/P1은 없었다. 좋은 사진의 색 제안은 먼저 명시적으로 「맞아요」를 누르거나 다른 색을 고르게 하고, 근거가 약한 사진은 수동 선택을 바로 제공한다. 전체 결과·미실행 범위와 코드/미리보기 게시 상태는 [검증 기록](verification-2026-10-13.md)을 따른다.
- **최신 비교 진입 검증:** `b359d6002a8cac2521b9abfbcf2986d9aec008b9`의 게시 대상 Node 359개와 독립 핵심 81개(순수 추천 30·등록/확인 29·상품 UI 16·비교 진입 6)가 통과했다. 새 `judge-entry` 6개는 실제 `renderJudge`와 실제 `Judge` 규칙을 합성 DOM에서 실행해 즉시 결과·가짜 before 없음·수동 미리보기·기존 진짜 before 유지·계정/state 경계·수정/삭제 도구 보존을 확인한다. 동결 코드 11개 파일/커밋 일치, 세 빌드·15 scripts·마커/CSP 검사를 확인했으며 이번 범위의 추가 확정 P0/P1은 없었다. 검증 코드 `b359d60`의 GitHub 기능 브랜치·초안 PR #10 게시와 최신 `core-flow` 미리보기 7개 파일의 HTTP 200·바이트/SHA 일치를 확인했다. 실제 브라우저·카메라·기기·운영 서버 검증은 별도다.
- **Claude 검토의 범위:** 후속 Opus 5.5 검토는 전달한 설명·검증 증거에 기반했다. 소스 열람·테스트·브라우저 실행을 한 독립 검토로 기록하지 않는다. 실제 상품 결과를 먼저 보이고 세부 근거를 접는 제안을 반영했으며 사업 파일럿 실행·사용자 효과는 아직 확인하지 않았다.
- **재검토 조건:** 실제 모바일에서 등록·확인·첫 상품까지 걸리는 행동과 이탈을 측정하고, 공식 상품별 미확인 속성·가격·옵션·재고를 재확인한다. 다음 실제 구매에서 추천·구매 또는 보류 이유·2주 후 착용/반품을 확인하는 시험은 계획이다. 단순 규칙 통과로 취향 적합성·핏·사업성·출시 준비나 100점에 가깝다고 평가하지 않는다.

## 구현 주체와 다음 설계

사용자가 사업·제품·시스템 검토를 Claude Opus 5.5에, 기능 구현을 Codex에 맡겼다. 위 코드와 문서는 AI가 작성·검토한 부분을 포함한다. 자동 테스트의 통과와 사용자 효용·사업 가설 검증은 구분한다.
PurchaseCase의 현재 상태 행+append-only 이벤트, 상태 변경의 `expectedCaseVersion`, 서버 `server_seq` 순서, 날짜 정밀도 보존은 후속 제안이다. 지금의 pickLog/decisions를 이미 통합했다고 기록하지 않는다.
선택을 바꿀 때는 이 파일에 문제를 바꾼 사실·대안·측정/검증·이전 계획을 남긴다. 새 테스트·CI·배포·실사용의 증거가 없으면 점수나 출시 준비도를 높여 적지 않는다.

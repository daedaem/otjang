# 어울 앱

서버 없이 브라우저에서 동작하는 정적 웹앱입니다. 실행·빌드에는 외부 패키지가 필요 없으며, 저장소 테스트에만 개발 의존성 `fake-indexeddb`를 사용합니다. Node 22에서 `npm ci --ignore-scripts`, `npm test`, `npm run build`로 확인합니다.

처음 방문하면 예시 옷 6벌로 코디·상품을 바로 보여 줍니다. "내 옷으로 바꾸기"에서 종류를 고르고 저장하면 실제 옷장으로 전환합니다. 사진·이름은 선택 사항이며 첫 저장 실패나 취소 때 예시는 유지됩니다. 같은 종류도 각각의 ID로 보관하고, 내 사진을 코디에 보여 줍니다. 사진을 자동 인식한 결과는 아닙니다.

`eoul:v1` 보유 종류는 최초 실행 때 이전하고 원문 키는 변경하지 않습니다. 이후 옛 버전 기록이 바뀌면 알림을 띄우고, 사용자가 확인한 추가 종류·찜만 가져옵니다. 기존 core-flow 앱의 사진·동기화 자료는 별도 모델이며 자동으로 가져오지 않습니다.

| `src/wardrobe-store.js` | IndexedDB 상태·사진 동시 저장, 충돌 보호, 사진 포함 바이너리 백업 |
| `src/garment-photo.js` | 기기 내 사진 축소·JPEG 변환, 외부 전송 없음 |

| `src/query.js` | 한 줄 요청 해석: 아이템·상황·계절·색·예산·"X에 어울리는 Y" |
| `src/data/slots.js` | 아이템 자리 정의(예: 화이트 옥스퍼드 셔츠): 스타일 점수, 상황, 계절, 추천 이유, 입는 법 |

## 추천이 정해지는 방식

1. **아이템 점수**: 고른 스타일에서의 중요도, 지금 계절, 고른 상황, 그리고 가진 옷과 같은 코디에 들어가는 횟수를 더합니다. 색을 모르는 셔츠는 셔츠 종류로만 매칭합니다. 여러 코디 자리에 맞더라도 실제 옷 ID 한 개로 세며, 특정 색을 이미 보유했다고 확정한 결과는 아닙니다.
2. **상품 고르기**: 각 아이템 자리에서 예산 안의 상품을 `평점 × log10(후기 수 + 10)` 순서로 고릅니다. 같은 자리의 다른 상품은 상세 화면의 "다른 선택"에 보여 줍니다.
3. **코디**: 코디 공식의 역할마다 가진 옷이 있으면 그 옷을 쓰고, 없으면 예산 안의 실제 상품으로 채웁니다. 가진 옷을 많이 쓰는 코디가 먼저 나옵니다.
4. **한 줄 검색**: 요청에서 아이템·상황·계절·색·예산을 뽑아 칩으로 보여 주고, 같은 점수 체계로 상품을 고릅니다. "청바지에 어울리는 신발"처럼 기준 아이템이 있으면, 그 아이템과 같은 코디 공식에 들어가는 상품을 먼저 보여 주고 그 아이템을 넣은 코디도 함께 만듭니다. 검색한 옷은 실제 보유 목록에 있을 때만 "내 옷"으로 표시합니다.
5. **상품 상세의 코디**: 같은 종류의 다른 상품으로 바꾸지 않고 상세 화면에서 선택한 상품을 코디와 합계에 반영합니다.

스타일 점수와 코디 공식은 편집자 판단입니다. 사용자 반응으로 검증한 값은 아닙니다.

## 상품 데이터

- 출처: 무신사 상품 페이지에 들어 있는 구조화 데이터(schema.org `Product`)의 상품명, 브랜드, 판매가, 평점, 후기 수, 대표 이미지 주소.
- 확인 날짜는 상품마다 `checkedAt`에 남기고, 앱 하단과 상세 화면에 표시합니다.
- 가격은 확인 시점의 판매가입니다. 회원 할인·쿠폰·배송비는 반영하지 않습니다.
- 이미지는 무신사 이미지 주소를 그대로 불러옵니다. 불러오지 못하면 옷 그림으로 바꿔 보여 줍니다.
- 상품 선택은 편집자가 했습니다. 크롭·과한 그래픽처럼 기본 아이템 역할에 맞지 않는 상품은 뺐고, 아이템마다 가격대가 다른 상품을 2~4개 골랐습니다(`tools/catalog/curation.json`).

### 갱신 방법

```bash
cd app/tools/catalog
npm i -D playwright                                      # 처음 한 번
node search-musinsa.mjs queries.json candidates.json     # 아이템별 검색 후보 수집
# candidates.json을 보고 curation.json에 {상품번호: [자리 id, 색]}을 추가
node read-musinsa.mjs curation.json snapshot.json        # 상품 페이지에서 값 읽기
node make-products.mjs                                   # src/data/products.js 생성
```

수집 도구는 개인 프로젝트용으로 요청 사이에 간격을 두고 소량만 읽습니다. 공개 서비스로 운영하려면 판매처의 제휴·상품 API나 이용 약관에 맞는 방식으로 바꿔야 합니다.

## 개인정보

가입·서버·분석 도구가 없습니다. 취향·옷·찜·사용자가 선택한 사진은 IndexedDB `eoul-wardrobe-v2`에 보관합니다. 프로필의 "이 옷장 비우고 처음부터"는 이 새 저장소의 현재 옷장과 참조 사진을 지우며, 이전 `eoul:v1` 원문과 별도 core-flow 저장소는 변경하지 않습니다. 전체 백업은 사진을 포함한 `.eoul` 파일입니다. 복원 전 내용과 교체 범위를 표시합니다. `.eoul-recovery`는 손상·미지원 기록을 보존하는 개발 지원용 파일이며 일반 복원에서는 거부합니다.

사진 입력은 JPG·PNG·WebP 25MB 이하, 저장본은 긴 변 최대 1024px JPEG 800KB 이하, 옷은 최대 200벌입니다. 기기의 실제 저장 공간이 먼저 부족할 수 있습니다. HEIC 변환, 실제 휴대폰 카메라·EXIF/GPS, 저장소 삭제·장기 보관은 검증을 마치지 않았습니다. 개인 사진을 GitHub에 포함하지 않습니다. 앱의 외부 요청은 상품 이미지와 사용자가 누른 판매처 링크이며 상품 이미지에는 `referrerpolicy="no-referrer"`를 붙입니다.

브라우저 저장소는 origin 단위입니다. 현재 GitHub Pages의 여러 경로는 보안상 격리된 앱이 아닙니다. 전용 서비스 주소·같은 origin의 다른 코드 점검은 정식 출시 전 운영 과제로 남아 있습니다. 서버 저장·계정 간 동기화를 제공한다고 표현하지 않습니다.

설계 이유·저장 형식·복구·남은 검증은 [실제 옷 등록 인수인계](../docs/instant-garments-handoff-20261014.md), 출시 전 평가 기준은 [평가와 파일럿 계획](../docs/prelaunch-evaluation-20261014.md)을 참고합니다.

# 어울 앱

서버 API 없이 브라우저에서 동작하는 정적 웹앱입니다. 배포물의 실행 의존성은 없으며, 테스트는 Node 22와 `npm ci`로 설치한 `fake-indexeddb@6.2.5`를 사용합니다.

## 추천이 정해지는 방식

1. **아이템 점수**: 고른 스타일에서의 중요도(첫 번째 스타일 100%, 나머지 85%), 지금 계절, 고른 상황, 그리고 가진 옷과 같은 코디에 들어가는 횟수를 더합니다. 가진 종류는 다시 추천하지 않습니다.
2. **상품 고르기**: 선호 브랜드를 먼저, 그다음 `평점 × log10(후기 수 + 좋아요/8 + 10)` 순서로 고릅니다. "내 브랜드만"이면 선호 브랜드 상품만 씁니다. 이 값은 인기 지표이며 품질·핏의 검증값이 아닙니다.
3. **코디**: 코디 공식의 역할마다 가진 옷이 있으면 그 옷을 쓰고(같은 종류가 여러 벌이면 색이 가장 잘 맞는 옷), 없으면 품질·권장 색·색 조화·선호 브랜드를 함께 보고 실제 상품으로 채웁니다.
4. **색 조화**: 포인트 색(그린·레드·핑크 등)은 한 코디에 하나까지, 상·하의는 밝기 차이가 있을 때 가점입니다. 미니멀 스타일은 비슷한 톤끼리 맞추는 것을 가점으로 봅니다.
5. **내 옷장 코디**: 가진 옷만으로 모든 필수 역할이 채워지는 코디("오늘 뭐 입지?")와, 하나만 사면 되는 코디를 따로 보여 줍니다.
6. **한 줄 검색**: 요청에서 아이템·상황·계절·색·예산을 뽑아 칩으로 보여 주고, 같은 점수 체계로 상품을 고릅니다. "청바지에 어울리는 신발"처럼 기준 아이템이 있으면, 그 아이템과 같은 코디 공식에 들어가는 상품을 먼저 보여 주고 그 아이템을 넣은 코디도 함께 만듭니다.

스타일 점수와 코디 공식은 편집자 판단입니다. 사용자 반응으로 검증한 값은 아닙니다.

사진 없는 일반 셔츠는 `slot:null, kind:'shirt'`로 남습니다. 코디에서는 셔츠 역할의 후보로 쓰되 소재·무늬는 확인하지 않았음을 표시합니다. 특정 기본템을 모두 소유한 것으로 세지 않고, 한 실제 옷 ID가 한 코디의 두 역할을 채우지 않습니다. 검색에 언급한 청바지도 실제 보유로 만들지 않습니다. 선택한 상품 상세의 코디에는 그 상품 ID를 고정합니다.

## 상품 데이터

- 출처 1: 편집자가 고른 상품 157개. 무신사 상품 페이지의 구조화 데이터(schema.org `Product`)에서 상품명·브랜드·판매가·평점·후기 수·이미지를 읽었습니다.
- 출처 2: 브랜드 목록. 브랜드(또는 "브랜드 + 대표 아이템")로 무신사를 검색한 결과 화면에서 상품 번호·이름·판매가·평점·후기 수·좋아요 수·이미지를 읽고, `tools/catalog/classify.mjs`가 이름의 단어로 종류와 색을 분류합니다. 색 표기가 없는 상품은 사진 가운데에서 색을 짐작합니다(`image-colors.json`). 아동·중고·그래픽·세트·트레이닝 상품은 뺍니다. 브랜드·종류마다 인기 순으로 3개까지 씁니다.
- 확인 날짜는 상품마다 `checkedAt`에 남기고, 앱 하단과 상세 화면에 표시합니다.
- 현재 생성 결과는 884개입니다. 신발 이름이 옷 종류에 들어간 경우, 수영복·장갑·반바지·라이선스 그래픽, 기능성 아우터를 후드·블루종으로 분류한 경우는 공통 제외 정책(`catalog-policy.js`)과 `fixes.json`으로 정리했습니다. `colorSource`는 `curation`, `correction`, `name`, `image`를 구분하고, `image` 색은 색 조화 계산에서 제외합니다. `classification`은 편집 분류/상품명 규칙의 출처이지 판매처 공식 카테고리 검증을 뜻하지 않습니다.
- 관리용품·아동복 제목 제외 규칙을 생성과 추천에 함께 적용합니다. 구두주걱·아동 쇼트올의 실제 오분류 사례를 제거했습니다. 제목 규칙으로 모든 오분류를 막을 수는 없습니다. 공식 상품 카테고리 허용 목록과 원문 해시를 이용한 수동 정정 재검토는 후속 과제입니다.
- 가격은 확인 시점의 판매가입니다. 회원 할인·쿠폰·배송비는 반영하지 않습니다.
- 이미지는 무신사 이미지 주소를 그대로 불러옵니다. 불러오지 못하면 옷 그림으로 바꿔 보여 줍니다.
- 상품 선택은 편집자가 했습니다. 크롭·과한 그래픽처럼 기본 아이템 역할에 맞지 않는 상품은 뺐고, 아이템마다 가격대가 다른 상품을 2~4개 골랐습니다(`tools/catalog/curation.json`).

### 갱신 방법

```bash
cd app/tools/catalog
npm i -D playwright                                      # 처음 한 번
node search-musinsa.mjs queries.json candidates.json     # 아이템별 검색 후보 수집 (편집용)
node read-musinsa.mjs curation.json snapshot.json        # 고른 상품의 페이지에서 값 읽기
node scan-brands.mjs brand-queries.json raw.json         # 브랜드 목록 화면 수집
node classify.mjs raw.json brands.json                   # 브랜드 목록 결과 분류
node make-products.mjs                                   # src/data/products.js 생성
# 잘못 분류된 상품은 exclude.json(빼기) 또는 fixes.json({번호: {slot, color}})으로 바로잡는다
```

수집 도구는 개인 프로젝트용으로 요청 사이에 간격을 두고 소량만 읽습니다. 공개 서비스로 운영하려면 판매처의 제휴·상품 API나 이용 약관에 맞는 방식으로 바꿔야 합니다.

## 개인정보

가입·서버 API·분석 도구가 없습니다. 취향·옷·찜과 사진은 `eoul-wardrobe-v2` IndexedDB의 같은 트랜잭션으로 저장합니다. 사진 입력은 25MB 이하, 변환본은 긴 변 1024px·JPEG 800KB 이하입니다. HEIC 직접 입력은 지원하지 않습니다. 예전 `eoul:v1` localStorage와 `eoul` 사진 DB는 읽기 전용으로 보존하며 자동으로 지우지 않습니다.

프로필에서 `.eoul` 사진 포함 백업, 내용을 확인한 뒤 교체 복원, 현재 옷장 비우기를 제공합니다. 누락된 구형 사진은 사용자 확인 후 `photoMissing:true`로 가져옵니다. `.eoul-recovery`는 새 DB의 원문·사진 및 구형 localStorage 문자열을 보관하는 개발 지원 파일이며, 예전 Claude 사진 DB 전체의 백업은 아닙니다. 자세한 형식과 장애 절차는 [인수인계](../docs/instant-garments-handoff-20261014.md)를 따릅니다.

외부 요청은 상품 이미지와 사용자가 여는 판매 링크입니다. 개인 사진을 업로드하지 않으며 상품 이미지에는 `referrerpolicy="no-referrer"`를 붙입니다. 브라우저 저장은 기기·브라우저·origin 단위입니다. GitHub Pages의 서로 다른 경로는 보안 격리가 아니며 정식 서비스의 전용 origin은 미완료 과제입니다.

## 구매 여정과 지원 범위

3탭은 추천/내 옷장/구매 여정입니다. 기존 찜은 구매 여정 안에 유지합니다. `journeys`는 상품·옵션 한 개, 수량 1의 사용자 직접 기록이며 다른 옵션은 `forkedFrom`으로 같은 첫 후보에 연결한 새 기록입니다. 결정 buy/hold/skip와 실제 기록 단계 candidate/ordered/received/kept/returned는 분리합니다.

수령은 잠정 상태입니다. 받은 옷과 여정을 원자 저장하지만 `kept`를 누르기 전에는 보유 코디에서 제외합니다. 주문/수령 중이거나 비슷한 옷이 있다고 확인한 종류는 추가 구매 후보를 잠시 멈추며 실제 보유로 만들지는 않습니다. 반품·처분한 이전 옷은 추천에서 제외하고 raw garments/사진은 보관합니다. 자료를 직접 삭제했다면 자동 부활 대신 명시적으로 다시 등록하도록 합니다.

사진 Blob은 기존 garments만 참조합니다. 후보는 HTTPS 링크·메타데이터만 보관하고 자동으로 외부 페이지를 읽지 않습니다. 원주소는 로컬 비공개, 공유용 주소는 별도 규칙이 필요한 데이터입니다. 현재가·최저가·핏·가상 착용·확인된 주문/반품을 검증하지 않습니다. 최대 200여정, 여정당 512이벤트, 전체 상태 JSON 850,000바이트의 한도가 있습니다. 여정 JSON은 500KiB에서 백업을 안내하고, 600KiB를 넘기는 증가 쓰기는 거절해 옷장 기록을 위한 여유를 둡니다. 기존 대용량 기록의 읽기·백업·복원·감축과 여정을 바꾸지 않는 옷장 쓰기는 전체 한도 안에서 유지합니다. 실제 브라우저 저장 공간 부족은 별도입니다.

메모 저장·후보 수정·확인 변경도 이력에 남습니다. 예전 M 주문을 L로 정정해도 원래 주문 이벤트의 M은 그대로 보관합니다. 다른 옵션 추가는 별도 여정이며 원래 기록을 바꾸거나 새 주문으로 자동 처리하지 않습니다. v4 이전 이력은 당시 옵션·이유가 없으므로 `details:null`로 남기고, 현재 알려진 값만 이전 시점의 `imported`에 보관합니다. 512개로 가득 차거나 마지막 기록이 미래인 경우는 이벤트를 덧붙이지 않고 기존 현재 값을 유지합니다.

가진 옷 확인에서 옵션·이유와 옷·사진은 함께 저장됩니다. 받은 옷과 후보 정보는 자동으로 덮어쓰지 않습니다. 차이를 보여주고 선택한 항목만 적용하며, 직접 붙인 옷 이름·브랜드·사진은 기본 선택에서 유지합니다. 종류·색이 다르더라도 같은 종류의 실제 옷을 교체 대상으로 고를 수 있습니다. “비슷한 옷 있음”만 답한 경우 그 여정의 판단에만 쓰며, 실제 옷과 연결해야 다른 추천에도 반영합니다. 안 사기·반품 사유는 상품을 자동으로 숨기거나 점수를 낮추는 근거가 아닙니다. “다시 추천하지 않기”는 사용자가 별도로 선택합니다.

검증은 Node 22의 249개 자동 검사와 단일 HTML 빌드입니다. 실제 번들 콜백/fake IndexedDB를 포함하지만 DOM·사진 디코딩은 대역입니다. 실제 브라우저 렌더링·휴대폰 카메라·실거래 검증은 별도입니다. 자세한 선택 이유와 전체 완료 기준은 [원스톱 계약](../docs/onestop-product-contract-20261014.md)을 봅니다.

보유 상태를 정리하는 정확한 수령·보유 확정·반품 전이와 기존 옷 처분 여부 변경에는 80KiB의 추가 여유를 두어 여정 680KiB까지 허용한다. 후보·옵션·이유·피드백을 함께 바꾸거나 착용·메모를 추가하는 쓰기에는 이 예외를 적용하지 않는다. 이벤트 당시 값과 현재 값이 일치하고 기존 이력과 다른 여정이 그대로인 경우만 허용한다. 전체 850,000바이트와 여정당 512이벤트 한도는 유지한다. 여정 용량과 별개로 전체 상태의 여유가 64KiB 이하이면 백업을 미리 안내하며 사진 Blob은 이 JSON 용량에 포함하지 않는다.
